## 0. 第六阶段先定死的实施决策

### 0.1 本阶段定位

第六阶段不定义为“并行化阶段”，也不定义为“HITL 主链化阶段”。  
第六阶段的准确定位是：

- 真实 AHU 质量收口阶段
- 真实 trace 证据收口阶段
- 检索与规划可解释性收口阶段
- Phase 7 `Send / HITL / persistence` 准入准备阶段

### 0.2 本阶段纳入

- 真实 query 语料与真实 trace 证据沉淀
- 检索质量评估与可观测性补齐
- 复杂 AHU 多子系统规划质量硬化
- 基于真实失败样本的 Repair 扩面
- 阶段验收脚本、输出目录和阶段文档同步
- 为下一阶段 `Send / HITL` 准备副作用清单、`thread_id` 约定和状态键风险清单

### 0.3 本阶段明确不纳入

- 正式主链切换到 `Send` fan-out / fan-in
- 正式主链接入 `interrupt` / checkpointer / persistence
- `workflow.py` / `workflow_trace.py` 主链拓扑改造
- 完整 `internal_flow_objects` body 编译主链化
- LangGraph 版本升级

### 0.4 为什么这轮仍不把 `Send` 和 HITL 拉进正式主链

这不是因为 API 不可用，而是因为当前工程条件还不够稳。

从当前代码看：

- [workflow.py](/d:/yjsproject/midea/workflow.py) 的 `compile()` 仍未传入 checkpointer
- [workflow_trace.py](/d:/yjsproject/midea/workflow_trace.py) 的 `compile()` 也仍未传入 checkpointer
- 当前 `WorkflowState` 还没有为并行共享写入设计 `Annotated[..., reducer]`
- 当前真正稳定的是顺序版 `subsystem_planning`，不是并行版 `subsystem_dispatcher -> Send -> merge`

从 LangGraph 官方文档看：

- `Send` / map-reduce 适合 fan-out，但多个分支写同一状态键时，需要显式 reducer  
  参考：<https://docs.langchain.com/oss/python/langgraph/use-graph-api>
- durable execution 要求同时具备 `checkpointer`、`thread_id`、确定性重放和副作用幂等性  
  参考：<https://docs.langchain.com/oss/python/langgraph/durable-execution>

因此，第六阶段的正确做法不是直接改主链，而是先把“真实质量和真实准入证据”补齐。只有这样，下一阶段再上 `Send / HITL` 才不会把问题放大。

## 1. 开工时识别的核心问题（保留归档）

> 本节保留第六阶段开工时的原始问题背景；若需查看当前正式状态，请直接读取 `AHU程序/第六阶段当前状态交接.md`。

### 1.1 deterministic suite 已有，但真实质量证据仍偏弱

当前有：

- `scripts/run_phase5_query_suite.py`
- `tests/test_phase5_workflow_query_suite.py`

它们很好地守住了契约稳定性，但它们主要依赖固定 stub、固定 payload、固定资产，不足以证明真实 `AnalysisAgent + RetrievalAgent + AHU 资产 + 当前环境` 的稳定性。

### 1.2 检索层已经可用，但“为什么检到这些资产”仍不够透明

当前 `retrieval_bundle.metadata` 已有计数，但还缺少下一步质量分析最需要的东西：

- top-N 子流程模板 ID
- top-N system pattern ID
- 关键召回结果的排序和分数
- “缺了哪个子系统模板”这类直接可诊断的信息

这会导致我们知道“检索数量不对”，但不容易快速定位是资产缺失、打分错误还是 query 变体失真。

### 1.3 复杂 AHU 多子系统案例已经能跑，但回归矩阵还不够完整

当前代码和测试已经覆盖了部分真实多子系统组合，但还没有形成正式的阶段级“黄金样例矩阵”。

缺少的不是单个 case，而是一个可复用的基线集合，例如：

- 送风机 + 电加热
- 送风机 + 冷水阀
- 送风机 + 直膨
- 送风机 + 风阀 / CO2
- 送风机 + 排风机
- 三子系统联动场景

### 1.4 Repair 已形成闭环，但支持面仍然偏窄

当前 [agents/repair_agent.py](/d:/yjsproject/midea/agents/repair_agent.py) 只稳定支持少数 rule：

- `ir.unresolved.ambiguous_shared_signal`
- `ir.unresolved.synthetic_shared_signal_source`
- `ir.unresolved.shared_signal_owner_mismatch`
- `ir.unresolved.missing_local_edge_endpoint`
- `compile.wire.port.range`

这说明 Repair 已经有价值，但还不足以覆盖真实阶段里更常见的模板接口不匹配、fallback 触发、占位源缺失等问题。

### 1.5 真正进入 `Send / HITL` 前的准入资料还没准备好

当前虽然已有：

- `AHU程序/Phase4_Send并行预留设计.md`
- `AHU程序/Phase4_HITL_POC记录.md`
- `scripts/poc_phase4_hitl.py`

但还缺：

- 节点级副作用幂等性清单
- `thread_id` 生成与生命周期约定
- 哪些状态键未来并行化时需要 reducer 的正式清单
- 哪些节点在 durable execution 下必须拆成 task 的清单

## 3. 第六阶段关键实施原则

### 3.1 先补真实质量，再谈主链升级

- 第六阶段的成功标志不是“图更复杂”，而是“现有图在真实场景下更可信”。
- 所有并行化和 HITL 相关工作，都以“准入准备”形式完成，不直接改正式主链。

### 3.2 真实样本与确定性样本并存，但职责不同

- `Phase 5 query suite` 继续作为契约守门
- `Phase 6 real query suite` 负责验证真实质量与真实证据

不能用真实样本替代 deterministic suite，也不能用 deterministic suite 代替真实质量证据。

### 3.3 Repair 扩面要以真实失败样本驱动

- 先统计真实 suite 中最常见的失败桶
- 只扩 deterministic 可控的 patch
- 对暂时不能自动修的类型，优先补结构化 reject reason 和 trace 诊断，而不是硬做不稳的自动修复

### 3.4 第六阶段必须输出可留档产物

本阶段不是只改代码，还必须稳定产出：

- 真实 query suite 摘要
- 检索评估摘要
- 保留的 trace 目录
- 失败桶统计
- `Send / HITL` 准入资料

## 4. 工作包与优先级

| 优先级 | 工作包 | 目标 |
| --- | --- | --- |
| `P0` | 工作包 A：真实 Query Suite 与证据 trace | 建立真实环境下的阶段交付证据 |
| `P0` | 工作包 B：检索评估与可观测性补齐 | 看清楚模板、pattern 和资产召回问题 |
| `P0` | 工作包 C：复杂 AHU 规划质量硬化 | 把多子系统案例从“能跑”推进到“更稳” |
| `P1` | 工作包 D：基于真实失败样本的 Repair 扩面 | 提高真实场景下的修复命中率与 reject 质量 |
| `P1` | 工作包 E：trace、输出目录与阶段文档收口 | 让阶段结果可回看、可比对、可交付 |
| `P2` | 工作包 F：Phase 7 `Send / HITL` 准入包 | 为下一阶段主链升级准备工程前置条件 |

### 4.1 默认开工顺序

第六阶段不是六个工作包同时平推，而是按下面顺序开工：

1. 工作包 A：先把真实 case 语料、输出目录、失败桶口径和 contract test 立住。
2. 工作包 B：在 A 的 case 语料上补检索评估字段、指标和分类规则。
3. 工作包 C：基于 A/B 第一轮结果做规划质量硬化，优先处理黄金成功 case。
4. 工作包 D：等真实失败桶统计稳定后，再挑前 2 个适合 deterministic patch 的问题扩面。
5. 工作包 E：跟随 A/B/D 的摘要字段与输出目录一起收口，不单独提前做。
6. 工作包 F：只在前面产物已成型后补齐准入资料，不作为本阶段阻塞 A/B/C 的前置项。

### 4.2 开工前先定死的通用规则

- `phase6_real_query_cases.json` 是第六阶段唯一正式 case 源；A/B/C/D 统一复用，不允许每个脚本各自维护 case 列表。
- `failure_bucket` 必须使用稳定枚举，不允许在脚本里临时拼中文结论；至少包含：
  - `passed`
  - `repair_then_passed`
  - `ambiguous_shared_signal`
  - `retry_budget_exhausted`
  - `template_interface_mismatch`
  - `missing_placeholder_source`
  - `retrieval_asset_gap`
  - `retrieval_ranking_issue`
  - `other_retryable_error`
  - `unexpected_exception`
- 第六阶段所有新增脚本都必须同时输出 JSON 和 Markdown 摘要，并回写绝对路径。
- 第六阶段新增测试至少包含两类：
  - contract test：验证 case/schema/摘要落盘和基础字段完整性
  - regression test：验证新增 metadata、failure bucket 和评估分类不会破坏旧 consumer

## 8. 第七阶段准入条件

只有在以下条件同时满足后，才进入正式 `Send` 并行或 HITL 主链化阶段：

1. 第五阶段 deterministic query suite 稳定通过。
2. 第六阶段真实 query suite 的黄金 case 稳定通过，且失败 case 有稳定分类。
3. 检索评估已经能清楚地区分资产缺失、query 变体不足和排序问题。
4. `repair` 扩面后的真实高频失败桶已明显下降，或已具备稳定 reject 语义。
5. 已完成副作用幂等性清单、`thread_id` 约定和状态键 reducer 风险清单。
6. 届时再重新验证 LangGraph 官方要求对应的工程条件：
   - `Send` 分支共享写入的 reducer
   - `checkpointer`
   - `thread_id`
   - durable execution 下的确定性重放与幂等副作用

## 9. 最终收口判断

第六阶段的任务不是“让图更复杂”，而是“让现有图更可信、更可交付、更适合进入下一轮主链升级”。

如果这一阶段做得好，下一阶段上 `Send / HITL` 时，面对的将是一个质量边界清楚、trace 证据完整、失败桶可解释的系统；而不是一条还没把真实质量收口就继续叠复杂度的主链。
