> 复核时间：2026-04-16

## 1. 先说结论

这套工作流已经不是“想法”或“原型”了，而是一条可以运行、可以回归、可以做有限自动修补的工程化主链。

但它也还不是设计稿里那种“完整 V2 终态”。现在最成熟的是：

- 分层规划
- 结构化中间产物
- 确定性编译
- 结构化验收
- 有边界的 Repair 闭环
- 可重复回归和 trace 诊断

现在还不成熟的部分主要是：

- 真实 AHU 大样本场景下的规划质量
- 检索资产和召回质量
- 更大范围的自动修复覆盖
- `Send` 并行派发
- 正式 HITL / `interrupt` / persistence 入主链
- 完整 `internal_flow_objects` body 编译复用

如果只按“代码里真的实现了什么”来判断：

- `Phase 1-4`：已经是可运行系统
- `Phase 5`：已经做了不少加固，但主要是契约、诊断和确定性验收层的加固，还不能等同于“真实业务质量已经完全闭环”

## 2. 当前状态怎么理解最准确

这套工作流本质上是在做一件事：把自然语言需求逐步变成结构化工程对象，最后再编译成平台 JSON。

当前正式主链是：

```text
analysis
  -> retrieval
  -> architecture_planning
  -> subsystem_planning
  -> global_assembly
  -> coding
  -> verification
  -> repair_router
  -> (accept -> END) / (repair_agent -> subsystem_planning | global_assembly | coding)
```

这里有一个很容易混淆的点：

- 如果从“主链拓扑有没有换”来看，当前还是第四阶段形态
- 如果从“仓库里实际多做了什么”来看，第五阶段前四批加固已经进来了

所以最准确的说法不是“还停在第四阶段”，而是：

> 主链仍是第四阶段 Repair 闭环拓扑，但第五阶段前四批的共享信号治理、结构化 repair payload、deterministic query suite 和 trace 摘要扩展已经落地。

## 3. 已经真正落地的能力

### 3.1 Phase 1：编译和验收底座已经稳定

这一阶段已经形成了完整闭环，不是空壳：

- 有 `AssembledGraphIR`
- 有确定性编译器 `CodingAgent`
- 有结构化验收器 `VerifierAgent`
- 有子流程定义和子流程实例编译
- 有基本的端口、连线、作用域校验

简单说，`Phase 1` 已经把“规划结果直接拼 JSON”升级成了“先有中间结构，再做编译和验收”。

### 3.2 Phase 2：检索层已经从单一上下文升级为正式 bundle

当前代码里，检索正式主输出已经是 `retrieval_bundle`，而不是旧的 `retrieval_context`。

已经落地的点包括：

- `atomic_modules`
- `subflow_templates`
- `system_patterns`
- `style_guides`
- AHU 资产构建链
- Chroma 多 collection 读写
- compat 视图回填

这意味着检索层已经不只是“找几个模块”，而是在给后面的规划层提供多种类型的工程资产。

### 3.3 Phase 3：分层规划主链已经真实接入

现在的主规划链已经不是旧 `PlanningAgent` 了，而是三层：

- `ArchitecturePlanner`：负责系统骨架、页签、共享信号草案
- `SubsystemPlanner`：负责每个子系统的模板复用或原子回退
- `GlobalAssembler`：负责把局部结果拼成全局 Graph IR

这一层已经具备的能力包括：

- `analysis_result -> requirement_spec` 的规则投影
- `system_patterns` 的评分和选择
- 页签和子系统拆分
- `planning_order` 串行规划
- 模板复用优先
- 原子模块 fallback
- 全局 Graph IR 组装
- compat `execution_plan` 回填

换句话说，第三阶段不是“文档里说分层”，而是代码里真的已经按分层在跑。

### 3.4 Phase 4：Repair 闭环是真的能跑

第四阶段最重要的事实是：Repair 不是 router 空转，而是有实际 patch 行为。

当前已实现的修补范围虽然有限，但是真实存在：

- `planning`：共享信号归属收敛、重分类为 external
- `assembly`：删除非法局部边
- `compile`：越界端口夹断或删边

同时还具备：

- scope 级 repair budget
- `route_decision`
- `repair_context`
- `repair_history`
- 回跳到 `subsystem_planning / global_assembly / coding`
- trace 摘要中的 repair 轮次、reject 原因和 scope 统计

所以第四阶段可以评价为：闭环已成型，但修复覆盖面还不大。

### 3.5 Phase 5：不是重写主链，而是围绕主链做加固

从当前代码和文档看，第五阶段已经落地的重点不是并行和 HITL，而是下面这些事情：

- 共享信号语义前移和收口
- `Verifier -> RepairAgent` 的结构化 `repair_payload`
- `ambiguous_shared_signal` 的“有限自动修复 + 稳定 reject”
- `scripts/run_phase5_query_suite.py`
- `tests/test_phase5_workflow_query_suite.py`
- `workflow_trace.py` 中新的 Phase 5 诊断字段

所以 `Phase 5` 现在更准确的定位是：

> 在不改变正式主链拓扑的前提下，把复杂规划、repair 语义、诊断和验收基线继续做实。

## 4. 当前最强的地方

我认为这套工作流当前最扎实的地方有四个。

第一，主对象边界比较清楚。`requirement_spec`、`retrieval_bundle`、`architecture_plan`、`subsystem_plan_map`、`assembled_graph_ir`、`compiled_artifact`、`verification_report` 这条主数据链已经形成。

第二，代码和“当前说明文档”基本一致。尤其是 `工作流总结文档.md` 和 `工作流节点输入输出说明.md`，已经比较接近真实实现，不像很多项目那样文档完全落后于代码。

第三，自动化基线已经不弱。本次复核我实际补跑了这些验证：

- 阶段测试合计：`99 passed, 3 subtests passed`
- `tests/test_runtime_versions.py`：`2 passed`
- `tests/test_phase3_workflow.py` 单独复核：`6 passed, 3 subtests passed`
- `scripts/poc_phase4_hitl.py --thread-id phase4-hitl-eval --resume approve`：当前环境可跑通

第四，项目对 LangGraph 新能力的态度比较稳。根据官方文档：

- LangGraph 节点本质上就是围绕共享 state 的函数
- `interrupt` 的恢复依赖 checkpointer
- 使用 persistence 时需要 `thread_id`

参考文档：

- <https://docs.langchain.com/oss/python/langgraph/thinking-in-langgraph>
- <https://docs.langchain.com/oss/python/langgraph/persistence>

结合这一点来看，项目现在把 HITL 先放在独立 POC，而不是急着并入正式主链，我认为这个判断是合理的。

## 5. 目前最需要保持清醒的地方

### 5.1 这还不是设计稿里的完整 V2

设计稿里提到的这些点，目前都没有正式进主链：

- `AmbiguityRouter`
- 人工澄清节点
- `Finalizer`
- `Send` 并行派发
- reducer fan-in
- 正式 HITL / persistence 主链化

所以 `AHU程序/LangGraph工作流V2架构设计.md` 更适合当路线图，而不是“当前实现说明书”。

### 5.2 Repair 现在是“有用但有限”

当前 `repair_agent.py` 是白名单模式，只支持少数 `rule_id`。这意味着：

- 有些问题可以自动修
- 很多 verifier 发现的问题仍然只能 reject

这不是坏事，因为它至少比“假装都能修”更诚实，但这也说明当前 Repair 还只是第一版可用集。

### 5.3 第五阶段的 query suite 很重要，但它主要证明的是“契约稳定”

`scripts/run_phase5_query_suite.py` 的价值很大，它能稳定覆盖：

- 成功通过
- planning repair
- assembly repair
- compile repair
- ambiguous reject
- budget exhausted

但要明确，它主要依赖固定 stub 和固定资产来守住主链行为，不等于真实线上质量已经被证明。

也就是说，它更像“工程回归基线”，不是“业务效果担保书”。

### 5.4 真正最容易波动的还是前半链质量

现在最容易不稳定的地方，其实不是编译器，而是前面的三件事：

- `analysis` 的 LLM 输出质量
- `retrieval` 的资产质量和召回质量
- 复杂 AHU 多子系统场景下的规划质量

这也是为什么当前阶段最重要的后续工作，应该还是“真实样本”和“真实质量”，而不是马上再加新节点。

### 5.5 交付证据还有缺口

文档中提到：

- `outputs/phase4_smoke/...`
- `outputs/phase5_query_suite/...`

已经有落盘结果。

但我这次在当前工作区直接检查时，没有看到这两个目录；当前仓库里能直接看到的固定产物主要是：

- `outputs/phase4_baseline/baseline_20260411_164711/`

这不影响我对“代码能力”的判断，但会影响“交付证据是否齐全”的说服力。换句话说，代码已经做了，证据沉淀还不够完整。

## 6. 文档和代码之间，我建议以后以谁为准

我建议以后优先按下面这个顺序理解当前状态：

1. `工作流总结文档.md`
2. `工作流节点输入输出说明.md`
3. `工作流演进记录.md`
4. `AHU程序/LangGraph工作流V2架构设计.md`

原因很简单：

- 前三份文档是在描述“现在代码实际怎么跑”
- 架构设计稿更多是在描述“理想中的 V2 应该长什么样”

尤其是 `Phase 5` 的定义，已经明显从早期设计稿里的“更偏澄清/HITL/规则库”转成了“共享信号治理、repair 扩面、query suite、trace 收口”。

## 7. 我给当前系统的客观评价

为了方便不熟悉项目的人快速理解，我给一个尽量直白的评级：

| 维度 | 评价 | 说明 |
| --- | --- | --- |
| 主链工程化程度 | 高 | 结构完整，已经能跑、能验、能追踪 |
| 数据契约清晰度 | 高 | 主对象边界已经比较稳定 |
| 自动修复覆盖面 | 中 | 有真实修补能力，但支持范围有限 |
| 真实业务质量证据 | 中等偏弱 | 还需要更多真实 AHU 样本和真实 trace 证据 |
| LangGraph 新能力落地程度 | 预研阶段 | POC 有，正式主链化还没开始 |

如果只用一句话概括：

> 当前系统最成熟的是“结构化主链 + 有边界的 Repair 闭环 + 可重复回归基线”；最不成熟的是“真实检索质量、真实 AHU 大样本质量，以及设计稿里更高级的并行/HITL/澄清机制”。

## 8. 最终判断

我的最终判断是：

- 这套工作流已经具备工程化主链，不应该再把它当作试验性原型
- 但它还不应该被描述成“完整 V2 已完成”
- 更准确的定位应该是：

> 已经完成了一条可运行、可观测、可回归、可局部修补的主链；当前进入的是质量加固和证据补齐阶段，而不是再做一轮大规模拓扑改造的最佳时机

## 9. 我建议的下一步优先级

### P0

- 继续补真实 AHU 多子系统样本，把“能跑通”推进到“规划质量稳定”
- 扩大 `repair_agent.py` 的支持面，把更多 verifier failure 纳入结构化修补或稳定 reject

### P1

- 用真实 `workflow_trace.run_workflow(...)` 补齐并保留交付证据，不只依赖 deterministic suite
- 继续提升 AHU 资产质量和 Chroma 召回质量

### P2

- 等主契约和质量基线更稳后，再推进 `Send` 并行
- 等副作用边界、`thread_id` 约定和持久化方案明确后，再推进正式 HITL / persistence 主链化
