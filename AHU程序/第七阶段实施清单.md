## 0. 第七阶段先定死的实施决策

### 0.1 本阶段定位

- 第六阶段已经收口，不再把本轮定义为“继续做 Phase 6 A/B/C/D/F”。
- 本阶段的正式目标是：在**不直接切换正式主链拓扑**的前提下，补齐进入 `Send / HITL / persistence` 前必须具备的最小工程条件。
- 本阶段要解决的是**工程运行时边界**，不是再做一轮规划质量摸底。

### 0.2 本阶段纳入

- 正式入口的 `thread_id` / runtime config 契约入链
- `checkpointer` 接线方式与默认兼容行为收口
- `workflow_trace` 的 `thread_id + attempt_id` 映射补齐
- `coding` 的稳定 ID / 可重放边界收口
- `repair_agent` 的 prepare/apply 边界拆分
- `Send + reducer` 的测试图/契约试点
- 改造前基线证据补齐与阶段护栏测试

### 0.3 本阶段明确不纳入

- 不直接把正式主链改成 `Send` 并行版本
- 不直接把 `interrupt / HITL / persistence` 正式接进生产主链
- 不重开第六阶段工作包 A/B/C
- 不在没有新稳定失败桶的前提下强行重开工作包 D
- 不做完整 `internal_flow_objects` body 编译扩面

### 0.4 为什么本轮先做“最小工程改造”而不是直接上主链

- 官方文档要求：要做 persistence / resume，必须有 `checkpointer` 与稳定的 `thread_id`；当前正式入口还没有这两个条件。
- 官方文档要求：要做 durable execution，带副作用或非确定性的步骤应先划清边界；当前 `analysis`、`retrieval`、`coding`、`repair_agent`、`workflow_trace` 还没有全部收口。
- 官方文档要求：并行分支写同一状态键时要用 reducer，并且节点应返回局部 state update；当前正式主链的大部分节点还是“原地改整份 state 后返回”。
- 所以本阶段正确打法不是“直接切到新拓扑”，而是先把**入口契约、重放边界、trace 索引、局部返回模式**补齐。

## 2. 本阶段实施原则

### 2.1 先补运行时契约，再谈拓扑升级

- 本轮优先级高于“并行化”的，是 `thread_id`、`checkpointer`、trace 索引、稳定重放。
- 只有这些边界收口后，`Send / HITL` 主链化才有意义。

### 2.2 所有改造默认保持主链兼容

- `run_workflow(user_query)` 现有调用方式必须保持可用。
- 新增参数、索引和辅助对象时，默认走可选参数或兼容分支。
- 不能为了准备 Phase 7，先把现有 Phase 4/5/6 基线打坏。

### 2.3 先做可验证的小闭环，不做大而全重构

- 每个工作包都必须有明确落点文件、验证命令和完成定义。
- 先把最小可验证路径打通，再考虑继续扩面。

### 2.4 以官方约束反推实现顺序

- `persistence` 先看入口契约和 checkpoint 接线
- `durable execution` 先看非确定性边界
- `Send` 先看 reducer 与局部 state update
- `HITL` 先看 prepare/review/apply 三段式边界
