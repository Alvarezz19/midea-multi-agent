# 工作流 V2 第四阶段实施清单（可执行版）

> 编写时间：2026-04-09  
> 依据：`工作流总结文档.md`、`工作流演进记录.md`、`AHU程序/LangGraph工作流V2架构设计.md`、当前 `workflow.py` / `workflow_trace.py` / `agents/*.py` / `tests/test_phase3_*.py` 的真实实现  
> 目标：在 `Phase 3 首版已完成` 的基线之上，交付一个可运行、可回跳、可审计的 `Repair` 闭环首版。

## 0. 当前基线与第四阶段问题定义

### 0.1 当前已经稳定的能力

- 正式主链已经稳定为：

```text
user_query
  -> analysis
  -> retrieval
  -> architecture_planning
  -> subsystem_planning
  -> global_assembly
  -> coding
  -> verification
  -> END
```

- `Phase 3` 的正式数据产物链已经跑通：  
  `requirement_spec -> decomposition_result -> architecture_plan -> subsystem_plan_map -> assembled_graph_ir -> compiled_artifact -> verification_report`
- `ArchitecturePlanner`、`SubsystemPlanner`、`GlobalAssembler` 已接入主链。
- `VerifierAgent` 已能稳定输出 `status`、`repair_scope`、`issues`、`warnings`、`metrics`。
- `workflow_trace.py` 已能记录节点输入输出、耗时和顶层字段变更，为第四阶段闭环调试提供基础。

### 0.2 当前真正的缺口

- 当前虽然已经有 `verification_report.status = retryable_error` 和 `repair_scope`，但主链仍是纯线性链，没有任何 repair 回跳。
- `retry_count`、`next_step` 目前只是预留字段，没有实际消费。
- `VerifierAgent` 目前给出的 `repair_scope` 还不够“机器可执行”，缺少明确的修复目标、修复策略和下一跳信息。
- 当前还没有 `RepairRouter`、`RepairAgent`、`repair_context`、`repair_history`、`route_decision`。
- 当前还没有“失败后只回到局部节点重做”的能力；所有失败都直接终止在 `verification`。

### 0.3 第四阶段核心目标

第四阶段只解决一件事：

> 把当前“能发现结构问题”的主链，升级为“能对可修复问题做局部修补并重新验证”的主链。

本阶段完成后，系统至少应具备：

- `verification -> repair_router -> repair_agent -> 局部回跳 -> verification` 的真实闭环
- 基于 `repair_scope` 的局部回跳，而不是从 `analysis` 全链重跑
- 明确的重试预算、退出条件和最终失败口径
- 至少一批高置信度结构问题的自动修补能力
- trace 中可追踪每一轮 repair 的原因、动作、结果

## 1. 先定死的实施决策

### 1.1 本阶段只做 Repair 闭环首版，不同时做 `Send` / HITL / body 编译

- 第四阶段只交付 `RepairRouter + RepairAgent + repair state contract + 局部回跳`。
- 明确不把以下事项混入本阶段首版：
  - `Send` 并行子系统派发
  - reducer fan-in
  - 人工澄清 / `interrupt`
  - `ValidationAgent` 接回主链
  - 完整 `internal_flow_objects` body 编译

原因：

- 当前最直接的结构缺口是 repair 闭环缺失，不是并行缺失。
- `Send` / reducer 在 LangGraph 官方文档中更适合 map-reduce 并行；这一步应放在 repair contract 稳定之后。
- HITL `interrupt` 官方文档明确依赖 persistence/checkpointer；当前项目并未把持久化恢复作为正式基线，不适合与 repair 首版一起上线。

### 1.2 第四阶段继续保持“同步主链 + 条件回跳”，不立即引入 `Command`

- 首版优先用 `add_conditional_edges()` 实现：
  - `verification -> repair_router`
  - `repair_router -> END / repair_agent`
  - `repair_agent -> subsystem_planning / global_assembly / coding`
- 不要求首版就改成 `Command` 路由。

原因：

- 当前仓库已经稳定在显式节点和显式边风格上。
- `add_conditional_edges()` 足够覆盖 repair 路由需求，风险小于直接改成 node 内 `Command` 跳转。

### 1.3 Repair 首版按 scope 局部回跳，不允许默认全链重跑

- `subsystem_plan` 问题：修补后回到 `subsystem_planning`
- `assembly` 问题：修补后回到 `global_assembly`
- `compile` 问题：修补后回到 `coding`
- `passed`：直接结束
- `fatal` / 超出预算：直接结束

### 1.4 首版只自动修“高置信度、可局部 patch”的问题

- 自动修补必须满足：
  - 目标对象明确
  - 修复动作可确定
  - 不需要重新理解整段自然语言
  - 不需要人工判断业务意图
- 对以下问题不做“猜测式修复”：
  - 多导出方共享信号且无法唯一判定归属
  - 需求本身缺信息
  - 需要人工确认的业务策略冲突

这些问题统一转为：

- `status = fatal` 或
- `status = retryable_error` 但 `repair_context.auto_repairable = false`

### 1.5 第四阶段必须引入重试预算与终止条件

建议首版默认：

```json
{
  "total": 2,
  "subsystem_plan": 1,
  "assembly": 1,
  "compile": 1
}
```

要求：

- 任一 repair 轮次都要累加 `retry_count`
- 任一 scope 都要单独累计
- 超出预算后必须终止，不允许无限循环
- 终止时 `final_output` 必须写明：
  - 最终状态
  - 最后一轮失败原因
  - 已执行过的 repair 历史

### 1.6 `ValidationAgent` 继续留在主链之外

- 当前 `ValidationAgent` 仍使用旧契约：依赖 `execution_result.result`
- 其语义验证仍是硬编码 stub，不适合作为第四阶段正式验收节点
- 第四阶段先把“结构修补闭环”做稳，再决定是否单独启动“语义验证回路”

## 2. 第四阶段完成后的目标画像

- `retry_count`

## 3. 第四阶段核心契约定义

## 3.1 `route_decision`

### 目标结构

```json
{
  "action": "end",
  "reason": "verification_passed",
  "target_node": "END",
  "repair_scope": "none",
  "retry_allowed": false
}
```

### 字段要求

- `action`：`end` / `repair`
- `reason`：路由原因
- `target_node`：`END` / `repair_agent`
- `repair_scope`：`none` / `subsystem_plan` / `assembly` / `compile`
- `retry_allowed`：是否允许进入 repair
- `budget_snapshot`：可选，记录预算消耗前后的状态

## 3.2 `repair_context`

### 目标结构

```json
{
  "repair_round": 1,
  "repair_scope": "assembly",
  "target_ids": ["supply_fan_ctrl"],
  "repair_strategy": "infer_missing_export_from_template_ports",
  "auto_repairable": true,
  "patch_instructions": [
    "为 supply_fan_ctrl 补齐 supply_fan_available_flag 的 exported_signals 绑定"
  ],
  "patch_summary": {
    "patched_object": "subsystem_plan_map",
    "patched_keys": ["supply_fan_ctrl.exported_signals"]
  }
}
```

### 字段要求

- `repair_round`：当前第几轮 repair
- `repair_scope`：本轮修补层级
- `target_ids`：目标子系统 / 节点 / 信号 / IR 对象
- `repair_strategy`：确定性的策略名
- `auto_repairable`：本轮是否允许自动修
- `patch_instructions`：面向 trace / 文档的可读描述
- `patch_summary`：真实改动了哪个状态对象
- `next_node`：修补后应该回跳到哪个节点

## 3.3 `verification_report` 第四阶段扩展要求

当前 `verification_report` 只够“给人看”，还不够“给 Router 和 RepairAgent 执行”。  
第四阶段应补齐以下可机读信息：

```json
{
  "status": "retryable_error",
  "repair_scope": "assembly",
  "retryable": true,
  "repair_targets": [
    {
      "scope": "assembly",
      "target_id": "supply_fan_available_flag",
      "rule_id": "ir.unresolved.synthetic_shared_signal_source",
      "candidate_strategy": "infer_missing_export_from_template_ports"
    }
  ]
}
```

### 必须新增或收紧的能力

- 区分 `retryable_error` 与 `fatal`
- 给出 `repair_targets`
- 给出 `candidate_strategy`
- 给出 `target_id` / `subsystem_id` / `signal_name`
- 不允许只返回宽泛的 `repair_scope` 而没有目标

## 3.4 `repair_history`

### 目标结构

```json
[
  {
    "repair_round": 1,
    "repair_scope": "assembly",
    "repair_strategy": "infer_missing_export_from_template_ports",
    "target_ids": ["supply_fan_ctrl"],
    "result": "patched",
    "verification_status_after_rerun": "passed"
  }
]
```

### 要求

- 每轮 repair 都必须落一条历史
- 即使 repair 被拒绝，也要记录 `result = skipped`
- `workflow_trace.py` 必须能看到该字段变化

## 5.5 工作包 E：新增 `RepairAgent` 首版修补能力

### 目标

- 先做一批高置信度、可落地的局部修补

### 需要新增的文件

- `agents/repair_agent.py`

### 建议首版策略

#### 策略 1：`assign_fallback_page`

- 适用问题：
  - `ir.node.page.must_exist`
  - `ir.node.must_belong_to_scope`
- 修补对象：
  - `architecture_plan.pages`
  - 必要时修正目标节点的 `page_id`
- 回跳节点：
  - `global_assembly`

#### 策略 2：`infer_missing_export_from_template_ports`

- 适用问题：
  - `ir.unresolved.synthetic_shared_signal_source`
- 修补条件：
  - 存在且仅存在一个候选子系统，其模板输出端口名可唯一匹配该共享信号
- 修补对象：
  - `subsystem_plan_map[*].exported_signals`
- 回跳节点：
  - `global_assembly`

#### 策略 3：`rebind_template_or_force_atomic_fallback`

- 适用问题：
  - 子系统计划层的模板绑定失败
  - 首轮规划使用了错误模板，且存在唯一更优模板
- 修补对象：
  - `architecture_plan.subsystem_slots`
- 回跳节点：
  - `subsystem_planning`

#### 策略 4：`sanitize_graph_ir_for_recompile`

- 适用问题：
  - `compile.parent.must_exist`
  - `compile.wire.target.must_exist`
  - `compile.wire.port.range`
- 修补对象：
  - `assembled_graph_ir`
- 修补方式：
  - 删除悬空边
  - 删除越界连线
  - 修正缺失作用域的节点到 fallback page
- 回跳节点：
  - `coding`

### 实施要求

- `RepairAgent` 首版优先规则驱动，不默认依赖 LLM
- 每个策略都必须写入：
  - `repair_context`
  - `repair_history`
- 无法唯一修补时必须显式放弃，而不是瞎改

### 验收标准

- 至少 3 类结构问题可被自动修复并在下一轮 `verification` 通过
- 无法自动修复的问题不会进入死循环

## 7. 关键风险与控制措施

## 7.1 风险：Repair 闭环进入死循环

### 控制措施

- 强制 `retry_budget`
- `repair_history` 中记录每轮 scope 和 strategy
- 同一 `rule_id + target_id + strategy` 连续重复时直接停止

## 7.2 风险：RepairAgent 过度修补，掩盖真实问题

### 控制措施

- 首版只允许高置信度策略
- 不能唯一判定时必须跳过自动修补
- 所有 patch 都要写入 `patch_summary`

## 7.3 风险：`workflow.py` 与 `workflow_trace.py` 再次分叉

### 控制措施

- 继续抽共用节点注册函数
- 每次拓扑改动同时更新 trace 入口
- `tests/test_phase4_workflow.py` 同时覆盖两套入口

## 7.4 风险：compile 问题被错误归类到 repair 可自动修范围

### 控制措施

- `compile` scope 首版只做结构 sanitization
- 不做“语义重编译”
- 对仍无法修复的 compile 问题直接终止并保留报告

## 7.5 风险：Phase 4 scope 漂移到并行 / HITL / 语义验证

### 控制措施

- 第四阶段 DoD 只与 repair 闭环绑定
- `Send`、HITL、`ValidationAgent` 统一延后
