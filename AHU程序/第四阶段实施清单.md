# 工作流 V2 第四阶段实施清单（修订稿）

> 日期：2026-04-11  
> 文档定位：本清单用于立即启动 Phase 4。  
> 本版目标：在不扩大发散范围的前提下，把 Repair 闭环实施方案收紧到“状态契约清楚、路由边界清楚、可回放、可验收、可稳定终止”。

## 0. 阶段目标与范围

### 0.1 当前基线（已完成）

- 当前正式主链：

```text
analysis
  -> retrieval
  -> architecture_planning
  -> subsystem_planning
  -> global_assembly
  -> coding
  -> verification
  -> END
```

- 当前系统已稳定在 Phase 3 首版，已有 Phase 1/2/3 回归基线与 runtime 版本基线。
- 当前尚未接入：RepairRouter / RepairAgent、人工澄清中断、Send 并行派发、reducer fan-in、完整 `internal_flow_objects` body 编译。

### 0.2 Phase 4 本阶段目标

本阶段只做一件核心事情：把验证失败后的闭环修复能力接入正式主链，并保证可控重试与可观测。

目标主链升级为：

```text
analysis
  -> retrieval
  -> architecture_planning
  -> subsystem_planning
  -> global_assembly
  -> coding
  -> verification
  -> repair_router
  -> (accept -> END) / (repair_agent -> 回到指定节点)
```

### 0.3 本阶段实现硬约束

- `workflow.py` 与 `workflow_trace.py` 必须继续共用同一套拓扑注册函数，不允许各自维护两份 Phase 4 拓扑。
- RepairAgent 只能修补“下一次重跑真正会消费”的上游对象，不能只修补即将被下游重算覆盖的派生产物。
- 路由预算判断必须按 scope 计数，不能只靠现有单一 `retry_count` 字段。
- Phase 4 V1 默认走规则优先、deterministic patch 优先，不把 LLM 当作主修复器。
- Loop 除了业务侧重试预算，还必须有运行时兜底保险丝，例如 `recursion_limit`。

### 0.4 本阶段不纳入（避免范围失控）

- 不在本阶段把 `subsystem_planning` 改成 `Send` 并行执行，只做接口预留与设计落盘。
- 不在本阶段把 `interrupt` / HITL / persistence 接入正式主链，只做独立 POC。
- 不在本阶段实现完整 `internal_flow_objects` body 编译，保留到后续 Phase 4.x / 5。
- 不在本阶段重写 `AnalysisAgent` / `ArchitecturePlanner` 的主策略，只在 Repair 所需最小范围内补契约。

## 3. 工作包 P0-2：实现 RepairRouter（条件路由 + 有界重试）

### 3.1 目标

把 `verification_report` 转成稳定路由决策，防止无限重试。

### 3.2 涉及文件

- 新增：`agents/repair_router.py`
- 修改：`workflow.py`
- 修改：`workflow_trace.py`
- 新增测试：`tests/test_phase4_repair_router.py`

### 3.3 路由规则（定死）

- `verification_report.status == "passed"` -> `accept`
- `verification_report.status != "passed"` 且 `repair_scope` 不在 `planning / assembly / compile` -> `reject`
- `verification_report.status != "passed"` 且 `retry_counts_by_scope[repair_scope] >= retry_budget[repair_scope]` -> `reject`
- 其他情况按 `repair_scope` 路由：
  - `planning` -> `planning_repair`
  - `assembly` -> `assembly_repair`
  - `compile` -> `compile_repair`

### 3.4 RouteDecision 产物要求

- 每次 `repair_router` 都必须写入 `route_decision`
- `route_decision.decision` 只允许取值：
  - `accept`
  - `planning_repair`
  - `assembly_repair`
  - `compile_repair`
  - `reject`
- `route_decision.reason` 必须是稳定短语，不写自由发挥长文本
- `route_decision.issue_ids` 必须来自本轮 `verification_report.issues`

### 3.5 工作流改动

- 在 Phase 4 拓扑 helper 中预留 `verification -> repair_router -> ...` 的条件边定义。
- P0-2 完成后，允许先把 `repair_router` 作为独立可测节点落地；完整主链闭环接入在 P0-3 与 `repair_agent` 一起收口，避免出现“路由节点已入链但修复节点尚不存在”的半成品拓扑。
- 为 Phase 4 loop 增加运行时兜底，例如 `recursion_limit=40`，防止路由 bug 时出现非预期自环。

### 3.6 验收标准

- 任一失败场景最多重试预算次数，绝不出现死循环。
- `route_decision` 能准确区分：
  - 通过
  - 合法 repair
  - 非法 scope reject
  - 预算耗尽 reject
- 路由预算判断明确基于 `retry_counts_by_scope`，而不是模糊使用总 `retry_count`。

## 4. 工作包 P0-3：实现 RepairAgent V1 并接入正式闭环

### 4.1 目标

先落地可控修复，不追求一次覆盖全部问题类型。

### 4.2 涉及文件

- 新增：`agents/repair_agent.py`
- 修改：`workflow.py`
- 修改：`workflow_trace.py`
- 新增测试：`tests/test_phase4_repair_agent.py`
- 新增测试：`tests/test_phase4_workflow_repair_loop.py`

### 4.3 修复对象与回跳节点映射（定死）

| repair scope | 允许修补的主对象 | 禁止只修补的对象 | 回跳节点 |
| --- | --- | --- | --- |
| `planning` | `architecture_plan`、`decomposition_result`、必要时同步 `shared_signal_registry/global_constraints` | 只修补 `assembled_graph_ir` 或只修补 `compiled_artifact` | `subsystem_planning` |
| `assembly` | `subsystem_plan_map` | 只修补 `compiled_artifact` | `global_assembly` |
| `compile` | `assembled_graph_ir` | 只修补 `compiled_artifact` | `coding` |

补充约束：

- `planning` scope 若需要改变共享信号归属，必须修改真正的上游来源：
  - `architecture_plan.shared_signal_registry`
  - `decomposition_result.shared_signal_registry`
  - 必要时同步 `architecture_plan.global_constraints`
- `assembly` scope 的 `missing_local_edge_endpoint` 根因在 `subsystem_plan_map[*].edges`，因此必须修补子系统局部边定义，再回 `global_assembly`。
- `compile` scope 不能只修改 `compiled_artifact`，因为回 `coding` 后会被重算覆盖；必须回写到 `assembled_graph_ir` 级别。

### 4.4 V1 必做自动修复类型

`planning` 范围：

- `synthetic_shared_signal_source`
- `ambiguous_shared_signal`
- `shared_signal_owner_mismatch`
- 修复方式限定为：
  - 通过 `owner_subsystem_id` 收敛唯一导出方
  - 通过唯一导出方规则收敛共享信号归属
  - 仅在规则可唯一判定时把信号标记为合法 external

`assembly` 范围：

- `missing_local_edge_endpoint`
- 修复方式限定为：
  - 删除非法局部边
  - 在对应 subsystem plan 上补充结构化 `unresolved_items`
  - 明确记录是“降级删除边”而不是“成功恢复语义”

`compile` 范围：

- `compile.wire.port.range`
- 修复方式限定为：
  - 从 `verification_report.issues` 解析问题，不允许只依赖 `verification metrics`
  - 通过 `compiled_artifact.id_map` 的逆向映射反查 `assembled_graph_ir` 中的实例与边
  - 夹断目标端口索引到合法范围，或在无法安全夹断时删除非法边并记录 patch 说明

### 4.5 V1 明确不自动修复的情况（直接 reject）

- `template_input_interface_mismatch`
- `template_output_interface_mismatch`
- `missing_atomic_candidates`
- `missing_placeholder_source`
- `compile.json.must_parse`
- `compile.flow_objects.must_be_dict`
- `compile.wire.target.must_exist`
- 任何需要重新理解自然语言需求、重新大范围规划、或无法唯一定位修改对象的问题

### 4.6 实现约束

- 规则优先：先 deterministic patch，再考虑调用 LLM。
- 每次 patch 必须写入 `repair_history`，结构至少包含：
  - `round`
  - `scope`
  - `issue_ids`
  - `target_state_keys`
  - `actions`
  - `result`
  - `next_node`
- 每次 repair 完成后必须同步更新：
  - `repair_context`
  - `route_decision`
  - `retry_counts_by_scope`
  - `retry_count`
- 对于会被重跑覆盖的下游派生产物，建议在 repair 后显式清空或标记过期：
  - `subsystem_plan_map`
  - `assembled_graph_ir`
  - `compiled_artifact`
  - `verification_report`
  - `final_output`

### 4.7 正式主链接入要求

- 在 P0-3 收口时一次性完成以下接线：
  - `verification -> repair_router`
  - `repair_router -> accept / reject / *_repair`
  - `*_repair -> repair_agent`
  - `repair_agent -> subsystem_planning / global_assembly / coding`
- `workflow_trace.py` 必须同步包装并记录 `repair_router` 与 `repair_agent`，禁止只在正式入口接入而 trace 入口缺失。

### 4.8 验收标准

- 至少以下 3 类负向样例可被自动修复并回到 `passed`：
  - `synthetic_shared_signal_source`
  - `ambiguous_shared_signal`
  - `missing_local_edge_endpoint`
- `compile.wire.port.range` 至少有 1 个样例被稳定修复或稳定 reject，结果必须可解释。
- 不支持的失败类型能稳定终止并输出 `reject` 原因，不会进入摇摆循环。

python -m unittest tests.test_phase4_workflow_repair_loop

## 8. 官方约束（实施中必须遵守）

以下约束来自 LangGraph 官方文档与参考 API：

- 持久化与中断前提：要启用 durable execution / HITL，必须配置 checkpointer，并在运行配置里提供 `thread_id`。
- 恢复一致性：恢复执行会从检查点对应的节点起点重放，不会从 Python 代码某一行继续；有副作用操作必须幂等，必要时包进 task。
- 条件路由：纯分支选择使用 `add_conditional_edges` 即可；只有在“同一个节点里需要同时更新状态并跳转”时，才引入 `Command`。
- 并行派发：`Send` 适用于 map-reduce 风格 fan-out；并行写同一状态键时必须配 reducer。
- Loop 保险丝：即使已有业务重试预算，也应设置 `recursion_limit` 作为运行时兜底。
