# 工作流 V2 第二阶段实施清单（可执行版）

> 日期：2026-04-03
> 目标：在**不改 LangGraph 主链拓扑**的前提下，把单层 `retrieval_context` 升级为三层 `retrieval_bundle`，并让现有 `planning -> assembly -> coding` 链路继续稳定可用。

## 0. 先定死的实施决策

### 0.1 本阶段只改“检索层和消费契约”，不改图拓扑

- 主链仍然保持：
  - `analysis -> retrieval -> planning -> assembly -> coding -> verification -> END`
- 本阶段**不引入**：
  - `add_conditional_edges()`
  - `Send` 并行派发
  - subgraph
  - `ArchitecturePlanner / SubsystemPlanner / GlobalAssembler`
  - `RepairRouter / RepairAgent`

### 0.2 `retrieval_bundle` 是新主契约，`retrieval_context` 是兼容视图

- `WorkflowState` 新增 `retrieval_bundle`
- `retrieval_context` 暂时继续保留，但语义收窄为：
  - `retrieval_bundle.atomic_modules` 的 legacy 视图
- 约束：
  - 新代码优先读取 `retrieval_bundle`
  - 旧代码允许继续读取 `retrieval_context`
  - Phase 2 结束后，不能再新增只依赖 `retrieval_context` 的 consumer
- 需要额外写清的兼容边界：
  - `RetrievalAgent.__call__()` 和 `build_legacy_retrieval_context(bundle)` 正式产出的 `retrieval_context`，**只能**包含 atomic module 视图
  - 但 `Planning / Assembly / Coding` 的 fallback 读取逻辑，仍必须容忍“历史混合型 legacy context”
  - 所谓“历史混合型 legacy context”是指：人工构造的 stub / 旧测试数据里，`relevant_nodes` 可能仍混有 subflow template 文档
  - 这样做的目的，是把“正式运行时输出口径”与“历史回归兼容能力”分开定义，避免自相矛盾

### 0.3 Planner 与 Compiler 的文档 join key 统一使用 `module_type`

- 这是 Phase 2 必须写死的契约。
- 对 `atomic_modules`：
  - `module_type` 延续现有 schema 定义
- 对 `subflow_templates`：
  - 必须同时包含 `template_id`
  - `definition_id`
  - 且必须满足：`module_type == template_id == definition_id`
  - 知识资产中的 `template_json.id` 也必须被重写为稳定的 `definition_id`
  - 原始 flow 中随机生成的 subflow `id` 只允许保留在 `source_info.original_subflow_id`
- 原因：
  - 当前 `PlanningAgent`、`AssemblyAgent`、`CodingAgent` 都以 `module_type` 作为白名单校验和 `doc_map` 主键
  - 当前 `AssemblyAgent` 在有 `raw_definition.id` 时会直接把它当作 `definition_id` 的来源
  - 如果 Phase 2 不统一这一点，Planner 的 bundle-aware 升级和 Assembly/Compiler 的聚合读取会互相冲突，而且 subflow definition 的身份会重新退化成不稳定随机值

### 0.4 Phase 2 的“子流程模板支持边界”先收窄，不隐藏大改动

- Phase 2 **必须完成**：
  - `subflow_templates` 能进入 `retrieval_bundle`
  - Planner 能感知并优先复用子流程模板
  - `Assembly / Compiler` 能从 bundle 中读取子流程模板定义，继续输出**结构正确**的 `subflow_definition + subflow实例`
- Phase 2 **不承诺完成**：
  - 把 `internal_flow_objects` 完整编译进最终平台 JSON
  - 对子流程内部 body 做业务级正确性校验
- 处理方式：
  - `internal_flow_objects` 在知识资产中必须保存，为 Phase 3/4 预留
  - 但当前 `Assembly / Compiler / Verifier` 只要求继续达到 Phase 1 的结构能力边界

### 0.5 知识库迁移采用“增量扩展”，不在 Phase 2 强推全量重构

- 继续保留现有 atomic module collection：
  - `kong_modules_v1`
- Phase 2 新增两类 collection：
  - `ahu_subflow_templates_v1`
  - `ahu_system_patterns_v1`
- 原子模块库在 Phase 2 内仍沿用现有 `json_schema` 元数据字段
- 新增 AHU collection 使用 `payload_json`
- 统一通过 helper 读取：
  - 优先读 `payload_json`
  - 不存在时回退 `json_schema`
- 这样可以避免在 Phase 2 同时重写：
  - `init_knowledge_base.py`
  - `update_knowledge_base.py`
  - `auto_sync_schemas.py`
  - `KnowledgeBaseManager`
  - 全部历史文档

### 0.6 Retrieval API 兼容策略明确如下

- 新增：
  - `retrieve_bundle(...) -> retrieval_bundle`
- 保留：
  - `retrieve(...) -> retrieval_context`
- LangGraph 节点 `RetrievalAgent.__call__()` 的行为改为：
  - 先生成 `retrieval_bundle`
  - 再用 `build_legacy_retrieval_context(bundle)` 回填 `retrieval_context`
- 目的：
  - 不破坏 `init_knowledge_base.py` 等仍直接调用 `retrieve()` 的脚本
  - 不让“节点状态输出”和“工具方法输出”混成一个高风险改动

| Consumer | Phase 2 输入优先级 | 备注 |
| --- | --- | --- |
| `PlanningAgent` | 先 `retrieval_bundle`，再 fallback `retrieval_context` | Phase 2 重点升级对象 |

## 3. 核心数据契约

### 3.1 `retrieval_bundle`

```json
{
  "atomic_modules": [],
  "subflow_templates": [],
  "system_patterns": [],
  "style_guides": [],
  "metadata": {
    "query_text": "",
    "query_variants": [],
    "intent": "general_query",
    "detected_operations": [],
    "selected_case_pattern_id": "",
    "retrieved_atomic_count": 0,
    "retrieved_subflow_count": 0,
    "retrieved_pattern_count": 0,
    "avg_atomic_score": 0.0,
    "query_bundle_version": "phase2-v1"
  }
}
```

### 3.2 `retrieval_context` 的兼容定义

```json
{
  "query": "",
  "relevant_nodes": [],
  "similar_cases": [],
  "metadata": {}
}
```

兼容规则：

- `relevant_nodes == retrieval_bundle.atomic_modules`
- 不把 `subflow_templates` 和 `system_patterns` 偷偷塞进 `relevant_nodes`
- 正式运行时由 `RetrievalAgent` 产生的 legacy context 必须满足上面两条
- 但 fallback consumer 仍需兼容人工构造的历史 mixed legacy context，以保证旧 stub / 回归场景可继续运行
- 理由：
  - 旧 consumer 的语义一直是“原子模块候选集”
  - 如果混入子流程模板，会让旧逻辑对白名单和模块类别的理解失真
  - 兼容读取历史 mixed legacy context 是为了平滑迁移，不代表系统允许继续新增这种正式输出

### 3.3 可编译文档统一契约 `CompilableDoc`

`atomic_modules` 和 `subflow_templates` 都必须能被 `build_compilable_doc_map(bundle_or_context)` 聚合成同一种下游视图。

最低字段要求：

```json
{
  "module_type": "stable_lookup_key",
  "asset_type": "atomic_module | subflow_template",
  "name": "",
  "description": "",
  "category": "",
  "parameters_schema": {},
  "ports_definition": {},
  "template_json": {},
  "keywords": [],
  "usage_guides": []
}
```

补充要求：

- `atomic_module`：
  - `module_type` = 当前 schema 中的 `module_type`
- `subflow_template`：
  - `module_type` = `template_id`
  - 必须额外带：
    - `template_id`
    - `definition_id`
    - `template_role`
    - `internal_flow_objects`
    - `dependency_module_types`
    - `compile_hints`

补充约束：

- `subflow_template.definition_id` 必须是稳定值，不能直接复用样例 flow 里的随机 subflow `id`
- `subflow_template.template_json.id` 必须与 `definition_id` 保持一致
- `AssemblyAgent` / `CodingAgent` 一律把 `definition_id` 视为子流程定义身份，而不是把原始源文件里的随机 `id` 当主键

### 3.4 `system_patterns` 契约

`system_patterns` 不进入 `doc_map`，只服务 Planning。

建议结构：

```json
{
  "pattern_id": "ahu_ctrl_chw_heater_co2__v1",
  "pattern_name": "AHU 控制骨架",
  "system_type": "AHU",
  "description": "",
  "feature_tags": [],
  "required_pages": [],
  "optional_pages": [],
  "subsystem_slots": [],
  "naming_hints": {},
  "layout_hints": {},
  "style_guides": {},
  "source_cases": []
}
```

Phase 2 的真实作用边界需要写死：

- `system_patterns` 在 Phase 2 里只是 `PlanningAgent` 的 prompt hint / soft reference
- 它可以影响“优先复用哪个子流程模板、优先保留哪些页面骨架”的规划倾向
- 但它**不会**在 Phase 2 里变成新的下游硬契约
- Phase 2 的 `PlanningAgent` 仍然只输出单体 `execution_plan`
- 因此不能把 `system_patterns` 理解成“Phase 2 已经开始交付 ArchitecturePlanner 输出”

`style_guides` 的归属也一并明确：

- `system_patterns[*].style_guides` 是 pattern 自身携带的原始风格信息
- `retrieval_bundle.style_guides` 是可选的顶层归一化覆盖层，来源可以是被选中的 pattern 或未来的项目级风格资产
- Phase 2 允许 `retrieval_bundle.style_guides` 为空；不要把它当成本阶段必须做完的独立检索切片

### 3.5 helper 契约

建议新增 `utils/retrieval_bundle_utils.py`，至少提供以下 helper：

- `is_retrieval_bundle(data) -> bool`
- `load_structured_payload(metadata) -> dict`
- `build_legacy_retrieval_context(bundle) -> dict`
- `get_atomic_modules(bundle_or_context) -> list[dict]`
- `get_subflow_templates(bundle_or_context) -> list[dict]`
- `build_compilable_doc_map(bundle_or_context) -> dict[str, dict]`
- `build_allowed_module_types(bundle_or_context) -> set[str]`

约束：

- `build_compilable_doc_map()` 只聚合：
  - `atomic_modules`
  - `subflow_templates`
- 不聚合：
  - `system_patterns`
  - `style_guides`
- `build_legacy_retrieval_context(bundle)` 的 metadata 回填规则必须固定：
  - `query = metadata.query_text`
  - `metadata.retrieved_count = metadata.retrieved_atomic_count`
  - `metadata.avg_confidence_score = metadata.avg_atomic_score`
  - `metadata.intent = metadata.intent`
  - `metadata.detected_operations = metadata.detected_operations`
  - `metadata.query_variants_used = len(metadata.query_variants)`
- 这样可以保证当前 `format_docs_for_planner()` 和旧调试输出不会因为 Phase 2 引入而悄悄退化

### 3.6 三层检索 query 来源规则

Phase 2 必须显式区分三层 query 的来源，不能把当前 atomic-only 的检索计划生硬复用到全部 collection：

- `atomic_modules`
  - 继续沿用当前 `analysis_result.retrieval_plan`
  - 主要使用：`queries / category_l1 / intent / detected_operations / keywords`
- `subflow_templates`
  - 主要从 `analysis_result.scenario_analysis` 生成能力短语
  - 优先使用：`business_goal / system_type / equipment_object / actuator / control_strategy / output_signal`
  - query 目标是“功能模板”，不是原子算子名
- `system_patterns`
  - 主要从 `scenario_analysis` 生成系统级骨架 query
  - 优先使用：`system_type / control_mode / operating_conditions / input_signals / output_signals`
  - query 目标是“页面组织和子系统骨架”，不是单个模块
- 若某一层缺少足够结构化线索，则该层允许退回到 `user_query` 做保守检索
- 这三层 query builder 可以共享底层向量查询工具，但不能共享同一份未区分语义的 query 列表

## 4. AHU 三层知识资产方案

### 4.1 collection 规划

| collection | 作用 | Phase 2 状态 |
| --- | --- | --- |
| `kong_modules_v1` | 原子模块知识库 | 保留并复用 |
| `ahu_subflow_templates_v1` | AHU 子流程模板库 | 新增 |
| `ahu_system_patterns_v1` | AHU 系统骨架模式库 | 新增 |

### 4.2 原子模块库策略

- 数据源：
  - `schemas/*.json`
- Phase 2 不重造 schema
- Phase 2 不迁移历史 metadata 键名
- 运行时通过 helper 兼容：
  - 旧库读 `json_schema`
  - 新库读 `payload_json`

### 4.3 子流程模板提取策略

- 数据源：
  - `AHU程序/flows_*.json`
- 抽取对象：
  - `type = subflow` 的定义对象
  - 与该 subflow `id` 对应的内部子图对象，即 `z == subflow.id` 的对象集合
- 必须保存：
  - 接口定义
  - `template_json`
  - `internal_flow_objects`
  - `dependency_module_types`
  - `source_info`

建议结构：

```json
{
  "module_type": "ahu_supply_fan_std__9in4out__v1",
  "asset_type": "subflow_template",
  "template_id": "ahu_supply_fan_std__9in4out__v1",
  "template_name": "末端组空送风机标准控制",
  "template_role": "supply_fan_control",
  "system_type": "AHU",
  "description": "送风机启停、故障、可用性标准控制模板",
  "keywords": [],
  "usage_guides": [],
  "category": "AHU子流程模板/送风机控制",
  "ports_definition": {
    "inputs": [],
    "outputs": []
  },
  "parameters_schema": {},
  "template_json": {
    "type": "subflow",
    "name": "末端组空送风机标准控制",
    "in": [],
    "out": [],
    "inputs": 9,
    "outputs": 4
  },
  "internal_flow_objects": [],
  "dependency_module_types": [],
  "compile_hints": {
    "supports_multi_instance": true
  },
  "source_info": {
    "source_flows": [],
    "signature_hash": ""
  }
}
```

### 4.4 子流程模板主键生成规则

`template_id` 生成规则必须固定，建议：

1. 先取归一化模板名
2. 再拼接 IO 签名
3. 再拼接稳定版本号或拓扑签名摘要

归一化时明确排除：

- 随机 `id`
- 实例坐标
- 项目名、站点名、医院名
- 仅影响布局、不影响模板身份的注释对象

同时补充定义身份规则：

- `definition_id = template_id`
- `template_json.id = definition_id`
- `source_info.original_subflow_id` 保存原始样例里的 subflow `id`
- 任何从样例 flow 直接抽出的随机 `id`，都不能再参与编译期身份判断

### 4.5 系统骨架模式提取策略

- 数据源：
  - 同一批 `AHU程序/flows_*.json`
- 抽取目标：
  - 页签骨架
  - 子系统槽位
  - 候选子流程模板
  - 命名/布局提示
- 关键约束：
  - 页签主键使用归一化 `page_key`
  - 原始页签标签保留在 `source_cases`
  - `required_pages / optional_pages` 的判定规则必须可测试：
    - 同一 pattern cluster 内，覆盖率 100% 的 `page_key` 进入 `required_pages`
    - 覆盖率大于 0 且小于 100% 的 `page_key` 进入 `optional_pages`
    - 项目名/医院名/站点名差异只能影响原始 `label`，不能影响归一化后的 `page_key`

建议结构：

```json
{
  "pattern_id": "ahu_ctrl_chw_heater_co2__v1",
  "pattern_name": "AHU 控制骨架",
  "system_type": "AHU",
  "description": "",
  "feature_tags": [],
  "required_pages": [
    {"page_key": "io_comm", "label": "IO/通讯", "kind": "io"},
    {"page_key": "control", "label": "控制", "kind": "control"}
  ],
  "optional_pages": [
    {"page_key": "timing", "label": "定时", "kind": "timing"},
    {"page_key": "dx_status", "label": "直膨机状态", "kind": "status"}
  ],
  "subsystem_slots": [],
  "naming_hints": {},
  "layout_hints": {},
  "style_guides": {},
  "source_cases": []
}
```

### 4.6 Phase 2 对知识库维护工具的边界

- `init_knowledge_base.py`
- `update_knowledge_base.py`
- `auto_sync_schemas.py`
- `KnowledgeBaseManager`

Phase 2 内默认只继续服务 `kong_modules_v1`。

新增 AHU 资产由专用脚本负责：

- `scripts/build_phase2_retrieval_indexes.py`

这样可以避免把“多 collection 管理台”也塞进本阶段范围。
