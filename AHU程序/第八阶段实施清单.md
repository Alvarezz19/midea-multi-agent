## 0. 第八阶段核心判断

- 第八阶段开工前的正式主链是顺序版 Repair 闭环；完成工作包 C 后，当前代码事实已升级为：

```text
analysis
  -> ambiguity_router
  -> (clarification_review -> clarification_apply -> retrieval) | retrieval
  -> architecture_planning
  -> architecture_review
  -> (architecture_feedback_apply -> architecture_planning) | subsystem_planning
  -> subsystem_planning
  -> global_assembly
  -> coding
  -> verification
  -> repair_router
  -> (accept -> END) / (repair_agent -> subsystem_planning | global_assembly | coding)
```

- 当前正式结果仍是绿色基线：
  - `phase6_real_query_suite = 12/12 passed`
  - `phase6_retrieval_eval = healthy=12`
  - `python -m unittest discover -s tests -p "test_phase7_*.py"`：`23` 个测试通过
  - `python -m unittest tests.test_phase6_real_query_suite_contract tests.test_phase6_retrieval_eval_contract tests.test_phase6_readiness_contract`：`8` 个测试通过
- Phase 7 真正完成的是工程前置条件，不是正式主链切换：
  - `thread_id / checkpointer` 接线位
  - `workflow_trace` 的 `thread_id + attempt_id` 索引
  - `CodingAgent` 稳定 ID
  - `RepairAgent` 的 `prepare / apply` 边界
  - `Send + reducer` 的独立 POC 与合同测试
- 从“用户友好”角度看，第一优先的人机介入点不应放在 `repair` 末端，而应尽量前移到：
  - `analysis` 之后：用于高歧义场景的需求澄清
  - `architecture_planning` 之后：用于默认主评审的结构确认
- `repair` 路径的人机审核仍然有价值，但它更适合作为兜底，而不是作为用户主入口。

因此，第八阶段的正式目标改为：

> 先把用户最需要的两类前置 HITL 做出来，即“条件式需求澄清”和“架构草图确认”，再把 `repair` 审核保留为后置兜底能力。

## 1. 为什么第八阶段这样排优先级

### 1.1 为什么不是只把 HITL 放在 `repair`

- `repair` 发生得太晚，用户看到的是“系统已经往下跑了很多步之后的补救”。
- 如果方向性理解一开始就偏了，到了 `repair` 再介入，返工成本更高，体验也更差。
- `repair` 更适合做：
  - 高风险 patch 审核
  - 多轮失败后的人工兜底
  - 即将 reject 时的人机裁决

### 1.2 为什么不是把主 HITL 直接塞进 `analysis` 节点内部

- LangGraph 官方文档明确指出，`interrupt()` 恢复时会从该节点开头重跑，而不是从 `interrupt()` 那一行继续。
- 当前 `analysis` 仍含非确定性 LLM 调用，直接把 `interrupt()` 塞在节点中间，恢复时容易重复执行上游逻辑。
- 所以更合理的做法是：
  - `analysis` 负责产出结构化结果
  - 单独增加 `clarification_review` 节点做澄清暂停

### 1.3 为什么 `architecture_planning` 之后最适合作为主评审点

- 到这个阶段，系统已经有了用户可理解的结构草图：
  - 页签
  - 子系统
  - 共享信号
  - 关键全局约束
- 用户此时更容易判断：
  - 是否缺子系统
  - 子系统划分是否合理
  - 哪些联动关系不对
  - 是否符合自己的工程习惯
- 同时又还没有进入 `subsystem_planning` 的细化阶段，返工成本相对低。

## 2. 第八阶段目标

- 在当前正式主链基础上，引入**前轻后重**的三层 HITL 结构：
  - `analysis` 后的条件式澄清
  - `architecture_planning` 后的默认主评审
  - `repair` 路径的兜底审核
- 让用户在“需求还模糊时”能补关键约束，在“系统骨架形成后”能确认结构方向，而不是只在最后救火。
- 保持当前 Phase 6/7 绿基线不回退，不直接切 `Send` 主链。
- 所有正式 HITL 都建立在 `checkpointer + thread_id + interrupt + Command(resume=...)` 的统一协议之上。

本轮完成后应达到的状态：

- 默认 `run_workflow(user_query)` 行为保持兼容
- 高歧义请求可在 `analysis` 后进入澄清分支
- 默认可以在 `architecture_planning` 后暂停，让用户确认结构后再进入 `subsystem_planning`
- `repair_review` 不再是唯一 HITL，而是后置兜底
- `workflow_trace` 能识别“本次停在澄清、架构评审还是 repair 审核”

---

## 3. 本轮明确不纳入

- 不把正式 `subsystem_planning` 切成 `Send` 并行版本
- 不把 reducer state keys 直接接入正式 `WorkflowState`
- 不把 `interrupt()` 直接插进 `analysis`、`architecture_planning`、`repair_agent` 这类已有复杂节点内部
- 不做完整 `internal_flow_objects` body 编译扩面
- 不在没有新稳定失败桶的前提下扩 Repair 自动修复白名单
- 不直接承诺生产级 checkpointer 后端选型；本轮只要求开发态可运行、可验证

---

## 4. 本轮实施原则

### 4.1 用户友好优先，但不能牺牲运行时边界

- 用户体验上，HITL 要尽量前移。
- 工程实现上，`interrupt()` 要放在独立 review 节点，避免恢复时重复跑非确定性逻辑。

### 4.2 条件式澄清，不做默认问答轰炸

- `analysis` 后的澄清只在高歧义场景触发。
- 不要把每条请求都强制变成多轮问答。

### 4.3 架构评审是默认主交互点

- 结构草图一旦形成，应优先给用户确认。
- 这是第八阶段最重要的正式 HITL 节点。

### 4.4 `repair_review` 是兜底，不是主入口

- 默认只有在高风险 patch、反复失败、或即将 reject 时才触发。

### 4.5 所有新能力默认可关闭

- 不传 `checkpointer`
- 不传 `thread_id`
- 不开启 review 模式

以上场景都必须保持与当前主链兼容。

---

## 5. 目标主链形态

第八阶段不要求一步到位做成最终形态，但目标方向应明确为：

```text
analysis
  -> ambiguity_router
  -> (continue -> retrieval)
  -> (need_clarification -> clarification_review -> clarification_apply -> retrieval)
  -> architecture_planning
  -> architecture_review
  -> (approve -> subsystem_planning)
  -> (feedback -> architecture_refine -> architecture_review)
  -> global_assembly
  -> coding
  -> verification
  -> repair_router
  -> (accept -> END)
  -> (repair -> repair_prepare -> repair_review? -> repair_apply -> resume)
```

说明：

- `clarification_review` 是条件节点，不是默认每次都走
- `architecture_review` 是默认主评审节点
- `repair_review` 可以是条件节点，只在需要时触发

## 12. 一句话结论

第八阶段最合理的目标，不是先把 HITL 落在 `repair` 末端，也不是把所有请求都强制改成多轮问答，而是做一套**更符合用户直觉的前置交互结构**：

```text
高歧义时先澄清
-> 架构草图出来后先确认
-> 真出问题时 repair 再兜底
```

这样既能减少前期误解带来的大返工，也能保持当前主链的工程边界和稳定基线。
