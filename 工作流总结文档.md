# 工作流总结文档

> 最后核对时间：2026-04-24
> 核对依据：`workflow.py`、`workflow_trace.py`、`utils/workflow_runtime.py`、`utils/phase3_contracts.py`、`agents/*.py`、`app/api/*.py`、`app/services/*.py`、`app/repositories/*.py`、`frontend/src/api/workflowClient.ts`、`frontend/src/types/workflow.ts`。
> 定位：给 Codex 快速建立当前工作流全局判断；节点级字段细节见 [工作流节点输入输出说明](工作流节点输入输出说明.md)，历史阶段决策见 [工作流演进记录](工作流演进记录.md)。

## 1. 先读结论

- 当前系统是 `Phase 3 分层规划主干 + Phase 8 前置澄清/架构评审 + Phase 4 deterministic repair 闭环 + Workflow API/Frontend V1 联调层` 的稳定基线。
- 正式主链已经接入 `ambiguity_router -> clarification_review -> clarification_apply`、`architecture_review -> architecture_feedback_apply`、`repair_router -> repair_agent`。
- 正式主链尚未接入 `Send` 并行派发、reducer fan-in、`repair_review`、完整 `internal_flow_objects` body 编译、生产级队列 worker、PostgreSQL checkpointer、SSE/WebSocket。
- `WorkflowState` 已不包含 `retrieval_context`、`execution_plan`、`generated_code`、`execution_result`、`validation_result`、`next_step`。
- 当前真实编译输入是 `assembled_graph_ir`，真实编译产物是 `compiled_artifact`；需要 JSON 文本时读取 `compiled_artifact["json_text"]` 或 `final_output["json_text"]`。
- Workflow API 与 Frontend 都是正式主链外的投影/编排层，不新增正式 `WorkflowState` 字段，不改变 LangGraph 拓扑。

## 2. 正式主链

```text
user_query
  -> analysis
  -> ambiguity_router
ambiguity_router
  -> clarification_review | retrieval
clarification_review
  -> clarification_review | clarification_apply | retrieval
clarification_apply
  -> retrieval | END(reject)
retrieval
  -> architecture_planning
architecture_planning
  -> architecture_review
architecture_review
  -> architecture_review | architecture_feedback_apply | subsystem_planning
architecture_feedback_apply
  -> architecture_planning(feedback/clarify) | subsystem_planning(approve) | END(reject)
subsystem_planning
  -> global_assembly
  -> coding
  -> verification
  -> repair_router
repair_router
  -> END(accept/reject) | repair_agent
repair_agent
  -> subsystem_planning | global_assembly | coding | END
```

代码常量：

- `PHASE3_NODE_ORDER = analysis -> retrieval -> architecture_planning -> subsystem_planning -> global_assembly -> coding -> verification`
- `PHASE8_REVIEW_NODE_ORDER = ambiguity_router -> clarification_review -> clarification_apply -> architecture_review -> architecture_feedback_apply`
- `PHASE4_RECURSION_LIMIT = 40`
- `repair_router` 决策：`accept / planning_repair / assembly_repair / compile_repair / reject`
- `repair_agent` 回跳：`planning -> subsystem_planning`、`assembly -> global_assembly`、`compile -> coding`

## 3. 状态与对象优先级

正式字段优先级：

```text
正式需求入口: requirement_spec > analysis_result
正式检索入口: retrieval_bundle
正式架构骨架: decomposition_result + architecture_plan
正式子系统局部 IR: subsystem_plan_map
正式全局 IR: assembled_graph_ir
正式编译产物: compiled_artifact
正式验收结果: verification_report
最终对外摘要: final_output
```

关键对象：

| 对象 | 生产者 | 主要消费者 | 判断口径 |
| --- | --- | --- | --- |
| `analysis_result` | `analysis` | `ambiguity_router`、`retrieval` | Analysis 原始结果，含 `clarification_signals` |
| `requirement_spec` | `analysis`、review apply | planner、assembly、verification | 正式需求入口，review 只允许回写需求侧 |
| `retrieval_bundle` | `retrieval` | planner、assembly、coding | 正式检索资产包 |
| `architecture_plan` / `decomposition_result` | `architecture_planning` | review、subsystem planning、assembly、verification | 系统骨架与子系统边界 |
| `subsystem_plan_map` | `subsystem_planning` | `global_assembly`、`verification` | 子系统局部 IR |
| `assembled_graph_ir` | `global_assembly` | `coding`、`verification`、compile repair | 全局 Graph IR |
| `compiled_artifact` | `coding` | `verification`、API result | 平台 JSON 编译产物 |
| `verification_report` | `verification` | `repair_router`、API diagnostics | 结构验收出口 |
| `route_decision` | `repair_router` / `repair_agent` | 条件边、trace、API diagnostics | repair 路由裁决 |
| `repair_context` / `repair_history` | `repair_agent` | repair 回跳、trace、审计 | 最近修补上下文与历史 |

预留/影子字段：

- `debug_history` 不参与主链决策。
- `retry_count` 是 `retry_counts_by_scope` 的聚合影子值；主路由按各 scope 计数判断。
- `current_step` 多数节点都会更新；`repair_router` 的 `accept` 分支保留上一步 `current_step`。

## 4. 入口与 HITL

正式 Python 入口：

```python
from workflow import run_workflow
result = run_workflow(user_query)
```

带 persistence / HITL 的入口：

```python
result = run_workflow(
    user_query,
    thread_id="demo-thread",
    checkpointer=cp,
    enable_hitl_clarification=True,
    enable_hitl_architecture_review=True,
)
```

Trace 入口：

```python
from workflow_trace import run_workflow
result = run_workflow(user_query)
```

运行规则：

- `workflow.py` 与 `workflow_trace.py` 共用 `populate_phase4_workflow(...)` 注册同一套正式拓扑。
- 未传 `checkpointer` 时，`thread_id` 只进入 metadata / trace 索引，不启用 LangGraph persistence。
- 传入 `checkpointer` 时必须提供非空 `thread_id`，否则 `build_runtime_invoke_config(...)` 会抛 `ValueError`。
- `enable_hitl_clarification` / `enable_hitl_architecture_review` 只有在 `checkpointer + thread_id` 同时存在时才会真正进入 `interrupt`。
- 不满足 HITL 条件时，review 节点仍会生成/记录 request，但走 `assumed` 旁路继续执行。
- `enable_repair_agent=False` 是默认行为；仍会经过 `verification -> repair_router`，但若验收未通过且原本需要 repair，`repair_router` 会直接输出 `reject -> END`，不会进入 `repair_agent`。

## 5. Trace 行为

- `workflow_trace.py` 包装每个节点，记录输入、输出、耗时和顶层字段变更。
- Trace 落盘：`workflow_node_io_record.json`、`workflow_node_io_record.md`、`final_state.json`。
- 成功返回结果对象时，`final_output["workflow_trace"]` 会追加 trace 文件路径。
- API runner 使用 trace 版 app 执行，并在正常、失败或中断路径尽力保存 trace。
- `thread_id` 非空时才会生成 thread / attempt 索引；存在 `review_history` 时才会生成 review 记录与 review 索引。

常见 trace 文件字段：

```text
thread_id, attempt_id, trace_dir, summary_json, summary_md, final_state_json,
review_records_json, approval_record_json, thread_index_json, attempt_index_json,
review_attempt_index_json, review_thread_index_json, review_record_jsons
```

## 6. Workflow API V1

API 是正式主链外的服务编排和状态投影层。

核心文件：

- 服务入口：`app.main:create_app()` / `app.main:app`
- 路由：`app/api/workflow_api.py`
- 编排：`app/services/workflow_service.py`
- LangGraph runner：`app/services/workflow_runner.py`
- 状态投影：`app/services/workflow_state_projection.py`
- 仓储：`app/repositories/workflow_run_repository.py`
- checkpointer：`app/services/checkpointer_factory.py`

核心接口：

```text
POST /api/workflow/runs
GET  /api/workflow/threads/{thread_id}
GET  /api/workflow/threads/{thread_id}/attempts
GET  /api/workflow/threads/{thread_id}/attempts/{attempt_id}
GET  /api/workflow/threads/{thread_id}/attempts/{attempt_id}/result
GET  /api/workflow/threads/{thread_id}/attempts/{attempt_id}/trace
GET  /api/workflow/threads/{thread_id}/attempts/{attempt_id}/state-history
POST /api/workflow/threads/{thread_id}/resume
GET  /api/workflow/health
```

API 契约：

- `thread_id` 是 LangGraph checkpoint 恢复指针。
- `attempt_id` 是 API / trace / 前端展示层的一次运行主键。
- `review_id` 是当前人工 review 卡片主键。
- 同一 `thread_id` 同一时刻只允许一个 active attempt。
- active 状态：`queued / running / interrupted`；终态：`completed / rejected / failed`。
- `POST /resume` 必须匹配当前 active interrupted attempt 的 `attempt_id` 与 `review_id`。
- 错误统一返回 `{ "error": { "code": "...", "message": "...", "details": {...} } }`。
- `POST /runs` 支持 `enable_repair_agent`；默认 false，只有显式为 true 时本次运行才启用自动修复节点。

API 运行态边界：

- 默认 checkpointer 为 SQLite，路径默认 `outputs/workflow_api/checkpoints.sqlite3`；`memory` 只用于单测或临时 demo。
- thread / attempt 元数据默认落盘到 `outputs/workflow_api/runs.json`，适合本地联调，不是生产仓储。
- 默认 worker 是本地线程执行器；生产仍需队列/独立 worker。

## 7. Workflow Frontend V1

前端是 API DTO 消费层，不读取完整 `WorkflowState`。

核心文件：

- 工程目录：`frontend/`
- API client：`frontend/src/api/workflowClient.ts`
- DTO：`frontend/src/types/workflow.ts`
- 路由：`frontend/src/app/routes.tsx`
- 功能目录：`frontend/src/features/workflow/`

页面：

- `/workflow`
- `/workflow/:threadId/:attemptId`
- `/workflow/:threadId/:attemptId/result`
- `/workflow/:threadId/:attemptId/debug`

前端契约：

- API base URL 来自 `VITE_WORKFLOW_API_BASE_URL`，默认 `http://127.0.0.1:8000`。
- 后端默认允许 `http://127.0.0.1:5173` 与 `http://localhost:5173` 跨域，可用 `WORKFLOW_CORS_ORIGINS` 调整。
- 组件层通过 `workflowClient` 调 API，不直接散落 `fetch`。
- `queued / running` 自动轮询；`interrupted / completed / rejected / failed` 停止高频轮询。
- review 提交固定携带 `attempt_id`、`review_id`、`decision`、`answers`、`feedback`、`updated_constraints`。
- 阶段轨道只能映射产品主阶段，不能依赖固定节点总数或百分比进度。

## 8. 资产与环境

- 原子模块来自 `schemas/*.json`，写入 Chroma collection `kong_modules_v1`。
- AHU 子流程模板与 system pattern 来自 `AHU程序/flows_*.json`。
- 正式 Chroma 默认落库目录是 `outputs/chroma_db`；按 `.env.example` 初始化时，`CHROMA_PERSIST_DIR` 可能覆盖为 `./chroma_db`。
- `pattern_library` 是可重建缓存，不是唯一事实源。
- 运行时版本基线以 `requirements.txt` 与 `tests/test_runtime_versions.py` 为准；升级 LangGraph/checkpointer 相关包后必须重跑 HITL/persistence 合同测试。

## 9. 当前完成与未完成

已完成：

- 正式主链接入条件式澄清、架构评审和 repair 闭环。
- `requirement_spec -> architecture_plan/decomposition_result -> subsystem_plan_map -> assembled_graph_ir -> compiled_artifact -> verification_report` 已形成稳定主契约。
- `workflow.py` / `workflow_trace.py` 支持显式 `thread_id` 与可选 `checkpointer`。
- Phase 4/5/6/7/8 关键合同测试已覆盖当前正式路径。
- Workflow API V1 已支持 REST 启动、轮询、review resume、trace 摘要、state-history 调试、统一错误 envelope。
- Workflow Frontend V1 已支持启动页、运行详情页、review 卡片、结果页、debug 页、attempt 历史、API client、fixture、测试与构建。

未完成：

- `Send` 并行子系统派发与 reducer fan-in 正式入链。
- `repair_review` 正式入链。
- 完整 `internal_flow_objects` body 编译。
- 在线 LLM 质量、真实 AHU 项目召回质量、真实项目级规划质量验收。
- 更大范围的自动修复类型扩展。
- 生产级队列 worker、PostgreSQL checkpointer、持久化数据库仓储、SSE/WebSocket。
- 前端真实浏览器端到端人工验收、鉴权/租户隔离、生产运行治理页。

## 10. 后续优先级

| 优先级 | 事项 | 判断 |
| --- | --- | --- |
| P0 | 前端 V1 真实浏览器联调验收 | 先基于 REST 轮询、review resume、trace 摘要和错误结构跑通页面闭环 |
| P0 | `repair_review` 是否正式入链 | 先确认是否需要把兜底审核前推到主链 |
| P1 | Durable execution 边界收口 | 持续守住 `analysis`、`retrieval`、`coding`、`repair_agent`、`workflow_trace` 的可恢复边界 |
| P1 | 生产级 worker / persistence | SQLite + JSON + 本地线程只是本地联调基线 |
| P1 | `Send` 迁移条件 | 当前仍停留在 POC / 合同层，未满足条件前不切正式主链 |
| P2 | Repair 扩面 | 只在出现新的稳定失败桶后扩展自动修复规则 |
