# 工作流节点输入输出说明

> 最后核对时间：2026-04-24
> 核对依据：`workflow.py`、`workflow_trace.py`、`utils/phase3_contracts.py`、`utils/workflow_runtime.py`、`agents/*.py`、`app/services/workflow_state_projection.py`、`app/api/models.py`、`frontend/src/types/workflow.ts`。
> 定位：节点契约速查。全局状态、API/前端定位与优先级见 [工作流总结文档](工作流总结文档.md)。

## 1. 阅读规则

- 本文只描述当前正式代码路径，不描述历史设计稿。
- `workflow.py` 与 `workflow_trace.py` 共用同一套正式拓扑。
- `WorkflowState` 的正式字段以 `workflow.WorkflowState` 与 `build_initial_state(...)` 为准。
- API 与前端只消费投影 DTO，不是节点输入输出的事实源。
- 旧字段 `retrieval_context / execution_plan / generated_code / execution_result / validation_result / next_step` 已退出正式 `WorkflowState`。

## 2. 主链拓扑

```text
analysis
  -> ambiguity_router
ambiguity_router
  -> clarification_review | retrieval
clarification_review
  -> clarification_review | clarification_apply | retrieval
clarification_apply
  -> retrieval | END
retrieval
  -> architecture_planning
architecture_planning
  -> architecture_review
architecture_review
  -> architecture_review | architecture_feedback_apply | subsystem_planning
architecture_feedback_apply
  -> architecture_planning | subsystem_planning | END
subsystem_planning
  -> global_assembly
  -> coding
  -> verification
  -> repair_router
repair_router
  -> END | repair_agent
repair_agent
  -> subsystem_planning | global_assembly | coding | END
```

| `analysis_result` | `analysis`、`ambiguity_router`、`clarification_apply` | `ambiguity_router`、`retrieval` | Analysis 原始结果，含 `clarification_signals` |
| `requirement_spec` | `analysis`、`clarification_apply`、`architecture_feedback_apply` | planner、assembly、verification | 正式需求入口 |
| `retrieval_bundle` | `retrieval` | planner、assembly、coding | 正式检索资产包 |

| `subsystem_plan_map` | `subsystem_planning`、assembly repair | assembly、verification、repair | 子系统局部 IR |

| `retry_counts_by_scope` | 初始状态、repair 节点 | `repair_router`、`repair_agent` | scope 已消耗计数 |
| `retry_count` | 初始状态、repair 节点 | trace | `retry_counts_by_scope` 聚合影子值 |
| `hitl_stage` | router / review 节点 | review 节点、API projection | 当前 review 阶段 |
| `review_request` | review 节点 | API/前端、review 条件边 | 冻结后的 review 请求 |
| `review_response` | review 节点 / resume | apply 节点、review 条件边 | 人工或 assumed 回复 |
| `review_history` | review / apply 节点 | trace、review artifacts | review 生命周期记录 |
| `review_enabled` | review 节点 | review 条件边 | 当前是否允许真正 `interrupt` |
| `review_required` | `ambiguity_router`、`architecture_review` | review 条件边 | 是否需要 review |
| `review_status` | router / review / apply | review 条件边、API projection | 常规值见第 5 节 |
| `review_id` | review 节点 | API resume 校验 | 当前 review 稳定 ID |
| `clarification_round` | `clarification_apply` | trace / 审计 | 澄清回写轮次 |
| `architecture_feedback_patch` | `architecture_feedback_apply` | architecture feedback 条件边 | 架构反馈补丁摘要 |
| `enable_hitl_clarification` | 入口 | `clarification_review` | clarification HITL 开关 |
| `enable_hitl_architecture_review` | 入口 | `architecture_review` | architecture review HITL 开关 |
| `enable_repair_agent` | 入口 | `repair_router` | 自动修复节点开关；默认 false，只有 true 时 repairable issue 才进入 `repair_agent` |
| `current_step` | 多数节点 | trace、API projection | 当前步骤标签 |
| `debug_history` | 初始状态 / 测试桩 | 无正式决策消费者 | 历史预留 |

## 4. 节点契约

### `analysis`

- 输入：`user_query`
- 输出：`analysis_result`、`requirement_spec`、`current_step=analysis_completed`
- 下游：`ambiguity_router`、`retrieval`
- 不变量：`requirement_spec` 是正式规划入口；`clarification_signals` 是前置澄清分支的输入。

### `ambiguity_router`

- 输入：`analysis_result`、`requirement_spec`
- 输出：`review_required`、`hitl_stage`、`review_status`、`current_step=ambiguity_routed`；必要时补写 `analysis_result.clarification_signals`
- 路由：`review_required=True -> clarification_review`，否则 `retrieval`
- 不变量：不修改检索、规划、装配、编译产物。

### `clarification_review`

- 输入：`analysis_result`、`requirement_spec`、`review_required`、`enable_hitl_clarification`、review 状态字段
- 输出：`review_request`、`review_response`、`review_history`、`review_enabled`、`review_status`、`review_id`、`hitl_stage`、`current_step`
- 路由：
  - `review_required=False`：跳过到 `retrieval`
  - `review_enabled=True` 且 `review_status=pending`：`interrupt(request)` 后回到本节点
  - 已回答或有 decision：进入 `clarification_apply`
  - 不启用 HITL：走 `assumed` 旁路到 `retrieval`
- 不变量：不修改 `retrieval_bundle / architecture_plan / subsystem_plan_map`。

### `clarification_apply`

- 输入：`review_response`、`analysis_result`、`requirement_spec`、`clarification_round`
- 输出：更新后的 `analysis_result`、`requirement_spec`、`clarification_round`、`review_history`、`review_status`、`hitl_stage=none`、`current_step=clarification_applied`
- 路由：`decision=reject -> END`，否则 `retrieval`
- 不变量：只回写需求侧输入；`reject` 时写 `final_output["review_abort"]`。

### `retrieval`

- 输入：`user_query`、`analysis_result`
- 输出：`retrieval_bundle`、`current_step=retrieval_completed`
- 下游：`architecture_planning`
- 不变量：正式节点只回填 `retrieval_bundle`；仓库级 `RetrievalAgent.retrieve()` compat API 已删除。

### `architecture_planning`

- 输入：`requirement_spec`、`retrieval_bundle`
- 输出：`decomposition_result`、`architecture_plan`、`current_step=architecture_planned`
- 下游：`architecture_review`
- 不变量：规则优先生成系统骨架、页签、子系统槽位、共享信号约束与规划顺序。

### `architecture_review`

- 输入：`architecture_plan`、`decomposition_result`、`enable_hitl_architecture_review`、review 状态字段
- 输出：`review_required`、`review_request`、`review_response`、`review_history`、`review_enabled`、`review_status`、`review_id`、`hitl_stage`、`current_step`
- 路由：
  - 架构对象为空：`not_required -> subsystem_planning`
  - `review_enabled=True` 且 `review_status=pending`：`interrupt(request)` 后回到本节点
  - 已回答或有 decision：进入 `architecture_feedback_apply`
  - 不启用 HITL：走 `assumed` 旁路到 `subsystem_planning`
- 不变量：只展示骨架摘要并收集反馈，不直接修改结构产物。

### `architecture_feedback_apply`

- 输入：`review_response`、`review_request`、`requirement_spec`
- 输出：按 decision 更新 `requirement_spec`、`architecture_feedback_patch`、`review_history`、`review_status`、`hitl_stage`、`current_step`，必要时写 `final_output["review_abort"]`
- 路由：
  - `approve` 或空 decision：`subsystem_planning`
  - `feedback / clarify`：回写需求侧后回到 `architecture_planning`
  - `reject`：`END`
- 不变量：`approve` 不生成 patch；`feedback/clarify` 只回写需求侧。

### `subsystem_planning`

- 输入：`requirement_spec`、`decomposition_result`、`architecture_plan`、`retrieval_bundle`
- 输出：`subsystem_plan_map`、`current_step=subsystem_planned`
- 下游：`global_assembly`
- 不变量：当前按 `planning_order` 串行执行，不使用 `Send`；只消费显式 `interface_bindings`，不再从 compat-only `imports / exports` 自动合成绑定。

### `global_assembly`

- 输入：`requirement_spec`、`architecture_plan`、`subsystem_plan_map`、`retrieval_bundle`
- 输出：`assembled_graph_ir`、`current_step=global_assembly_completed`
- 下游：`coding`
- 不变量：正式输入是 bundle-only；不回填顶层 `execution_plan`，`assembled_graph_ir` 也不携带 `source_execution_plan`。

### `coding`

- 输入：`assembled_graph_ir`、`retrieval_bundle`
- 输出：`compiled_artifact`、`current_step=coding_completed`
- 下游：`verification`
- 不变量：正式产物是 `compiled_artifact`；仓库级 `compile_graph(...) / generate_json(...)` compat API 已删除；不回填顶层 `generated_code`。

### `verification`

- 输入：`assembled_graph_ir`、`compiled_artifact`、`requirement_spec`、`architecture_plan`、`subsystem_plan_map`
- 输出：`verification_report`、`final_output`、`current_step=verification_completed`
- 下游：`repair_router`
- 不变量：同时检查 planning / assembly / compile 三层；`repair_payload` 是 repair 正式输入。

### `repair_router`

- 输入：`verification_report`、`retry_budget`、`retry_counts_by_scope`
- 输出：规范化后的 retry 字段、`route_decision`；非 `accept` 时写 `current_step=repair_router_completed`
- 路由：
  - `verification_report.status=passed`：`accept -> END`
  - `repair_scope=planning` 且预算未耗尽：`planning_repair -> repair_agent`
  - `repair_scope=assembly` 且预算未耗尽：`assembly_repair -> repair_agent`
  - `repair_scope=compile` 且预算未耗尽：`compile_repair -> repair_agent`
  - `enable_repair_agent=False` 且原本需要 repair：`reject -> END`
  - scope 不支持或预算耗尽：`reject -> END`
- 不变量：主预算按 scope 计数，不按 `retry_count` 决策。

### `repair_agent`

- 输入：`route_decision`、`verification_report`、retry 字段、以及 repair scope 对应的上游主对象
- 输出：`repair_context`、`repair_history`、更新后的 `route_decision`、retry 字段、被修补主对象、`current_step`
- 回跳：
  - `planning`：修补 `architecture_plan / decomposition_result`，回到 `subsystem_planning`
  - `assembly`：修补 `subsystem_plan_map`，回到 `global_assembly`
  - `compile`：修补 `assembled_graph_ir`，回到 `coding`
  - 无可修补项或不支持规则：`reject -> END`
- 不变量：只修补下一跳真正会消费的上游对象；repair 后显式失效对应下游派生产物，避免旧结果覆盖 patch。

## 5. Review / HITL 契约

合法 review stage：

```text
none, clarification_review, architecture_review, repair_review
```

当前正式主链只使用：

```text
none, clarification_review, architecture_review
```

合法 decision：

```text
approve, feedback, clarify, reject
```

合法 status：

```text
none, not_required, pending, interrupted, assumed, answered, applied, rejected
```

注意：

- `interrupted` 主要由 trace/API 状态归纳或外部投影使用，review 节点常规回写多为 `pending / assumed / answered / applied / rejected / not_required`。
- `review_request` 必须包含 `review_id / stage / question / options / context_summary / created_at`。
- `review_response` 必须包含 `decision / answers / feedback / updated_constraints / review_id`。
- review apply 节点只能回写需求侧允许字段，不能直接改检索、规划、装配、编译、验收产物。
- `enable_hitl_*` 开关只有在 `checkpointer + thread_id` 同时存在时才会由入口置为 true。

## 7. API 投影 DTO 边界

API 不返回完整 `WorkflowState`，只返回投影。

| DTO | 来源 | 关键字段 |
| --- | --- | --- |
| `ThreadOverview` | `build_thread_overview` | `thread_id`、`title`、`latest_attempt_id`、`latest_status`、`latest_current_step`、`latest_review` |
| `AttemptListResponse` | `build_attempt_list_item` | `attempt_id`、`status`、`current_step`、`started_at`、`finished_at`、`verification_status`、`final_route_decision` |
| `AttemptDetail` | `build_attempt_detail` | `status`、`current_step`、`user_query`、`review`、`progress`、`diagnostics`、`trace_files`、`subtasks` |
| `AttemptResult` | `build_attempt_result` | `result.json_text`、`result.compile_report`、`result.verification_report`、`trace_files` |
| `TraceProjection` | `build_trace_projection` | `summary`、`review`、`diagnostics`、`trace_files` |
| `StateHistoryProjection` | `build_state_history_projection` | `created_at`、`next`、`metadata`、瘦身 state |
| `WorkflowHealth` | `WorkflowService.health` | LLM/embedding provider、checkpointer、worker、trace、Chroma readiness |

attempt 状态推断：

- `__interrupt__` 或 `review_status=pending` 且有 review stage：`interrupted`
- `route_decision.decision=reject` 或 `final_output.review_abort`：`rejected`
- `route_decision.decision=accept` 或 `verification_report.status=passed`：`completed`
- 否则使用 repository fallback 状态

前端不得依赖：

- 完整 `WorkflowState`
- 完整节点 IO trace
- trace 文件物理路径格式
- 固定节点数量或百分比进度
- `subtasks` 当前为空这个实现细节

## 8. 已移除 / 不应复活的兼容口径

- 正式 `WorkflowState` 不包含 `retrieval_context`、`execution_plan`、`generated_code`、`execution_result`、`validation_result`、`next_step`。
- `assembled_graph_ir.source_execution_plan` 已退出正式 IR。
- `RetrievalAgent.retrieve()` 仓库级 compat API 已删除；正式调用使用 `retrieve_bundle(...)` / `__call__`。
- `CodingAgent.compile_graph(...)`、`CodingAgent.generate_json(...)` 仓库级 compat API 已删除；正式调用使用 `compile_graph_from_bundle(...)` / `__call__`。
- `utils.retrieval_bundle_utils` 与 `utils.context_formatter` 当前只保留 formal bundle-only helper。
- `SubsystemPlanner` 不再从 compat-only `imports / exports` 自动合成 signal bindings。
- `Send` 只在 POC/合同测试层出现，正式 `workflow.py` / `workflow_trace.py` 不应出现 `Send(`。

## 9. 一句话主线

```text
自然语言需求
-> analysis_result / requirement_spec
-> 条件式 clarification review
-> retrieval_bundle
-> architecture_plan / decomposition_result
-> architecture review
-> subsystem_plan_map
-> assembled_graph_ir
-> compiled_artifact
-> verification_report
-> route_decision
-> 必要时 deterministic repair 并回跳
```
