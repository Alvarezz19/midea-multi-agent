# 工作流节点输入输出说明

> 基于当前代码实现整理，核对范围以 `workflow.py`、`workflow_trace.py`、`agents/*.py`、`utils/phase3_*.py`、`utils/signal_semantics.py`、`utils/retrieval_bundle_utils.py`、`utils/graph_ir.py`、`scripts/run_phase5_query_suite.py`、`scripts/run_phase6_real_query_suite.py`、`scripts/run_phase6_retrieval_eval.py`、`tests/test_phase3_*.py`、`tests/test_phase4_*.py`、`tests/test_phase5_workflow_query_suite.py`、`tests/test_phase6_*.py` 为主。  
> 若与现有设计稿或旧文档不一致，以代码为准。

## 1. 当前正式主链

当前 `workflow.py` 中注册的正式 LangGraph 主链保持 Phase 4 Repair 闭环拓扑；Phase 5 与 Phase 6 主要扩展共享信号契约、结构化 repair payload、真实 query suite、检索评估、规划硬化和 trace 摘要，不新增正式主链节点：

```text
analysis
  -> retrieval
  -> architecture_planning
  -> subsystem_planning
  -> global_assembly
  -> coding
  -> verification
  -> repair_router
  -> (accept -> END) / (repair_agent -> subsystem_planning | global_assembly | coding)
```

对应常量在 `workflow.py` 中是：

```python
PHASE3_NODE_ORDER = [
    "analysis",
    "retrieval",
    "architecture_planning",
    "subsystem_planning",
    "global_assembly",
    "coding",
    "verification",
]
```

Phase 4/5 额外还有：

```python
REPAIR_ROUTER_NODE = "repair_router"
REPAIR_AGENT_NODE = "repair_agent"
PHASE4_RECURSION_LIMIT = 40
```

这条主链当前有 repair 条件分支；Phase 5 与 Phase 6 都没有引入并行 `Send`、reducer fan-in，也没有把人工澄清 / HITL 正式节点接入主链。

## 2. 入口与初始状态

### 2.1 正式入口

- `workflow.create_workflow()`：创建图，但不运行
- `workflow.run_workflow(user_query: str)`：构建图、编译图、构造初始状态并直接 `invoke`
- `workflow_trace.run_workflow(user_query: str)`：与正式主链相同，但额外记录节点 IO 和 trace 文件
- `scripts/run_phase5_query_suite.py`：使用固定 fake analysis payload、固定内存检索资产和 workflow 级 deterministic stubs 跑 6 类 Phase 5 验收 case，并输出 JSON/Markdown 摘要与 trace 路径
- `scripts/run_phase6_real_query_suite.py`：使用唯一正式 case 源 `AHU程序/phase6_real_query_cases.json` 跑真实 `workflow_trace.run_workflow(...)`，输出 suite 级摘要、failure bucket、trace 路径与 retained 信息
- `scripts/run_phase6_retrieval_eval.py`：复用同一份 case 源，只跑检索层，输出 `retrieval_diagnosis`、golden 命中率、asset gap 根因与 `ready_for_c` 裁决

两条入口都会在 `invoke` 配置里带上：

```python
{"recursion_limit": 40}
```

补充说明：

- 当前正式主链 `compile()` 仍未传入 `checkpointer`
- 当前正式 `invoke_config` 仍未传入 `configurable.thread_id`
- `thread_id / interrupt / persistence` 当前只在 `scripts/poc_phase4_hitl.py` 的独立 POC 中验证

## 3. 顶层状态字段说明

### 3.1 正式字段

这些字段是真正被当前正式主链使用的主字段：

| 字段 | 生产节点 | 主要消费者 | 说明 |
| --- | --- | --- | --- |
| `user_query` | 入口 | `analysis`、`retrieval` | 用户原始需求 |
| `analysis_result` | `analysis` | `retrieval`，兼容观察 | Analysis 原始分析结果 |
| `requirement_spec` | `analysis` | `architecture_planning`、`subsystem_planning`、`global_assembly`、`verification` | Phase 3 正式结构化需求 |
| `retrieval_bundle` | `retrieval` | `architecture_planning`、`subsystem_planning`、`global_assembly`、`coding` | 正式检索主输出 |
| `decomposition_result` | `architecture_planning` | `subsystem_planning` | 页签/子系统拆分结果 |
| `architecture_plan` | `architecture_planning` | `subsystem_planning`、`global_assembly`、`verification` | 系统级骨架 |
| `subsystem_plan_map` | `subsystem_planning` | `global_assembly`、`verification` | 各子系统局部 IR |
| `assembled_graph_ir` | `global_assembly` | `coding`、`verification` | 当前真实编译输入 |
| `compiled_artifact` | `coding` | `verification` | 当前真实编译产物 |
| `verification_report` | `verification` | `repair_router`、输出阶段 | 当前真实验收结果 |
| `repair_context` | `repair_agent` | `repair_agent` 路由回跳逻辑、trace | 最近一次 repair 的上下文 |
| `repair_history` | `repair_agent` | `workflow_trace`、调试/审计 | 每次 repair / reject 的结构化历史 |
| `route_decision` | `repair_router` / `repair_agent` | `repair_agent`、终止分支、trace | 当前稳定路由决定 |
| `retry_budget` | 初始状态 | `repair_router`、`repair_agent` | 各 scope 预算上限 |
| `retry_counts_by_scope` | `repair_agent` | `repair_router`、trace | 各 scope 已消耗计数 |
| `final_output` | `verification` | 外部调用方 | 最终摘要输出 |

### 3.2 兼容字段

这些字段仍会被回填，但已经不是主链核心契约：

| 字段 | 来源 | 当前定位 |
| --- | --- | --- |
| `retrieval_context` | `retrieval_bundle` 派生 | 给旧节点/旧逻辑保留的 compat 视图 |
| `execution_plan` | `GlobalAssembler` 基于 Phase 3 结果投影 | compat 平面计划，不再是正式编译输入 |
| `generated_code` | `compiled_artifact["json_text"]` | compat 字段，不是真实主产物 |

### 3.3 预留/历史字段

`execution_result`、`validation_result`、`debug_history`、`next_step` 目前不参与正式主链决策；`retry_count` 是聚合统计值，等于 `sum(retry_counts_by_scope.values())`；`current_step` 会被节点更新。

## 4. 节点之间的信息传递主线

```text
user_query
  -> analysis_result
  -> requirement_spec
  -> retrieval_bundle
  -> decomposition_result + architecture_plan
  -> subsystem_plan_map
  -> execution_plan(compat) + assembled_graph_ir
  -> compiled_artifact + generated_code(compat)
  -> verification_report + final_output
  -> route_decision
  -> repair_context + repair_history
```

更具体地说：

1. `analysis` 把自然语言变成 `analysis_result`，再投影出 `requirement_spec`
2. `retrieval` 读取 `user_query + analysis_result`（重点使用 `retrieval_plan` 与 `scenario_analysis`），检索出 `retrieval_bundle`
3. `architecture_planning` 用 `requirement_spec + retrieval_bundle` 生成系统级骨架
4. `subsystem_planning` 用系统骨架逐个生成子系统局部 IR
5. `global_assembly` 把局部 IR 拼成全局 `assembled_graph_ir`，同时回填 compat `execution_plan`
6. `coding` 只消费 `assembled_graph_ir` 和检索文档，确定性编译出 JSON
7. `verification` 同时看原生规划产物、全局 IR 和编译结果，输出验收结论
8. `repair_router` 根据 `verification_report + retry_counts_by_scope` 决定 `accept / *_repair / reject`
9. `repair_agent` 只修补下一跳真正会消费的上游主对象，再回到 `subsystem_planning / global_assembly / coding`

## 5. 节点详解

## 5.1 `analysis`

### 输入

从顶层状态读取：

```python
{
    "user_query": str
}
```

### 内部工作方式

`AnalysisAgent.__call__()` 的真实流程是：

1. 读取 `state["user_query"]`
2. 调用 `analyze(query)`
3. `analyze()` 优先尝试 LLM structured output
4. structured output 失败时，回退到普通 LLM + JSON 解析
5. 再失败时，使用本地兜底 `_fallback_result`
6. 对结果做归一化：
   - `retrieval_plan`
   - `scenario_analysis`
7. 调用 `build_requirement_spec(analysis_result)`，把分析结果投影成正式 `requirement_spec`

`build_requirement_spec()` 不是简单复制字段，而是规则投影：

- 从 `scenario_analysis` 推断 `system_type`
- 根据关键词识别子系统，如 `supply_fan_ctrl`、`chw_valve_ctrl`、`heater_ctrl`、`dx_ctrl`
- 推断 `global_modes`
- 推断 `required_pages`
- 把输入/输出/软件点/报警点归并到 `signals`
- 信息不足时写 `warnings` 和 `ambiguities`

## 5.2 `retrieval`

### 输入

从顶层状态读取：

```python
{
    "user_query": str,
    "analysis_result": dict
}
```

其中真实关键输入是：

- `user_query`
- `analysis_result["retrieval_plan"]`
- `analysis_result["scenario_analysis"]`

### 内部工作方式

`RetrievalAgent.__call__()` 会：

1. 用 `user_query + analysis_result` 调用 `retrieve_bundle()`
2. `retrieve_bundle()` 内部分三路组织检索结果：
   - `atomic_modules`
   - `subflow_templates`
   - `system_patterns`
3. 原子模块检索走 `self.collection`，可使用多查询变体批量检索
4. 子流程模板和系统骨架走各自 collection
5. 如果 `system_patterns` 有命中，取首个 pattern 的 `style_guides` 写入 bundle
6. 再调用 `build_legacy_retrieval_context(bundle)` 生成 compat `retrieval_context`

## 5.3 `architecture_planning`

### 输入

从顶层状态读取：

```python
{
    "requirement_spec": dict,
    "retrieval_bundle": dict
}
```

### 内部工作方式

`ArchitecturePlanner.plan()` 是规则优先的系统级规划器，主要做 5 件事：

1. 从 `retrieval_bundle.system_patterns` 中评分选择最合适的系统骨架
   - 看 `system_type`
   - 看页面键命中情况
   - 看子系统类型和 pattern 页面是否匹配
   - 若 `selected_case_pattern_id` 命中会额外加分
2. 构造页面列表 `pages`
   - 先用 pattern 的 `required_pages`
   - 再按条件补 `optional_pages`
   - 再补 `requirement_spec.required_pages`
3. 对每个子系统生成：
   - `subsystem_descriptors`
   - `subsystem_slots`
   - `template_needs`
4. 先把模板接口和显式 imports / exports 统一投影成 `interface_bindings`
5. 只把 `binding_kind == "shared_signal"` 的接口写入 `shared_signal_registry`
6. 生成命名策略、布局策略和 pattern 绑定说明

如果 `requirement_spec.subsystems` 为空，会退化成一个 `generic_control` 子系统。

### `interface_bindings` 与 `shared_signal_registry` 的真实作用

`interface_bindings` 是 Phase 4 整改后新增的统一接口语义层，先回答“这个接口到底是 shared 还是 external”。典型单项格式：

```python
{
    "signal_name": str,
    "signal_key": str,
    "canonical_signal_key": str,
    "direction": "input" | "output",
    "binding_kind": "shared_signal" | "external_input" | "external_parameter" | "external_command" | "subsystem_output",
    "allowed_external": bool,
    "owner_subsystem_id": str,
    "port_index": int,
    "evidence": list[str],
    "confidence": float,
}
```

`shared_signal_registry` 只收 `binding_kind == "shared_signal"` 的接口，它才是后续跨子系统连线的核心约束表。典型单项格式：

```python
{
    "signal_name": str,
    "signal_key": str,
    "semantic_role": "global_mode" | "shared_input" | "shared_output",
    "owner_subsystem_id": str,
    "allowed_external": bool,
    "required_exporter_count": int,
    "consumers": list[str],
    "exporter_candidates": list[str],
    "source_reason": str,
}
```

后续：

- `SubsystemPlanner` 先消费 `interface_bindings`，再参考它投影 `imported_signals / exported_signals`
- `GlobalAssembler` 只对 `shared_signal_registry` 中的真实共享信号做 exporter / owner / ambiguity 判定
- `external_input / external_parameter / external_command` 不会再进入 shared-signal owner 推断链

## 5.4 `subsystem_planning`

### 输入

从顶层状态读取：

```python
{
    "requirement_spec": dict,
    "decomposition_result": dict,
    "architecture_plan": dict,
    "retrieval_bundle": dict
}
```

### 内部工作方式

`SubsystemPlanner.plan()` 的真实执行方式是串行的，不并行：

1. 基于 `retrieval_bundle` 建立 `doc_map`
2. 从 `decomposition_result` 取 `planning_order`
3. 按顺序逐个处理子系统
4. 对每个子系统：
   - 先从 `descriptor.interface_bindings` 建立统一接口语义
   - 再从 `architecture_plan.subsystem_slots.preferred_template_ids` 里找可用模板
   - 找到模板则走 `_plan_template_reuse()`
   - 找不到则走 `_plan_atomic_fallback()`
   - 若找到的模板与接口投影明显不匹配，也会尽早改走 `_plan_atomic_fallback()`

#### 模板复用路径

特点：

- 只生成 1 个主节点
- `implementation_mode = "reuse_template"`
- 节点 `module_type` 和 `template_id` 都是模板 ID
- `template_interface_bindings` 保留完整接口语义
- `imported_signals` / `exported_signals` 从 `template_interface_bindings` 裁剪，并保留 `binding_kind / allowed_external / canonical_signal_key`
- 如果模板接口覆盖明显不足，不再继续带着坏模板向后传，而是写清 `degrade_reason` 并提前降级到 `atomic_assembly`

#### 原子装配退化路径

特点：

- `implementation_mode = "atomic_assembly"`
- 先选一个原子模块作为主节点
- 若主节点有输入端，则再选零输入模块作为本地占位源
- 用局部边把占位源接到主节点
- 找不到合适占位源时，写 `unresolved_items`

### 内部工作方式

`GlobalAssembler.__call__()` 先做一件 compat 事情，再做正式装配：

1. 调用 `build_legacy_execution_plan(...)` 回填 `execution_plan`
2. 调用 `assemble(...)` 生成 `assembled_graph_ir`

`assemble(...)` 主要做以下工作：

1. 根据 `architecture_plan.pages` 建 `pages`
2. 遍历每个子系统的 `node_instances`，提升成全局节点实例
3. 根据模块文档识别子流程模板，补 `subflow_definitions`
4. 把子系统内部局部边抬升成全局 `edges`
5. 汇总所有 `imported_signals` / `exported_signals`
6. 只对 `binding_kind == "shared_signal"` 的 imported signal 做跨子系统匹配连线：
   - 若有唯一真实导出方，直接连线

   - 若没有真实导出方，且不允许外部输入，也会注入 placeholder source，但同时写入 `synthetic_shared_signal_source`
7. 对 `external_input / external_parameter / external_command`，直接注入 external placeholder，不走 shared-signal owner/exporter 判定，也不会生成 `synthetic_shared_signal_source`
8. 把子系统层 `unresolved_items` 合并到全局

## 5.7 `verification`

### 输入

从顶层状态读取：

```python
{
    "assembled_graph_ir": dict,
    "compiled_artifact": dict,
    "requirement_spec": dict,
    "architecture_plan": dict,
    "subsystem_plan_map": dict,
}
```

### 内部工作方式

`VerifierAgent.verify()` 会同时做三层检查：

#### 1. planning 层

- compat `source_execution_plan` 是否失败/为空
- `architecture_plan.subsystem_slots` 是否为空
- `subsystem_plan_map` 是否为空
- 是否覆盖了所有预期子系统
- 是否有空的子系统节点集
- 原生 planning 级 `unresolved_items` 是否存在
- 对 planning 级 `unresolved_items` 生成结构化 `repair_payload`

#### 2. assembly 层

- `assembled_graph_ir.node_instances` 是否为空
- 节点是否属于合法页面/子流程
- 边的两端是否存在
- 端口是否越界
- 必需输入端口是否都有连线
- `unresolved_items` 中 `severity=error` 的项目会转成正式 issue

#### 3. compile 层

- `compiled_artifact.json_text` 是否可解析
- 顶层是否是 list
- `flow_objects` 是否结构合法
- `z` 指向的父对象是否存在
- `wires` 结构是否合法
- `wire` 目标节点和端口是否合法
- `compile_report` 统计是否和实际对象数大致一致
- 对 `compile.wire.port.range` 生成结构化 `repair_payload`

写回状态：

```python
{
    "verification_report": {
        "status": "passed" | "retryable_error",
        "repair_scope": "none" | "planning" | "assembly" | "compile",
        "issue_summary": str,
        "issues": list[{
            "issue_id": str,
            "severity": str,
            "scope": str,
            "target_id": str,
            "rule_id": str,
            "message": str,
            "suggested_fix": str,
            "repair_payload": dict,
        }],
        "warnings": list[str],
        "metrics": {
            "missing_required_inputs": int,
            "isolated_nodes": int,
            "invalid_port_refs": int,
        },
    },
    "final_output": {
        "json_text": compiled_artifact["json_text"],
        "compile_report": compiled_artifact["compile_report"],
        "verification_report": verification_report,
    },
    "current_step": "verification_completed"
}
```

### 状态判定规则

- 只要存在 `severity=error` 的 issue，`status = "retryable_error"`
- 否则 `status = "passed"`
- `repair_scope` 会按优先级选：
  - `planning`
  - `assembly`
  - `compile`

注意：当前 verifier 只负责验收，不负责自动修复；自动修复发生在后续 `repair_router -> repair_agent`。

其中 `repair_payload` 的真实用途是把修补所需上下文显式传给 `RepairAgent`。当前已覆盖三类：

- planning unresolved item：
  - `signal_name`
  - `canonical_signal_key`
  - `binding_kind`
  - `allowed_external`
  - `candidate_exporters`
  - `consumer_subsystem_ids`
  - `owner_subsystem_id`
  - `resolution_status`
- assembly unresolved item：
  - `subsystem_id`
  - `edge_ids`
  - `from_node`
  - `to_node`
  - `reason`
- `compile.wire.port.range`：
  - `source_real_id`
  - `target_real_id`
  - `invalid_target_port`
  - `target_input_count`

## 5.8 `repair_router`

### 输入

从顶层状态读取：

```python
{
    "verification_report": dict,
    "retry_budget": {"planning": int, "assembly": int, "compile": int},
    "retry_counts_by_scope": {"planning": int, "assembly": int, "compile": int},
}
```

### 内部工作方式

`RepairRouter.route()` 是规则优先节点，逻辑固定：

1. 若 `verification_report.status == "passed"`，返回 `accept`
2. 若 `repair_scope` 不在 `planning / assembly / compile`，返回 `reject`
3. 若 `retry_counts_by_scope[repair_scope] >= retry_budget[repair_scope]`，返回 `reject`
4. 其他情况按 `repair_scope` 返回：
   - `planning_repair`
   - `assembly_repair`
   - `compile_repair`

它不会修改规划对象或编译对象，只负责产出稳定 `route_decision`。

### 输出

写回状态：

```python
{
    "route_decision": {
        "decision": "accept" | "planning_repair" | "assembly_repair" | "compile_repair" | "reject",
        "repair_scope": str,
        "next_node": "END" | "repair_agent",
        "reason": str,
        "issue_ids": list[str],
        "retry_exhausted": bool,
        "retry_count_for_scope": int,
        "retry_budget_for_scope": int,
    },
    "retry_budget": dict[str, int],
    "retry_counts_by_scope": dict[str, int],
    "retry_count": int,
    "current_step": "repair_router_completed",   # 仅 decision != accept 时写入
}
```

### 路由结果的真实去向

- `accept` -> `END`
- `planning_repair` / `assembly_repair` / `compile_repair` -> `repair_agent`
- `reject` -> `END`

## 5.9 `repair_agent`

### 输入

从顶层状态读取：

```python
{
    "route_decision": dict,
    "verification_report": dict,
    "retry_budget": dict,
    "retry_counts_by_scope": dict,
    "architecture_plan": dict,
    "decomposition_result": dict,
    "subsystem_plan_map": dict,
    "assembled_graph_ir": dict,
    "compiled_artifact": dict,
}
```

### 内部工作方式

`RepairAgent.__call__()` 是 deterministic patch 优先节点。它先递增当前 scope 的计数，再筛选本轮 `issue_ids` 对应的问题，最后按 scope 修补真正会被下一跳消费的上游对象。

当前 V1 支持：

- `planning`
  - `ir.unresolved.ambiguous_shared_signal`
  - `ir.unresolved.synthetic_shared_signal_source`
  - `ir.unresolved.shared_signal_owner_mismatch`
  - 修补对象：`architecture_plan`、`decomposition_result`
  - 回跳：`subsystem_planning`

- `assembly`
  - `ir.unresolved.missing_local_edge_endpoint`
  - 修补对象：`subsystem_plan_map`
  - 回跳：`global_assembly`

- `compile`
  - `compile.wire.port.range`
  - 修补对象：`assembled_graph_ir`
  - 回跳：`coding`

不支持的问题不会硬修，而是直接写 `reject`。

planning scope 的真实策略已经调整为：

- 若 `repair_payload` 表明该信号本质是 `external_input / external_parameter / external_command`，则直接把 `shared_signal` 重分类为 external
- 否则只在存在唯一导出方时回填 `owner_subsystem_id`
- 对 `ambiguous_shared_signal`，若候选导出方按当前状态过滤后只剩一个，则收敛 owner；否则稳定 reject，`route_decision.reason = ambiguous_shared_signal_unresolved`

assembly scope 的真实策略是优先消费 `repair_payload.edge_ids / from_node / to_node` 定位局部边，再删除非法边并记录降级 warning。

compile scope 的真实策略是依赖结构化 `repair_payload` 中的 `source_real_id / target_real_id / invalid_target_port / target_input_count` 定位和修正 Graph IR 边，不再依赖 verifier message 的 regex fallback 作为修补路径。

## 6. 当前几个关键对象之间的关系

## 6.1 `requirement_spec` -> `architecture_plan`

这一层解决的是“系统骨架长什么样”，不是节点级连线。输出包括：

- 页面有哪些
- 子系统有哪些
- 每个子系统优先复用模板还是原子装配
- 共享信号应该由谁导出、谁消费

## 6.2 `architecture_plan` -> `subsystem_plan_map`

这一层解决的是“每个子系统自己内部怎么落图”。输出包括：

- 局部节点实例
- 局部边
- 对外导入接口
- 对外导出接口

## 6.3 `subsystem_plan_map` -> `assembled_graph_ir`

这一层解决的是“把多个子系统拼成整个项目图”。输出包括：

- 全局节点实例 ID
- 全局边
- 页面归属
- 子流程定义
- 跨子系统共享信号连线
- 未解决项

## 6.4 `assembled_graph_ir` -> `compiled_artifact`

这一层解决的是“把强结构 IR 编译成平台 JSON”。输出包括：

- 平台 `flow_objects`

- 编译映射表
- 编译报告

## 7. 兼容字段与正式字段的真实优先级

当前优先级可以直接理解为：

```text
正式需求入口: requirement_spec > analysis_result
正式检索入口: retrieval_bundle > retrieval_context
正式编译输入: assembled_graph_ir > execution_plan
正式编译产物: compiled_artifact > generated_code
正式验收结果: verification_report
最终对外摘要: final_output
```

所以如果后续文档、工具或者调用方仍把以下字段当主字段，就已经落后于当前代码：

- `retrieval_context`
- `execution_plan`
- `generated_code`

## 8. `workflow_trace.py` 的附加行为

`workflow_trace.py` 与正式主链共用同一套拓扑和同一套节点实现，只多做三件事：

1. 用 `_wrap_node()` 包装每个节点，记录输入、输出、耗时、变更字段
2. 在运行结束后把 trace 落盘到 `outputs/workflow_trace_<timestamp>_<microseconds>/`
3. 把 trace 文件路径写入：

```python
final_output["workflow_trace"] = {
    "trace_dir": str,
    "summary_json": str,
    "summary_md": str,
    "final_state_json": str,
}
```

它不会改变任何节点契约，也不会改变主链流程。

Phase 4 之后，trace 摘要除原有字段外，还会直接从最终状态读取：

- `repair_history`
- `route_decision`
- `retry_counts_by_scope`
- `assembled_graph_ir.unresolved_items`
- `architecture_plan.shared_signal_registry`

并生成：

- `repair_round_count`
- `repair_scopes_seen`
- `final_route_decision`
- `retry_exhausted`
- `retry_counts_by_scope`
- `last_repair_issue_ids`
- `last_repair_actions`
- `reject_reason`
- `planning_unresolved_by_type`
- `ambiguous_signal_count`
- `repair_reject_category`

其中：

- `planning_unresolved_by_type` 只统计 `scope == planning` 的 unresolved item 类型计数。
- `ambiguous_signal_count` 会按共享信号 key 去重统计仍处于 `resolution_status == ambiguous` 或 unresolved 类型为 `ambiguous_shared_signal` 的信号。
- `repair_reject_category` 是对 `route_decision.reason` 的稳定分类，例如 `ambiguous_shared_signal`、`budget_exhausted`、`no_repairable_issue`、`unsupported_repair_issue`、`repair_patch_failed`。

## 9. 当前流程的边界与未接入能力

按当前代码事实，以下能力还没有进入正式主链：

- 人工澄清 / 中断节点
- `Send` 并行子系统派发
- reducer fan-in
- 完整 `internal_flow_objects` body 编译
- HITL / persistence 的正式运行态
- 超出当前 deterministic Repair 白名单的自动修复类型

因此当前工作流更准确的描述是：

> 一个带有 Repair 条件分支的、规则优先的分层规划流水线。它已经完成了需求结构化、分层检索、系统骨架规划、子系统局部规划、全局装配、确定性编译、结构验收和有限范围的自动修复，但还没有进入并行化、人工澄清或正式 HITL。

## 10. 一句话总结

当前代码里的真实工作流不是“LLM 直接规划并输出 JSON”，而是：

```text
自然语言需求
-> 结构化需求 requirement_spec
-> 分层检索 retrieval_bundle
-> 系统级骨架 architecture_plan
-> 子系统局部 IR subsystem_plan_map
-> 全局 Graph IR assembled_graph_ir
-> 确定性编译 compiled_artifact
-> 结构验收 verification_report
-> 条件路由 route_decision
-> 必要时 deterministic repair 并回跳
```

这也是当前仓库里最应该被当成正式主契约来理解的一条主线。
