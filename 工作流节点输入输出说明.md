## 1. 当前正式主链

当前正式主链已经接入条件式澄清、架构评审和 Repair 闭环；`Send` 并行与 `repair_review` 仍未入主链。

```text
analysis
  -> ambiguity_router
ambiguity_router
  -> clarification_review | retrieval
clarification_review
  -> clarification_review | clarification_apply | retrieval
clarification_apply
  -> retrieval | END(reject)
retrieval
  -> architecture_planning
architecture_planning
  -> architecture_review
architecture_review
  -> architecture_review | architecture_feedback_apply | subsystem_planning
architecture_feedback_apply
  -> architecture_planning(feedback/clarify) | subsystem_planning(approve) | END(reject)
subsystem_planning
  -> global_assembly
  -> coding
  -> verification
  -> repair_router
repair_router
  -> END(accept/reject) | repair_agent
repair_agent
  -> subsystem_planning | global_assembly | coding | END
```

对应常量：

```python
PHASE3_NODE_ORDER = [
    "analysis",
    "retrieval",
    "architecture_planning",
    "subsystem_planning",
    "global_assembly",
    "coding",
    "verification",
]

PHASE8_REVIEW_NODE_ORDER = [
    "ambiguity_router",
    "clarification_review",
    "clarification_apply",
    "architecture_review",
    "architecture_feedback_apply",
]

REPAIR_ROUTER_NODE = "repair_router"
REPAIR_AGENT_NODE = "repair_agent"
PHASE4_RECURSION_LIMIT = 40
```

## 2. 入口与运行时

### 2.1 正式入口

- `workflow.create_workflow(checkpointer: Any | None = None)`：创建主图，不运行
- `workflow.run_workflow(user_query: str, *, thread_id: str | None = None, checkpointer: Any | None = None, runtime_metadata: dict | None = None, enable_hitl_clarification: bool = False, enable_hitl_architecture_review: bool = False)`：运行正式主链
- `workflow_trace.run_workflow(...)`：运行同一条主链，并额外记录 trace
- `scripts/run_phase5_query_suite.py`：固定 6 条 deterministic workflow case
- `scripts/run_phase6_real_query_suite.py`：固定 case 源 `AHU程序/phase6_real_query_cases.json` 的真实 workflow suite
- `scripts/run_phase6_retrieval_eval.py`：基于同一 case 源的检索层评估
- `scripts/run_phase8_hitl_smoke.py`：最小 HITL smoke CLI，用于 pause/resume、thread continuity 与 state history 冒烟验证

两条运行入口都会带：

```python
{"recursion_limit": 40}
```

### 2.2 `thread_id` / `checkpointer` / HITL 规则

- 未传 `checkpointer` 时，`thread_id` 只进入 `metadata` 与 trace 索引；不会建立 LangGraph persistence
- 传入 `checkpointer` 时，必须同时提供非空 `thread_id`；否则会抛 `ValueError`
- `enable_hitl_clarification=True` 或 `enable_hitl_architecture_review=True` 只有在同时满足 `checkpointer + thread_id` 时才会真正触发 `interrupt`
- 不满足上述条件时，review 节点仍会运行，但走 `assumed` 旁路，不会暂停

## 3. 顶层状态字段

### 3.1 主链主字段

| 字段 | 生产节点 | 主要消费者 | 说明 |
| --- | --- | --- | --- |
| `user_query` | 入口 | `analysis`、`retrieval` | 用户自然语言需求 |
| `analysis_result` | `analysis` | `ambiguity_router`、`retrieval` | Analysis 原始结果；包含 `clarification_signals` |
| `requirement_spec` | `analysis` / review apply | `architecture_planning`、`subsystem_planning`、`global_assembly`、`verification` | 正式结构化需求入口 |
| `retrieval_bundle` | `retrieval` | `architecture_planning`、`subsystem_planning`、`global_assembly`、`coding` | 正式检索主输出 |
| `decomposition_result` | `architecture_planning` | `architecture_review`、`subsystem_planning` | 系统拆解结果 |
| `architecture_plan` | `architecture_planning` | `architecture_review`、`subsystem_planning`、`global_assembly`、`verification` | 系统级骨架 |
| `subsystem_plan_map` | `subsystem_planning` | `global_assembly`、`verification` | 各子系统局部 IR |
| `assembled_graph_ir` | `global_assembly` | `coding`、`verification` | 当前真实编译输入 |
| `compiled_artifact` | `coding` | `verification` | 当前真实编译产物 |
| `verification_report` | `verification` | `repair_router`、外部调用方 | 当前真实验收结果 |
| `repair_context` | `repair_agent` | repair 回跳、trace | 最近一轮 repair 的上下文 |
| `repair_history` | `repair_agent` | trace、审计 | repair / reject 结构化历史 |
| `route_decision` | `repair_router` / `repair_agent` | repair 分支、trace | 稳定路由决策 |
| `retry_budget` | 初始状态 | `repair_router`、`repair_agent` | 各 scope 预算上限 |
| `retry_counts_by_scope` | `repair_agent` | `repair_router`、trace | 各 scope 已消耗计数 |
| `retry_count` | 初始状态 / `repair_agent` | trace | 聚合计数，等于 `sum(retry_counts_by_scope.values())` |
| `final_output` | `verification` / review apply / trace | 外部调用方 | 最终对外摘要；trace 版本会追加 `workflow_trace` |

### 3.2 Review / HITL 字段

| 字段 | 生产节点 | 说明 |
| --- | --- | --- |
| `hitl_stage` | `ambiguity_router` / review 节点 | 当前 review 所在阶段，典型值为 `none`、`clarification_review`、`architecture_review` |
| `review_request` | `clarification_review` / `architecture_review` | 冻结后的 review 请求 |
| `review_response` | review 节点 / 恢复命令 | review 回复载荷 |
| `review_history` | review 与 apply 节点 | review 生命周期审计记录 |
| `review_enabled` | review 节点 | 当前 review 是否允许真正 `interrupt` |
| `review_required` | `ambiguity_router` / `architecture_review` | 是否需要 review |
| `review_status` | router / review / apply | `none / pending / assumed / answered / applied / rejected / interrupted / not_required` 等稳定状态 |
| `review_id` | review 节点 | 当前 review 的稳定 ID |
| `clarification_round` | `clarification_apply` | 澄清回写轮次 |
| `architecture_feedback_patch` | `architecture_feedback_apply` | 架构反馈回写到需求侧的补丁摘要 |
| `enable_hitl_clarification` | 入口 | clarification review 的 HITL 开关 |
| `enable_hitl_architecture_review` | 入口 | architecture review 的 HITL 开关 |

### 3.3 Compat 字段

| 字段 | 来源 | 当前定位 |
| --- | --- | --- |
| `retrieval_context` | `build_legacy_retrieval_context(retrieval_bundle)` | 旧节点兼容视图 |
| `execution_plan` | `GlobalAssembler` compat 投影 | 旧平面计划，不再是正式编译输入 |
| `generated_code` | `compiled_artifact["json_text"]` | compat 字段，不是真实主产物 |

### 3.4 预留 / 历史字段

`execution_result`、`validation_result`、`debug_history`、`next_step` 当前不参与主链决策。

## 4. 节点间主线

```text
user_query
  -> analysis_result + requirement_spec
  -> review_required / review_request / review_response / clarification_round / architecture_feedback_patch
  -> retrieval_bundle
  -> decomposition_result + architecture_plan
  -> subsystem_plan_map
  -> execution_plan(compat) + assembled_graph_ir
  -> compiled_artifact + generated_code(compat)
  -> verification_report + final_output
  -> route_decision
  -> repair_context + repair_history
```

主链传播逻辑：

1. `analysis` 产出 `analysis_result`，并投影出 `requirement_spec`
2. `ambiguity_router` 基于 `clarification_signals` 决定是否进入前置澄清
3. `clarification_review / clarification_apply` 只允许回写需求侧输入，不直接修改检索和规划产物
4. `retrieval` 基于 `user_query + analysis_result` 产出 `retrieval_bundle`
5. `architecture_planning` 基于 `requirement_spec + retrieval_bundle` 产出系统级骨架
6. `architecture_review / architecture_feedback_apply` 只允许把反馈回写到需求侧，再决定是否重跑 `architecture_planning`
7. `subsystem_planning` 生成各子系统局部 IR
8. `global_assembly` 组装成全局 `assembled_graph_ir`，同时回填 compat `execution_plan`
9. `coding` 仅消费 `assembled_graph_ir` 与检索文档，确定性编译
10. `verification` 同时检查规划层、装配层和编译层
11. `repair_router` 负责 scope 路由与预算裁决
12. `repair_agent` 只修补下一跳真正会消费的上游对象，然后回跳

## 5. 节点详解

### 5.1 `analysis`

输入：

```python
{"user_query": str}
```

输出：

```python
{
    "analysis_result": {
        "retrieval_plan": {...},
        "scenario_analysis": {...},
        "metadata": {...},
        "clarification_signals": {
            "should_clarify": bool,
            "signals": list[dict],
            "signal_count": int,
        },
    },
    "requirement_spec": {...},
    "current_step": "analysis_completed",
}
```

说明：

- `analyze()` 优先走 LLM structured output，失败后回退到普通 LLM + JSON 解析，再失败走本地 fallback
- `build_requirement_spec()` 会把 `scenario_analysis` 投影成正式 `requirement_spec`
- `clarification_signals` 是前置澄清分支的真实上游输入

### 5.2 `ambiguity_router`

输入：

```python
{
    "analysis_result": dict,
    "requirement_spec": dict,
}
```

输出：

```python
{
    "analysis_result": dict,   # 当 clarification_signals 缺失时会补写
    "review_required": bool,
    "hitl_stage": "clarification_review" | "none",
    "review_status": "pending" | "not_required",
    "current_step": "ambiguity_routed",
}
```

说明：

- 若 `analysis_result.clarification_signals` 缺失，会先重新推导并回写 `analysis_result`
- 该节点不改检索、规划和装配对象

### 5.3 `clarification_review`

输入：

```python
{
    "analysis_result": dict,
    "requirement_spec": dict,
    "review_required": bool,
    "review_enabled": bool,
    "review_request": dict,
    "review_history": list,
    "review_id": str,
}
```

输出：

```python
{
    "review_request": {
        "review_id": str,
        "stage": "clarification_review",
        "question": str,
        "options": list[dict],
        "context_summary": str,
        "created_at": str,
    },
    "review_response": dict,
    "review_history": list,
    "review_enabled": bool,
    "review_status": "pending" | "assumed" | "answered" | "not_required",
    "review_id": str,
    "hitl_stage": "clarification_review" | "none",
    "current_step": str,
}
```

说明：

- `review_required=False` 时直接旁路，`current_step = clarification_skipped`
- `review_enabled=False` 时会冻结 request，但走 `assumed`
- `review_enabled=True` 时会 `interrupt(request)`，恢复后把结果规范化到 `review_response`
- 该节点不会改 `retrieval_bundle / architecture_plan / subsystem_plan_map`

### 5.4 `clarification_apply`

输入：

```python
{
    "review_response": dict,
    "analysis_result": dict,
    "requirement_spec": dict,
    "clarification_round": int,
}
```

输出：

```python
{
    "analysis_result": dict,
    "requirement_spec": dict,
    "clarification_round": int,
    "review_history": list,
    "review_enabled": False,
    "review_status": "applied" | "rejected",
    "hitl_stage": "none",
    "final_output": dict,   # reject 时会补 review_abort
    "current_step": "clarification_applied",
}
```

说明：

- 只允许回写需求侧输入
- 会把 `answers / feedback` 追加到 `assumptions`
- `decision == "reject"` 时会写 `final_output["review_abort"]`

### 5.8 `architecture_feedback_apply`

输入：

```python
{
    "review_response": dict,
    "review_request": dict,
    "requirement_spec": dict,
}
```

输出：

```python
{
    "requirement_spec": dict,
    "architecture_feedback_patch": {
        "review_id": str,
        "decision": str,
        "answers": list,
        "feedback": str,
        "updated_constraints": dict,

    "review_request": dict,
    "review_response": dict,
    "review_history": list,
```

- `approve`：不改 `requirement_spec`，直接进入 `subsystem_planning`

## 6. 核心对象关系

### 6.1 `requirement_spec` -> `architecture_plan`

## 10. 当前边界

当前仍未进入正式主链的能力：

- `Send` 并行子系统派发
- reducer fan-in
- `repair_review`
- 完整 `internal_flow_objects` body 编译
- 超出当前 deterministic Repair 白名单的自动修复类型

## 11. 一句话总结

当前正式工作流不是“LLM 直接输出 JSON”，而是：

```text
自然语言需求
-> analysis_result / requirement_spec
-> 条件式 clarification review
-> retrieval_bundle
-> architecture_plan / decomposition_result
-> architecture review
-> subsystem_plan_map
-> assembled_graph_ir
-> compiled_artifact
-> verification_report
-> route_decision
-> 必要时 deterministic repair 并回跳
```
