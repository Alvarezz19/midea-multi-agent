# 第四阶段评估问题整改实施方案（Phase 4.1）

> 日期：2026-04-11  
> 适用范围：当前仓库中的 Phase 4 首版 LangGraph 工作流  
> 目标：在**不改主链拓扑**、**不引入 Send/HITL 正式入链**的前提下，优先解决第四阶段评估报告中已经确认的 P0/P1 问题，让真实 AHU 模板复用查询恢复到可稳定复现的基线。

---

## 0. 先给结论

这次不建议先继续堆更多 LangGraph 节点，也不建议先动 `Send` 并行或正式 HITL。

当前最值得立刻执行的方案是：

1. 在 **ArchitecturePlanner -> SubsystemPlanner -> GlobalAssembler** 之间补一层“模板接口语义分类”。
2. 把“模板输入口”从“默认共享信号”改成“先分类，再决定是否进入共享信号装配”。
3. 把 `Verifier -> RepairAgent` 的 repair 信息从“解析 message 文本”改成“消费结构化 payload”。
4. 用固定中文查询 smoke 和模板语义回归用例把这条链守住。

这是当前投入产出比最高、且对现有代码侵入最小的路径。

---

## 1. 背景与问题复述

结合 `第四阶段工作流评估报告.md`、当前代码和 trace，当前真实失败链路已经很清楚：

1. `ArchitecturePlanner` 在模板复用路径下，会把模板 `ports_definition.inputs/outputs` 直接投影成子系统 `imports/exports`。
2. `_build_shared_signal_registry()` 又把这些 `imports/exports` 抬升成共享信号约束。
3. `SubsystemPlanner` 把模板接口与 `shared_signal_registry` 混合处理，默认认为这些口都参与共享信号装配。
4. `GlobalAssembler` 对每个 import 都去找 exporter；找不到就注入 placeholder。
5. 当 `allowed_external=False` 时，placeholder 会被记成 `synthetic_shared_signal_source`。
6. `RepairAgent` 的 planning repair 目前只能：
   - 推断唯一 owner
   - 或把已存在于 `requirement_spec.signals.inputs/software_points/global_modes` 的信号改成 external
7. 因此像“送风机运行状态 / 送风机故障状态 / 送风机启停手动控制命令 / PID 设定值”这类模板输入口，会直接落到：
   - `ir.unresolved.synthetic_shared_signal_source`
   - `repair_patch_failed`
   - `reject`

问题本质不是 Repair Loop 没接上，而是：

- 当前主链把“模板输入口”“跨子系统共享信号”“外部输入”“操作命令”“配置参数”混成了一类对象。
- 这会让真实 AHU 模板复用场景在进入 repair 之前就已经被错误语义击穿。

---

## 2. 推荐方案与不推荐方案

### 2.1 推荐方案

推荐采用“**补接口语义层 + 最小改动收紧共享信号集合**”的方案。

核心思想：

- 不再让模板 `inputs` 天然等于共享信号。
- 先把模板接口分类成：
  - `shared_signal`
  - `external_input`
  - `external_parameter`
  - `external_command`
  - `subsystem_output`
- 再决定：
  - 哪些口进入 `shared_signal_registry`
  - 哪些口允许 external placeholder
  - 哪些口只作为模板实例输入，不要求真实 exporter

### 2.2 不推荐方案

以下 3 种路径都不建议作为主方案：

1. 只在 `GlobalAssembler` 里把当前失败信号一股脑标记成 external。  
   原因：能止血，但会把真实跨子系统依赖也一并放掉，后续会把结构错误静默吞掉。

2. 只改 `AnalysisAgent` prompt，让它多抽一些 signals。  
   原因：能改善前链波动，但修不了“模板输入口默认被当共享信号”的契约问题。

3. 直接进入 `Send` 并行、正式 HITL 或更多 LangGraph 节点升级。  
   原因：当前主问题不在拓扑，而在状态语义。先加复杂度只会放大不稳定面。

---

## 3. Phase 4.1 总体目标

本次整改只做 4 件事：

1. 修正“模板输入口 -> 共享信号”的默认判定策略。
2. 扩展 planning repair，让它能处理“应视为 external”的场景。
3. 改造 compile repair，去掉对 verifier 中文 message 的强耦合。
4. 建立最小但有效的回归守护，覆盖真实模板复用查询。

本次**不纳入**：

- `Send` 并行正式入链
- 正式 persistence / HITL
- `internal_flow_objects` 完整 body 编译
- 全面重写 `AnalysisAgent`

## 4. 工作包 P0-1：补模板接口语义层

### 4.1 目标

让模板接口先被分类，再决定是否进入共享信号装配。

### 4.2 涉及文件

- 新增：`utils/signal_semantics.py`
- 修改：`utils/phase3_contracts.py`
- 修改：`agents/architecture_planner.py`
- 修改：`agents/subsystem_planner.py`

### 4.3 状态契约新增字段

建议新增一个统一的接口条目结构，供 `ArchitecturePlanner` 与 `SubsystemPlanner` 共用：

```python
class InterfaceBindingSpec(TypedDict, total=False):
    signal_name: str
    signal_key: str
    canonical_signal_key: str
    direction: str                 # input / output
    binding_kind: str              # shared_signal / external_input / external_parameter / external_command / subsystem_output
    allowed_external: bool
    owner_subsystem_id: str
    port_index: int
    evidence: list[str]
    confidence: float
```

建议把它挂到以下对象上：

- `SubsystemDescriptor.interface_bindings`
- `SubsystemPlan.template_interface_bindings`

兼容要求：

- 现有 `imports / exports / imported_signals / exported_signals` 继续保留。
- 但它们改为**由 `interface_bindings` 派生**，不再作为唯一事实源。

### 4.4 分类规则

`utils/signal_semantics.py` 建议提供 3 个函数：

```python
classify_template_input(...)
classify_template_output(...)
canonicalize_signal_name(...)
```

#### 输入口分类规则

按以下优先级执行：

1. 显式命中 `requirement_spec.signals.inputs / software_points / global_modes`
   - 归类为 `external_input`

2. 命中 AHU 已知跨子系统依赖表
   - 归类为 `shared_signal`

3. 命中“参数类”关键词
   - 例如：`设定值`、`比例增益`、`积分增益`、`微分增益`、`上限`、`下限`、`系数`、`运算间隔`、`延时`、`配置`
   - 归类为 `external_parameter`

4. 命中“命令/模式类”关键词
   - 例如：`命令`、`手动`、`自动`、`手/自动`、`本地/远程`、`复位`
   - 归类为 `external_command`

5. 命中“反馈/测点类”关键词
   - 例如：`状态`、`反馈`、`故障`、`压差`、`温度`、`CO2`
   - 默认归类为 `external_input`

6. 兜底规则
   - 在模板复用路径下，**模板输入默认归为 `external_input`，而不是 `shared_signal`**

#### 输出口分类规则

1. 若该输出被其他子系统显式依赖或命中跨子系统依赖别名
   - 归类为 `shared_signal`

2. 其他情况
   - 归类为 `subsystem_output`

### 4.5 初版别名表

建议只做一版小而够用的 AHU 别名表，不要一开始做大而全语义库：

```python
CANONICAL_SIGNAL_ALIASES = {
    "supply_fan_run_state": [
        "送风机运行状态",
        "送风机运行标志",
        "风机运行状态反馈",
    ],
    "supply_fan_available": [
        "送风机可用标志",
        "控制使能",
    ],
    "auto_manual_mode": [
        "手自动控制切换",
        "手/自动",
        "自动/手动",
    ],
    "local_remote_mode": [
        "本地/远程",
        "远程/本地",
    ],
}
```

注意：

- 初版别名表只覆盖当前 7 个 AHU 子流程模板里真实出现、且已经导致问题的名称。
- 不要把别名表做成开放式 prompt 推断，保持 deterministic。

### 4.6 验收标准

- `ArchitecturePlanner` 不再把单子系统模板的全部输入口无差别写入 `shared_signal_registry`
- `SubsystemDescriptor` 和 `SubsystemPlan` 中能看到结构化接口分类信息
- 兼容字段仍存在，旧路径不被立即打断

## 5. 工作包 P0-2：收紧共享信号装配边界

### 5.1 目标

只让真正的 `shared_signal` 走“找 exporter / owner / ambiguity”链路；外部输入、参数和命令允许走 external placeholder。

### 5.2 涉及文件

- 修改：`agents/architecture_planner.py`
- 修改：`agents/subsystem_planner.py`
- 修改：`agents/global_assembler.py`

### 5.3 具体改法

#### `ArchitecturePlanner`

修改点：

- 模板复用命中时，优先读取模板 `ports_definition`
- 对模板输入/输出先做分类，再生成：
  - `interface_bindings`
  - `imports / exports` compat 视图
  - `shared_signal_registry`

关键约束：

- `shared_signal_registry` 只收 `binding_kind == "shared_signal"` 的条目
- `external_input / external_parameter / external_command` 不再进入共享信号强约束

#### `SubsystemPlanner`

修改点：

- `_plan_template_reuse()` 改为以 `interface_bindings` 为主输入
- `imported_signals / exported_signals` 增加字段：
  - `binding_kind`
  - `allowed_external`
  - `canonical_signal_key`

关键约束：

- `shared_signal_registry` 只对 `shared_signal` 起作用
- 不能再把 registry 中的共享信号反向注入到所有模板输入口

#### `GlobalAssembler`

修改点：

- `exports_by_signal` 的 key 改成 `canonical_signal_key -> signal_key -> signal_name` 三层 fallback
- 处理 import 时按 `binding_kind` 分流：
  - `shared_signal`：走现有 exporter 查找逻辑
  - `external_input / external_parameter / external_command`：允许直接注入 external placeholder，不记 `synthetic_shared_signal_source`

建议新增一个更清晰的 placeholder reason：

- `Synthetic external placeholder injected by GlobalAssembler.`

不要再把它作为 `planning error`。

### 5.4 为什么这一步是 P0

这一步完成后，至少下面这类真实问题可以立即止血：

- `为 AHU 生成送风机标准控制`
  - 模板 9 个输入口不再全部被当成共享信号
  - 不会再因为缺 exporter 直接 reject

### 5.5 验收标准

- 单送风机查询不再产生 `synthetic_shared_signal_source`
- trace 中不再出现 `Unsupported planning repair target: 送风机运行状态`
- `shared_signal_registry` 规模显著收缩到真实跨子系统依赖集合

## 6. 工作包 P0-3：补 planning repair 的 external 重分类能力

### 6.1 目标

即使上游仍有漏判，repair 也要能把“其实应视为 external 的模板输入口”从 reject 拉回到可继续运行。

### 6.2 涉及文件

- 修改：`agents/verifier_agent.py`
- 修改：`agents/repair_agent.py`
- 可选修改：`utils/phase3_contracts.py`

### 6.3 结构化 repair payload

建议给 `verification_report.issues[*]` 增加 `repair_payload`：

```python
{
    "signal_name": "送风机运行状态",
    "canonical_signal_key": "supply_fan_run_state",
    "binding_kind": "external_input",
    "allowed_external": True,
    "candidate_exporters": [],
    "consumer_subsystem_ids": ["supply_fan_ctrl"]
}
```

planning issue 不再只靠：

- `target_id`
- `message`

来推断修补动作。

### 6.4 `RepairAgent` 改法

在 planning repair 中新增第三类动作：

1. `rebind_shared_signal_owner`
2. `mark_as_external`
3. `reject_unsupported_issue`

规则改为：

- 若有唯一 exporter，沿用现有 owner 收敛逻辑
- 若 `repair_payload.allowed_external=True`，则把该信号在：
  - `architecture_plan.shared_signal_registry`
  - `decomposition_result.shared_signal_registry`
  中改成：
  - `allowed_external=True`
  - `required_exporter_count=0`
- 写入清晰动作：
  - `将共享信号 XXX 重分类为 external_input`

### 6.5 关于 `ambiguous_shared_signal`

当前建议：

1. **先把它从 planning scope 的“已支持自动修复”列表中移除**
2. 等别名归一和接口语义层稳定后，再把它作为 P1 恢复支持

原因：

- 现在代码会把它识别为“可修”
- 但遇到典型多导出方场景仍会 `repair_patch_failed`
- 这会制造错误预期

### 6.6 验收标准

- planning repair 能处理“应改为 external”的场景
- `Unsupported planning repair target` 这类 reject 文案消失
- 不再靠字符串碰运气决定 planning repair 成败

## 7. 工作包 P1-1：compile repair 改成结构化字段

### 7.1 目标

去掉 `compile repair` 对 verifier 中文 message 的正则耦合。

### 7.2 涉及文件

- 修改：`agents/verifier_agent.py`
- 修改：`agents/repair_agent.py`
- 修改：`tests/test_phase4_repair_agent.py`

### 7.3 改法

在 `compile.wire.port.range` 的 issue 上直接写入：

```python
"repair_payload": {
    "source_real_id": "...",
    "target_real_id": "...",
    "invalid_target_port": 2,
    "target_input_count": 1
}
```

`RepairAgent` 读取顺序：

1. 优先读 `issue["repair_payload"]`
2. 若为空，再 fallback 到旧正则解析

注意：

- fallback 只保留一个过渡版本
- Phase 4.1 完成后，应补一个 TODO，计划删除 regex 路径

### 7.4 验收标准

- verifier 文案变化不会立即打断 compile repair
- 结构化字段覆盖现有 `compile.wire.port.range` 用例

## 10. DoD（完成定义）

满足以下条件，才算这轮整改完成：

1. `为 AHU 生成送风机标准控制`
   - 不再出现 `synthetic_shared_signal_source`
   - 不再 `planning -> reject`

   - 不再因为模板输入口误判导致大面积 planning reject

3. `RepairAgent`
   - 能处理 external 重分类
   - 不再把 `ambiguous_shared_signal` 误报为“已支持自动修复”

4. `compile repair`
   - 优先消费结构化 payload

5. 自动化
   - 新增测试全部通过
   - Phase 1/2/3/4 既有回归不退化

## 13. 最终建议

当前最优执行策略不是“继续扩图”，而是“先把模板接口语义收紧”。

只要这一步不修，Repair 闭环会持续在真实模板复用场景里被前置语义问题击穿；一旦这一步修好，Phase 4 首版的闭环框架才真正开始发挥价值。
