# 工作流 V2 第三阶段实施清单（可执行版）

> 日期：2026-04-07  
> 目标：在保持 Phase 1 / Phase 2 稳定基线不退化的前提下，把当前单体 `PlanningAgent` 拆成可落地的分层规划链，正式进入 `ArchitecturePlanner + SubsystemPlanner + GlobalAssembler` 阶段。  
> 当前基线：`Phase 1 已稳定，Phase 2 已通过`，主链为 `analysis -> retrieval -> planning -> assembly -> coding -> verification -> END`。  
> 执行结果：`Phase 3 首版已完成`，主链已切换为 `analysis -> retrieval -> architecture_planning -> subsystem_planning -> global_assembly -> coding -> verification -> END`，并已建立 Phase 3 回归基线。  
> 本文定位：不是设计讨论稿，而是可直接按项实施、按项验收的执行清单。

---

## 0. 当前基线与第三阶段问题定义

### 0.1 当前已经稳定的能力

- 主链已经从“弱计划直接出 JSON”升级为“弱计划 -> `assembled_graph_ir` -> `compiled_artifact` -> `verification_report`”。
- `retrieval_bundle` 已经正式入链，包含：
  - `atomic_modules`
  - `subflow_templates`
  - `system_patterns`
  - `style_guides`
- `AssemblyAgent`、`CodingAgent`、`VerifierAgent` 已经形成稳定的确定性后半链。
- `Phase 1` 与 `Phase 2` 回归已通过，当前仓库状态可作为第三阶段起点。

### 0.2 当前真正的瓶颈

- 当前 `PlanningAgent` 仍是单体弱计划层，只能输出一个单层 `execution_plan`。
- `system_patterns` 目前只作为 prompt hint，没有变成真正的系统级规划输入。
- `subflow_templates` 已经能被检索和引用，但“系统骨架 -> 子系统拆分 -> 模板绑定 -> 全局装配”这条链路还没有正式建立。
- 当前主链仍不能稳定处理“多页签、多子系统、跨子系统共享信号、全局命名与布局约束”的 AHU 系统级规划。

### 0.3 第三阶段的核心目标

第三阶段不再继续强化单体 `PlanningAgent`，而是完成以下结构升级：

```text
user_query
  -> analysis
  -> retrieval
  -> architecture_planning
  -> subsystem_planning
  -> global_assembly
  -> coding
  -> verification
  -> END
```

也就是说，本阶段要把“规划”从一个节点拆成三层：

- `ArchitecturePlanner`：决定系统骨架和约束
- `SubsystemPlanner`：对子系统逐个规划
- `GlobalAssembler`：把子系统局部结果装配成全局 `assembled_graph_ir`

## 1. 先定死的实施决策

下面这些决策在第三阶段开始前必须明确，不允许边做边改。

### 1.1 本阶段只做“分层规划”，不做 Repair 闭环

- 本阶段**包含**：
  - `ArchitecturePlanner`
  - `SubsystemPlanner`
  - `GlobalAssembler`
  - 新状态契约
  - 分层规划测试与验收
- 本阶段**不包含**：
  - `RepairRouter / RepairAgent`
  - 人工澄清 / 中断节点
  - 完整 HITL 流程
  - 语义修复闭环

原因：

- 当前最缺的是“系统级规划能力”，不是“自动修复能力”。
- `VerifierAgent` 已经在第一阶段落地，本阶段优先利用已有验收，而不是再扩修复面。

### 1.2 首版 Phase 3 仍保持线性主链，不立即引入 `Send`

- 第三阶段首版允许修改主链拓扑，但仍保持**顺序执行**。
- 本阶段**不强制**接入：
  - `add_conditional_edges()`
  - `Send`
  - reducer fan-in
  - subgraph 并行子图
- `SubsystemPlanner` 首版采用“按 `planning_order` 顺序规划”的方式落地。

原因：

- 当前环境 `langgraph` 版本已满足 Graph API 能力要求，但第三阶段的主要风险不在 LangGraph API 本身，而在新契约是否稳定。
- 先把 `architecture_plan / subsystem_plan_map / assembled_graph_ir` 的数据边界跑通，再做 `Send` 并行，会更稳。

### 1.3 不新增独立 `SystemDecomposer` 节点

第三阶段首版不引入独立 `SystemDecomposer` 节点，而采用下面的职责划分：

- `analysis`：保留当前职责，同时补 `requirement_spec`
- `architecture_planning`：同时产出
  - `decomposition_result`
  - `architecture_plan`

原因：

- 当前第三阶段的核心范围是拆 `PlanningAgent`，不应再额外扩出新的前置节点。
- `decomposition_result` 虽然需要正式入状态，但不必为此新建一个独立节点。

### 1.4 `analysis_result` 与 `execution_plan` 暂时保留兼容语义

- `analysis_result` 暂时保留，但新代码优先消费 `requirement_spec`
- `execution_plan` 暂时保留为兼容字段，但它不再是第三阶段主规划产物
- 第三阶段正式主中间产物是：
  - `requirement_spec`
  - `decomposition_result`
  - `architecture_plan`
  - `subsystem_plan_map`
  - `assembled_graph_ir`

### 1.5 `internal_flow_objects` 在第三阶段先进入“规划与追踪上下文”，不直接做完整 body 编译

第三阶段必须明确：

- `internal_flow_objects` 继续保留在 Phase 2 知识资产中
- `ArchitecturePlanner / SubsystemPlanner` 可以把它作为模板绑定和规划解释的证据
- `GlobalAssembler / CodingAgent` 本阶段**不承诺**把 `internal_flow_objects` 完整编译进最终平台 JSON

原因：

- 如果本阶段同时做“分层规划 + 完整子流程 body 编译”，范围会失控。
- 完整 body 编译可作为 `Phase 3B` 或 `Phase 4` 的后续任务。

### 1.6 Phase 2 资产构建链继续沿用，不在第三阶段重构知识库体系

- `kong_modules_v1`
- `ahu_subflow_templates_v1`
- `ahu_system_patterns_v1`

第三阶段继续复用这三类 collection，不在本阶段重写：

- `init_knowledge_base.py`
- `update_knowledge_base.py`
- `auto_sync_schemas.py`

第三阶段聚焦“消费这些资产进行分层规划”，而不是重做资产生成体系。

## 3. 第三阶段核心契约定义

这一节是实施时最重要的部分。没有把契约写清楚，第三阶段会反复返工。

## 3.1 `requirement_spec`

### 最低必需字段

```json
{
  "schema_version": "3.0",
  "system_type": "AHU",
  "scenario_summary": "",
  "subsystems": [],
  "signals": {
    "inputs": [],
    "outputs": [],
    "software_points": [],
    "alarm_points": []
  },
  "required_pages": [],
  "global_modes": [],
  "ambiguities": [],
  "assumptions": [],
  "acceptance_criteria": [],
  "confidence": 0.0
}
```

### 生成策略

- 由当前 `analysis_result.scenario_analysis` 转换得到
- 当前 `AnalysisAgent` 不重写业务理解逻辑，只加一层适配输出
- 若 `scenario_analysis` 信息不足：
  - 可以留空
  - 但必须把不确定项放入 `ambiguities` / `assumptions`

### 第三阶段要求

- `ArchitecturePlanner` 只读 `requirement_spec`，不再直接消费宽语义的 `analysis_result`
- `requirement_spec` 必须是结构化对象，而不是 prompt 文本

## 3.2 `decomposition_result`

### 最低必需字段

```json
{
  "pages": [],
  "subsystem_descriptors": [],
  "shared_signal_registry": [],
  "template_needs": [],
  "planning_order": []
}
```

### 字段要求

- `pages`
  - 页签候选清单
  - 至少含 `page_id / label / kind / order`
- `subsystem_descriptors`
  - 每个子系统的规划边界
  - 至少含：
    - `subsystem_id`
    - `subsystem_type`
    - `page_id`
    - `goal`
    - `implementation_preference`
    - `imports`
    - `exports`
- `shared_signal_registry`
  - 跨子系统共享信号描述
- `planning_order`
  - 子系统规划顺序

### 生产者

- `ArchitecturePlanner`

## 3.3 `architecture_plan`

### 最低必需字段

```json
{
  "pages": [],
  "subsystem_slots": [],
  "global_constraints": [],
  "naming_strategy": {},
  "layout_strategy": {},
  "pattern_bindings": [],
  "warnings": []
}
```

### 字段要求

- `pages`
  - 不是候选页签，而是正式系统骨架页签
- `subsystem_slots`
  - 系统级对子系统的约束
  - 至少含：
    - `subsystem_id`
    - `page_id`
    - `preferred_implementation`
    - `preferred_template_ids`
    - `fallback_mode`
    - `priority`
- `global_constraints`
  - 全局命名、模式切换、共享点位、布局约束
- `pattern_bindings`
  - 当前命中的 `system_patterns`
  - 至少记录：
    - `pattern_id`
    - `reasoning`
    - `applied_scope`

### 第三阶段要求

- `system_patterns` 不再只停留在 prompt hint
- `ArchitecturePlanner` 必须显式记录“哪个 pattern 被采用、采用到哪一层、为什么采用”

## 3.4 `subsystem_plan_map`

### 目标结构

```json
{
  "supply_fan_ctrl": {
    "subsystem_id": "supply_fan_ctrl",
    "page_id": "page_control",
    "implementation_mode": "reuse_template",
    "template_binding": {},
    "node_instances": [],
    "edges": [],
    "imported_signals": [],
    "exported_signals": [],
    "constraints": [],
    "unresolved_items": []
  }
}
```

### 关键要求

- 每个子系统必须独立规划
- 每个子系统必须显式给出：
  - `implementation_mode`
    - `reuse_template`
    - `atomic_assembly`
  - `template_binding`
    - 若命中模板，必须写入 `template_id`
    - 若未命中模板，必须明确退化到 `atomic_modules`
- `node_instances` / `edges` 表达的是**子系统局部 IR**
- `imported_signals` / `exported_signals` 用于后续全局装配

### 局部 IR 最低字段

为了让 `GlobalAssembler` 可以**纯确定性**消费 `subsystem_plan_map`，第三阶段首版必须把子系统局部 IR 的最低字段定死。

- `node_instances[*]` 最低要求与当前 `NodeInstanceIR` 核心字段对齐，至少包含：
  - `logic_id`
  - `module_type`
  - `page_id`
  - `template_id`
    - 命中模板时必填
    - 原子拼装时可为空字符串或 `null`
  - `parameters`
  - `input_count`
  - `output_count`
  - `position`
    - 首版允许写入占位坐标，如 `{ "x": 0, "y": 0 }`
    - 但必须是结构化对象，不能留成自然语言描述
  - `reasoning`
- `node_instances[*].instance_id`
  - 首版允许由 `GlobalAssembler` 统一补全
  - 但若 `SubsystemPlanner` 不直接给出，则必须能由 `subsystem_id + logic_id` 确定性生成
- `edges[*]` 最低要求至少包含：
  - `from_node`
  - `from_port`
  - `to_node`
  - `to_port`
  - `signal_name`（可选）
- `GlobalAssembler` 可以在全局装配阶段补全：
  - `instance_id`
  - `edge_id`
  - `signal_id`
  - 最终布局坐标

建议局部 `node_instances[*]` 最低结构如下：

```json
{
  "logic_id": "supply_fan_ctrl_main",
  "module_type": "ahu_supply_fan_std",
  "page_id": "page_control",
  "template_id": "ahu_supply_fan_std",
  "parameters": {},
  "input_count": 2,
  "output_count": 1,
  "position": {"x": 0, "y": 0},
  "reasoning": "优先复用送风机标准模板"
}
```

### 第三阶段约束

- `SubsystemPlanner` 不允许跨子系统随意规划
- 跨子系统连接必须通过 `imported_signals / exported_signals` 声明，而不是直接拉全局边

## 3.5 `assembled_graph_ir`

第三阶段中，`assembled_graph_ir` 仍然是 `CodingAgent` 和 `VerifierAgent` 的正式输入。

但是它的来源要从：

- 旧路径：`execution_plan -> AssemblyAgent`

升级为：

- 新路径：`architecture_plan + subsystem_plan_map -> GlobalAssembler`

### 第三阶段要求

- 继续兼容当前 `utils/graph_ir.py` 的核心结构
- 必须补齐：
  - 多页签
  - 跨子系统共享信号
  - 全局命名策略落地
  - 未解析约束写入 `unresolved_items`

### Verifier 兼容策略

第三阶段首版必须明确：当前 `VerifierAgent` 仍然依赖 `assembled_graph_ir.source_execution_plan` 来判断以下问题：

- 规划失败
- 空计划
- 空节点产物的来源归因

因此，在 `VerifierAgent` 完成最小适配之前，`GlobalAssembler` 必须执行以下二选一策略之一，并在实现前写死：

1. 推荐方案：
   - 通过 `build_legacy_execution_plan(...)` 从
     - `requirement_spec`
     - `architecture_plan`
     - `subsystem_plan_map`
     生成兼容投影
   - 写回 `assembled_graph_ir.source_execution_plan`
2. 备选方案：
   - 对 `VerifierAgent` 做**最小兼容适配**
   - 让它在缺少 `source_execution_plan` 时，改为读取新的分层规划产物判断 planning failure

第三阶段首版默认采用方案 1，原因如下：

- 可以最大限度复用当前 Phase 1 / Phase 2 已通过的验收口径
- 可以避免在主规划链尚未稳定前，同时改动 `GlobalAssembler` 和 `VerifierAgent` 的核心判断逻辑
- `execution_plan` 在本阶段只是兼容投影，不再作为正式主规划产物

## 7. 关键风险与控制措施

## 7.1 风险：新状态字段进入主链后，旧测试大面积失效

### 控制措施

- 保留 `analysis_result` / `retrieval_context` / `execution_plan` 兼容层
- 先补适配函数，再改工作流拓扑

## 7.2 风险：`ArchitecturePlanner` 输出过宽，导致 `SubsystemPlanner` 无法稳定消费

### 控制措施

- 先定最小 schema
- 在测试里锁住最低必需字段

## 7.3 风险：`SubsystemPlanner` 越权输出全局连接，导致 `GlobalAssembler` 失去意义

### 控制措施

- 强制子系统只输出局部 IR
- 跨子系统依赖只能通过 `imported_signals / exported_signals`

## 7.4 风险：第三阶段被 `internal_flow_objects` 完整编译拖垮

### 控制措施

- 本阶段明确不承诺完整 body 编译
- 只把它作为模板解释与追踪上下文

## 7.5 风险：`workflow.py` 与 `workflow_trace.py` 再次分叉

### 控制措施

- 共享建图函数
- 同步维护 `WorkflowState`
