# 工作流前三阶段遗留问题集中整改实施清单（可执行版）

> 目标：在不提前进入 `Phase 4 Repair` / `Send` 并行 / HITL 的前提下，集中收口 `Phase 1 ~ Phase 3` 留下的真实遗留问题，把当前“已跑通且有回归”的基线提升为“契约更干净、质量更稳定、资产可正式落库、文档与环境口径一致”的稳定基线。  
> 当前核对日期：`2026-04-09`。  
> 当前核对结果：主链仍为 `analysis -> retrieval -> architecture_planning -> subsystem_planning -> global_assembly -> coding -> verification -> END`；本地执行 `python -m unittest discover -s tests -p "test_phase*.py"` 共 `46` 个测试通过。  
> 本文定位：不是第四阶段设计稿，也不是问题讨论稿，而是可以立刻分批执行、分批验收的整改清单。

## 0. 本轮范围先定死

### 0.1 本轮纳入

- `Phase 3` 原生契约收口：减少对 `execution_plan` / `source_execution_plan` 兼容投影的硬依赖。
- `Phase 3` 规划质量硬化：提高 `requirement_spec -> architecture_plan -> subsystem_plan_map` 的真实 AHU 规划稳定性。
- `Phase 2` 正式落库策略闭环：把 `chroma_db` 的写入策略、验收路径和资产来源管理定死。
- 文档、遗留模块、依赖版本口径收口。

### 0.2 本轮明确不纳入

- `RepairRouter / RepairAgent`
- `Send` 并行子系统派发
- reducer fan-in
- HITL / `interrupt` / checkpointer 恢复机制
- `ValidationAgent` 回主链
- 完整 `internal_flow_objects` body 编译

### 0.3 为什么这轮不把这些一起做

- `docs/ahu/LangGraph工作流V2架构设计.md` 与 `docs/ahu/第四阶段实施清单.md` 已明确把 `Repair`、`Send`、HITL 放到后续阶段。
- LangGraph 官方文档把 `Send` 定义为并行 fan-out 手段，把 `Command` 用于单点路由；这两者都属于图路由能力升级，不是前三阶段遗留收口本身。
- LangGraph 官方文档也明确 `interrupt` / HITL 依赖 checkpointer 与 `thread_id`；当前仓库还没有把持久化恢复当作正式基线，不适合并入本轮。

## 1. 当前真实遗留问题画像

### 1.1 `Phase 3` 仍然对 legacy 兼容投影有硬依赖

当前代码里，`Phase 3` 的正式主产物已经是：

- `requirement_spec`
- `decomposition_result`
- `architecture_plan`
- `subsystem_plan_map`
- `assembled_graph_ir`
- `compiled_artifact`
- `verification_report`

但以下 legacy 兼容字段仍然深度参与主链：

- `workflow.py` / `workflow_trace.py` 的 `WorkflowState` 仍保留 `retrieval_context`、`execution_plan`、`generated_code`、`execution_result`、`validation_result` 等历史字段。
- `agents/global_assembler.py` 仍通过 `build_legacy_execution_plan(...)` 回填 `execution_plan`。
- `agents/verifier_agent.py` 仍优先依赖 `assembled_graph_ir.source_execution_plan` 判断规划失败与空计划。

需要补充说明的是：当前 `VerifierAgent` 并不是“只看 legacy compat 投影”，其大部分结构验收已经基于 `assembled_graph_ir`、`compiled_artifact` 与 `unresolved_items`；但它仍把 `source_execution_plan` 的缺失/空节点当作错误条件，这会导致 `Phase 3` 原生产物尚不能完全独立完成验收。

另外，当前 `VerifierAgent.verify()` 的函数签名只接收：

- `assembled_graph_ir`
- `compiled_artifact`

如果要真正让它直接理解 `Phase 3` 原生产物，还需要明确它是：

- 扩展 `verify(...)` 输入边界
- 还是在 `__call__` 中读取完整状态并做原生契约判定

这说明当前 `Phase 3` 还没有真正做到“只靠原生分层产物即可完成验收”，只是已经把主链切到了分层规划。

### 1.2 `Phase 3` 的主要瓶颈已经从“能不能跑通”变成“规划质量够不够稳”

结合文档与代码，当前质量瓶颈主要集中在下面四点：

- `utils/phase3_adapters.py` 的 `build_requirement_spec()` 仍以规则投影为主，遇到场景描述不完整时容易退化到空子系统或弱约束输出。
- `agents/architecture_planner.py` 对 `system_patterns` 的选择仍是“metadata 指定优先，否则首个 pattern”，对 `subflow_templates` 虽已有基于 `template_role` 与关键词的粗评分，但仍缺少更强的匹配评分、拒识策略，以及对 `required_pages / global_modes / signals` 的显式利用。
- `agents/subsystem_planner.py` 的 atomic fallback 仍偏粗粒度，更多是在“拼一个可编译骨架”，还不是“高可信 AHU 子系统方案”。
- `agents/global_assembler.py` 仍承担较多“兜底推断”职责，例如共享信号缺少导出方时注入 placeholder；虽然后续已经能把“未声明为外部输入的内部共享信号 placeholder”打成 `synthetic_shared_signal_source` 错误，但这仍说明共享信号归属没有在更前面的规划阶段被定死。

还需要补充两个事实：

- `agents/subsystem_planner.py` 当前几乎不消费 `requirement_spec` 与架构层共享信号归属约束，`imported_signals / exported_signals` 仍主要由本地模板端口和 fallback 结构投影得到。
- 当前多子系统质量回归还不够完整：已有 `送风机 + 电加热` 的装配级测试、`送风机 + 直膨` 的架构级测试，以及单 `送风机` 的真实集成回归，但尚未形成 `送风机 + 冷水阀 / 电加热 / 直膨` 的端到端回归矩阵。

### 1.3 `Phase 2` 的正式 collections 落库策略仍未闭环

这部分代码能力已经具备，但工程决策仍未落地：

- `utils/ahu_knowledge_builder.py` 和 `scripts/build_phase2_retrieval_indexes.py` 已支持生成资产并写入 Chroma。
- 现有测试已覆盖模板主键稳定性、依赖提取、stale ID 清理、临时 Chroma 检索回归。
- 但 `工作流总结文档.md`、`工作流演进记录.md` 都明确指出：`Phase 2 collections` 正式写入目标 `chroma_db` 的策略仍未定。
- 同时，`AHU程序/flows_*.json` 虽已作为仓库输入资产存在，但其正式基线、更新流程、校验口径尚未冻结。

这会导致“测试环境可复现”和“正式库可维护”之间仍有断层。

这里还需要补充三个工程事实：

- 当前实现是“同一次构建从内存 `assets` 同时写 `pattern_library` 与 Chroma”，而不是“Chroma 再从落盘后的 `pattern_library` 反向导入”。
- `manifest` 当前只记录目录与数量，没有源文件 hash / mtime、生成时间、目标 collection 名、embedding 配置等追溯信息。
- `chroma_db` 当前已进入版本管理，且工作区里存在变更；因此本轮必须明确它到底是“正式参考库”还是“可重建缓存”，否则正式写库、回滚和提交策略都会继续模糊。

### 1.4 仓库里的文档与环境口径仍有明显分叉

实际核对后，至少存在以下偏差：

- `README.md` 仍以 `PlanningAgent -> CodingAgent` 为主链描述。
- `docs/analysis_agent_summary.md` 仍停留在旧主链口径，没有反映 `requirement_spec` 与 `Phase 3` 分层规划。
- `docs/new_retrieval_agent_summary.md`、`docs/planning_agent_summary.md`、`docs/knowledge_base_architecture.md` 仍混有旧主链或旧知识库口径。
- `requirements.txt` 中 `langgraph>=0.0.40` 的声明明显落后于当前实际验证环境；当前本地环境实测版本为 `1.0.6`。

如果不先把这些口径收拢，后面不论做质量迭代还是做 `Repair`，协作成本都会继续上升。

另外还有两点需要一起收口：

- `workflow_trace.py` 当前已经是正式 `Phase 3` 主链的 trace 入口，不应继续被误写成旧实验编排文件。
- 依赖基线不应只看 `langgraph / langchain / chromadb`，实际运行还依赖 `langchain-openai / openai / pydantic / sentence-transformers / torch / transformers / python-dotenv / langsmith` 等包。

## 2. 本轮整改目标

完成本轮后，仓库应达到下面的目标画像：

1. `VerifierAgent` 可以直接理解 `Phase 3` 原生产物，不再把 `execution_plan` 当作必需依赖。
2. `ArchitecturePlanner / SubsystemPlanner / GlobalAssembler` 对真实 AHU 多子系统场景的稳定性明显提升，并有新的回归样本证明。
3. `Phase 2` 资产写入正式 `chroma_db` 的策略、命令、回滚和验收路径被明确写死。
4. 顶层文档、遗留模块状态、依赖版本声明与当前真实主链一致。

## 4. 具体实施清单

## 4.1 工作包 A：去除 `Phase 3` 对 legacy `execution_plan` 的验收强依赖

### 目标

- 保留兼容投影，但让 `VerifierAgent` 可以直接消费 `Phase 3` 原生规划产物。
- 把 `execution_plan` 从“验收硬依赖”降级为“兼容输出”。

### 需要修改的文件

- `agents/verifier_agent.py`
- `agents/global_assembler.py`
- `utils/phase3_adapters.py`
- `workflow.py`
- `workflow_trace.py`
- `tests/test_phase3_workflow.py`
- 建议新增：`tests/test_phase3_verifier_native_contract.py`

### 具体任务

- [ ] 给 `VerifierAgent` 增加 `Phase 3` 原生输入判定逻辑，至少直接检查：
  - `architecture_plan.subsystem_slots`
  - `subsystem_plan_map`
  - `assembled_graph_ir.unresolved_items`
- [ ] 明确 `VerifierAgent` 的输入边界调整方式：
  - 扩展 `verify(...)` 的输入签名
  - 或在 `__call__` 中读取完整 `WorkflowState` 后补原生契约判定
- [ ] 当 `source_execution_plan` 缺失时，不再把它直接判成“无法验收”；应改为读取分层产物判断：
  - 规划是否为空
  - 子系统是否全部缺失
  - 是否存在未解析的共享信号 / page / module
- [ ] 保留 `build_legacy_execution_plan(...)`，但把它标记为 compat-only，不再承载主验收语义。
- [ ] 修正 `verification_report.repair_scope` 的分类逻辑，避免 `planning` 类问题被错误落到 `compile`。
- [ ] 在 `workflow.py` / `workflow_trace.py` 中把状态字段按“正式字段 / compat 字段 / 历史保留字段”分组，避免继续混淆。
- [ ] 新增回归：即使不回填 `execution_plan`，`Phase 3` 真实产物仍能通过或失败得足够明确。
- [ ] 新增 native contract 回归，至少覆盖：
  - 无 `source_execution_plan` 但原生 `assembled_graph_ir` 完整时可正常验收
  - 无 `source_execution_plan` 且 `subsystem_plan_map` 为空时可明确失败
  - `planning` 类错误的 `repair_scope` 不再被错误映射

### 验收标准

- `VerifierAgent` 在没有 `source_execution_plan` 时，仍能对 `Phase 3` 原生状态给出稳定结论。
- `GlobalAssembler` 的 compat 回填不再是验证成功的前置条件。
- 现有 `Phase 1 / Phase 2 / Phase 3` 回归不退化。

## 4.2 工作包 B：补齐 `Phase 3` 质量回归与共享信号前置约束

### 目标

- 把当前“能跑通但质量仍需迭代”的状态，推进到“关键多子系统场景有真实回归保护”。
- 让共享信号归属尽量在 `ArchitecturePlanner / SubsystemPlanner` 阶段被定死，而不是等到 `GlobalAssembler` 再兜底。

### 需要修改的文件

- `utils/phase3_adapters.py`
- `agents/architecture_planner.py`
- `agents/subsystem_planner.py`
- `agents/global_assembler.py`
- `tests/test_phase3_architecture_planner.py`
- `tests/test_phase3_subsystem_planner.py`
- `tests/test_phase3_global_assembler.py`
- `tests/test_phase3_workflow.py`
- 建议新增：`tests/data/phase3_acceptance_cases/` 或 `AHU程序/phase3_acceptance_cases/`

### 具体任务

- [ ] 给 `build_requirement_spec()` 增加更强的“子系统/全局模式/页面/信号”投影规则，并把低置信度情况显式写入 `warnings` 与 `ambiguities`。
- [ ] `ArchitecturePlanner` 不再默认“metadata 指中的 pattern 或首个 pattern 就直接使用”；改为基于：
  - `required_pages`
  - `subsystem_type`
  - `global_modes`
  - `signals`
  做可解释的 pattern 评分。
- [ ] `ArchitecturePlanner` 对 `metadata.selected_case_pattern_id` 不再直接盲信；它应作为强信号参与评分或校验，而不是绕过评分逻辑。
- [ ] `ArchitecturePlanner` 显式生成共享信号归属草案，例如：
  - 哪些信号必须有唯一导出方
  - 哪些信号允许来自外部输入
  - 哪些信号属于全局模式
- [ ] 给共享信号归属草案补稳定字段，至少包括：
  - `signal_name`
  - `owner_subsystem_id`
  - `allowed_external`
  - `required_exporter_count`
  - `consumers`
  - `source_reason`
- [ ] `SubsystemPlanner` 在生成 `imported_signals / exported_signals` 时，优先遵循架构层归属，不再只按本地模板端口被动投影。
- [ ] 缩小 atomic fallback 触发面：
  - 没有合格模板时才 fallback
  - fallback 后必须留下明确 `reasoning` 与降级标记
  - 真正存在未解决问题时再写入 `unresolved_items`
- [ ] 补多子系统真实回归场景，至少覆盖：
  - 送风机 + 冷水阀
  - 送风机 + 电加热
  - 送风机 + 直膨
  - 共享 `schedule_enable` / `auto_manual` / 可用标志
  - 外部输入合法 placeholder 与非法 placeholder 两条路径

### 验收标准

- 新增多子系统回归通过。
- `ambiguous_shared_signal` 与 `synthetic_shared_signal_source` 的触发率下降，且更早在规划阶段暴露。
- `ArchitecturePlanner / SubsystemPlanner` 的关键决策都可在测试中被断言，而不是只能靠人工读 trace。
- 合法外部输入 placeholder 与非法内部 placeholder 都有明确正/负向断言。
