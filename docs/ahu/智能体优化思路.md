# 智能体优化思路

要让你的 LangGraph 工作流从“能拼简单计算模块”进化到“能生成 AHU 这类复杂控制程序”，核心不是单纯把某个 Agent 做得更强，而是要把整个系统从**单步线性生成**升级为**面向工程结构的分层规划 + 约束生成 + 多轮校验**。

因为前面那种 AHU 程序，难点不在“把几个模块接起来”，而在这几件事同时成立：

1. **它有强烈的层级结构**：页签、子流程、控制回路、点位层、参数层、告警层。
2. **它有大量隐含工程约束**：手自动、启停联锁、故障/可用、上下限、延时、PID 参数、模板风格。
3. **它不是单回路，而是多子系统协同**：送风机、冷水阀、电加热、新回风阀、CO2、排风、故障、定时。
4. **它要求生成结果“像已有项目”**：不只是逻辑正确，还要结构风格一致、命名一致、模板一致、接口一致。
5. **它本质上是图生成问题，不是纯文本续写问题**。

所以你现在这条线性链路：

**需求分析 → 模块检索 → 逻辑规划 → JSON生成**

对于简单需求够用，但对复杂控制程序会遇到几个根本瓶颈。

---

## 一、当前工作流的主要瓶颈

### 1. Analysis 太偏“语义理解”，不够“工程结构化”

现在的 Analysis Agent 能输出 retrieval_plan 和 scenario_analysis，但对于复杂控制程序还不够。

因为复杂控制程序不是只要提取“业务目标、输入输出、控制策略”就行，它还需要额外识别：

- 系统由哪些**子系统**组成
- 每个子系统对应哪些**标准控制模式**
- 哪些是**主控制链**，哪些是**保护链/联锁链/告警链**
- 哪些变量是**测点**，哪些是**软点**，哪些是**设定值**
- 哪些对象应该抽成**子流程**
- 哪些逻辑必须复用已有模板，而不能自由生成

也就是说，Analysis 现在更像“自然语言理解器”，但复杂控制程序需要它升级成“**控制工程需求编译器**”。

---

### 2. Retrieval 只检索“模块”，没有检索“结构模式”

现在的 Retrieval Agent 是去 ChromaDB 检索基础模块，这对于简单程序没问题。

但复杂 AHU 程序的关键知识，不只是“有哪些模块”，而是：

- AHU 常见由哪些**控制子回路**构成
- 某个子回路常见的**连接范式**是什么
- 某类程序通常有哪些**页签组织方式**
- 哪些子流程是高频复用模板
- 某种控制策略对应什么样的**图结构骨架**
- 类似项目最终 JSON 的**组织风格**

换句话说，复杂控制程序生成需要检索三层知识：

1. **原子模块**：比较器、PID、限幅、延时、切换器
2. **组合模块 / 子流程模板**：送风机标准控制、冷水阀控制、7档电加热
3. **系统级结构模式**：AHU 程序通常如何分 tab、如何划分主流程、如何布置 I/O 与控制页

你现在只检索第 1 层和部分第 2 层，但第 3 层几乎没有进入系统。

---

### 3. Planning 产出的 execution_plan 还不够“图中间表示”

你现在把 execution_plan 定义为逻辑中间表示，这个方向是对的，但如果它还是偏文本式计划，那就不够支撑复杂控制程序。

复杂控制程序需要的 execution_plan，不应该只是“要用哪些模块、怎么连”，而应该是一个更强约束的**图 IR**，至少要显式表达：

- 系统分成哪些子系统
- 每个子系统包含哪些节点实例
- 每个实例来自哪个模板
- 每个实例的输入输出端口是什么
- 连接关系是什么
- 哪些节点属于哪个页签/分组
- 哪些参数来自用户需求，哪些来自默认库
- 哪些地方允许自动补全，哪些地方必须严格命中检索模板

如果没有这种结构化 IR，Coding Agent 很容易“从规划文本自由发挥”，最后又回到幻觉式生成。

---

### 4. Coding 现在更像“渲染器”，还不是“受约束的编译器”

复杂 JSON 生成时，Coding Agent 不能只是把 plan 翻成 JSON。

它必须承担类似编译器后端的职责：

- 节点实例化
- 端口映射检查
- 参数类型检查
- ID 分配
- 子流程引用关系维护
- 位置布局
- 跨 tab 连接处理
- 模板字段填充
- 平台约束合法性检查

尤其是复杂控制程序里，常见问题不是“逻辑思路错”，而是：

- 端口名对不上
- 模板缺少必须字段
- 引用的 subflow 没定义
- 一个参数名在不同节点里不一致
- 连线方向错
- 某个点位既当输入又当输出
- 某页签节点漏放
- 自动布局导致结构不可读

所以 Coding 不能只是最后一步“生成 JSON”，而应该是“**约束驱动的图编译器 + 校验器**”。

---

## 二、要生成复杂控制程序，建议从 8 个方面升级

---

### 1. 把“线性链路”升级为“分层规划链路”

你现在是：

**Analysis → Retrieval → Planning → Coding**

更适合复杂控制程序的应该是：

**需求编译 → 系统拆解 → 分层检索 → 子系统规划 → 全局装配 → JSON编译 → 校验修复**

更具体一点，可以变成：

#### 第1层：需求编译

把用户需求转换成结构化规范书，例如：

- **系统类型**：末端组空 / 直膨 AHU / 带排风 / 带除湿 / 医疗场景
- **控制对象树**：送风机、新风阀、回风阀、冷水阀、电加热、排风机、直膨机
- **运行模式**：关机、通风、制冷、制热、自动
- **季节/工况分支**：夏季、冬季、除湿优先、预热优先
- **闭环控制表**：每个回路的 PV / SP / MV / 约束 / PID 参数
- **联锁与保护**：故障停机、缺风报警、报警复位、延时逻辑
- **人工接管语义**：手/自动、手动命令、自动命令、最终命令
- **通讯映射需求**：哪些点要上 Modbus/BACnet，哪些是读点、哪些是写点
- **页面组织需求**：控制页、IO/通讯页、定时页、故障页、状态页
- **默认假设与待确认项**：比如湿度控制是否启用、排风机是否独立控制

#### 第2层：系统拆解

先让 Planner 不直接生成整图，而是先回答：

“这个系统应该拆成哪些子系统？”

例如 AHU 可拆成：

- 送风机启停控制
- 送风机频率控制
- 冷水阀控制
- 电加热控制
- 新/回风阀 CO2 控制
- 定时控制
- 故障状态页
- I/O 通讯页

#### 第3层：子系统独立规划

每个子系统单独生成自己的 graph plan。

#### 第4层：全局装配

最后再把子系统 plan 合并成一个完整系统图，并解决跨子系统引用。

这一步很关键，因为复杂程序不是一次性“从需求直接吐总图”，而是先分块，再组装。

---

### 2. 把检索对象从“模块”扩展到“模块 + 模式 + 案例”

这是最重要的一点之一。

你现在的 ChromaDB 里最好不要只存“基础模块”，而要分三层知识库。

#### 第一层：原子模块库

例如：

- compare
- limit
- switch
- logic
- delayOn
- delayOff
- PID
- modbusInput
- modbusOutput
- swInput
- quote

这是“积木”。

#### 第二层：控制子流程库

例如：

- 末端组空送风机标准控制
- 送风机频率控制
- 冷水阀开度控制
- 7档电加热
- 新风/回风阀 CO2 控制
- 直膨除湿

这是“标准组件”。

#### 第三层：系统级案例/骨架库

例如：

- 标准 AHU 模板
- AHU + CO2 控制版
- AHU + 排风联动版
- AHU + 除湿版
- 纯送排风系统
- 冷热切换空调箱

这里存的不是单个模块，而是：

- 页签结构
- 子流程组合方式
- 典型连线关系
- 命名规范
- 节点布局风格
- 常见默认参数

这类检索结果对复杂程序特别有价值，因为它告诉 Planner：

**“不是从零设计，而是先找最相似的工程骨架，再局部改造。”**

---

### 3. 引入“控制工程领域模型”，让 Analysis 能读懂工程语义

建议你给 Analysis Agent 增加一个显式的领域本体或 schema，而不是只让它自由总结。

比如建立一套控制程序 DSL / schema：

```json
{
  "system_type": "AHU",
  "subsystems": [
    {
      "name": "supply_fan_control",
      "control_type": "on_off_with_fault_status",
      "inputs": [...],
      "outputs": [...],
      "constraints": [...]
    }
  ],
  "control_targets": ["temperature", "co2"],
  "actuators": ["fan", "chw_valve", "damper", "heater"],
  "sensors": ["supply_temp", "return_temp", "co2", "dp"],
  "modes": ["auto_manual", "schedule", "summer_winter"],
  "required_pages": ["IO", "control", "schedule", "status"]
}
```

这样 Analysis 的输出就不再只是说明性文本，而是可供后续直接消费的“工程语义规范”。

尤其要让它显式识别这些东西：

- **设备对象**
- **测点对象**
- **控制目标**
- **控制回路类型**
- **联锁条件**
- **故障条件**
- **手自动切换**
- **时程控制**
- **季节切换**
- **子流程候选**

只要这一步不够强，后面的 Retrieval 和 Planning 都会飘。

---

### 4. 把 execution_plan 升级为“强约束图 IR”

这是另一个关键点。

你需要的 execution_plan 不应只是：

“使用模块A、模块B，A 输出连 B 输入”

而应该是分层图 IR，比如：

```json
{
  "pages": [
    {
      "name": "控制",
      "groups": [
        {
          "name": "送风机控制",
          "subflow_instance": {
            "template_id": "ahu_supply_fan_std",
            "instance_id": "sf_01",
            "inputs": {...},
            "outputs": {...},
            "params": {...}
          }
        }
      ]
    }
  ],
  "signals": [...],
  "connections": [...],
  "constraints": [...],
  "naming_policy": {...},
  "layout_hints": {...}
}
```

最好把 IR 分成 4 层：

1. **System IR**：整个项目有哪些页签和子系统
2. **Subflow IR**：每个子系统调用哪些模板
3. **Node IR**：模板展开后包含哪些节点实例
4. **Wiring IR**：端口到端口的连接关系

这样 Coding 就不是“理解自然语言 plan”，而是“消费结构化图 IR”。

---

### 5. 增加“规划前置约束”和“规划后校验”，不要让 Planner 自由发挥

复杂程序失败，很多时候不是模型不会想，而是**没有硬约束**。

你已经有一个很好的思想：retrieval_context 是白名单硬约束。这个要继续加强。

建议把约束明确分为三类：

**A. 可用模块约束**

Planner 只能使用检索到的模板或模块。

**B. 端口约束**

每个模块有哪些输入输出端口，Planner 不能自造端口名。

**C. 工程结构约束**

例如：

- AHU 必须至少有控制页
- 若出现风机，则必须有运行/故障/可用三类状态之一
- 若存在 PID 控制，则必须有设定值、实测值、P/I/D、上下限
- 若有风阀 CO2 控制，则要成对考虑新风阀和回风阀
- 若有时程控制，则要有 schedule 类节点或定时页

也就是把“合理程序结构”变成可机器检查的规则。

---

### 6. 增加专门的 Verification / Critic Agent

你现在的链路缺一个非常关键的角色：**校验者**。复杂控制程序不能一遍生成就结束，至少要有一轮“自审”。建议新增一个 Verification Agent，专门检查：

**结构一致性**

- subflow 是否都定义了
- 引用是否存在
- tab 是否完整
- 有没有孤立节点
- 有没有未连接必要输入

**端口合法性**

- 连接的端口名是否存在
- 输入输出方向是否匹配
- 参数类型是否匹配

**工程合理性**

- 风机控制是否有启停与故障
- PID 是否有设定值和反馈
- 阀门输出是否有限幅
- 手自动逻辑是否存在
- 关键设备是否有可用性判断

**风格一致性**

- 命名是否统一
- 页签组织是否符合模板
- 布局是否有明显可读性问题

这个 Agent 最好不是“再生成”，而是输出：

- 错误列表
- 警告列表
- 自动修复建议

然后再回流给 Planning 或 Coding 做修补。这会比单次生成稳很多。

---

### 7. 从“模块检索”转向“案例驱动 + 模板约束生成”

这是生成复杂控制程序最实用的一条路。不要只让系统从需求出发推理“应该怎么做”，而是尽量让它回答：**“这次需求最像哪个历史 AHU 模板？”**然后基于相似案例做变体生成。

也就是流程从：“从自然语言构造程序” 变成：“先找最像的控制骨架 → 再按需求增删改局部”

对于前面那类 AHU JSON，非常适合做成：

- 标准 AHU 基础模板
- AHU + CO2 模板
- AHU + 排风模板
- AHU + 电加热模板
- AHU + 除湿模板

用户一旦说“设计一个带送风机、冷水阀、电加热和 CO2 联动的 AHU”，系统应优先命中某个标准骨架，而不是从零构图。这会极大降低幻觉和结构失真。

---

### 8. 增加“子流程抽象与复用”能力

前面三个 JSON 文件最明显的特点，就是它们不是扁平大图，而是有大量可复用的子流程。

所以你的系统不能只会“拼节点”，还要会：

- 识别哪些逻辑块适合抽成子流程
- 优先复用已有子流程模板
- 必要时生成新的子流程定义
- 让顶层控制页调用子流程实例，而不是直接铺满原子节点

这一步非常重要，因为复杂程序的工程可维护性，很多时候就来自“子流程化”。

如果你的生成器永远只在原子模块层面拼图，那么规模一大就会崩：

- 图太散
- 连线太乱
- 命名失控
- 复用困难
- 风格不像真实项目

所以最好让 Planning 先决定：

“这次是直接拼原子模块，还是应该调用某个子流程模板？”

---

## 三、具体到 AHU 这类复杂控制程序，你最该补的能力

如果目标就是生成前面那种 AHU 程序，我建议优先补这 6 类能力。

**1. 系统级骨架识别**

让系统先判断这是哪类 AHU：

- 基础送风型
- 带冷水阀
- 带电加热
- 带 CO2 风阀联动
- 带排风
- 带除湿
- 带直膨状态/故障页

这一步决定整套程序的骨架。

**2. 子回路模板选型**

针对每个功能点，选标准子流程：

- 风机启停 → 送风机标准控制
- 风机调速 → 频率控制
- 温控 → 冷水阀开度控制
- 冬季补热 → 7档电加热
- 空气品质 → 新/回风阀 CO2 控制
- 除湿 → 直膨除湿

**3. 工程点位语义映射**

用户说“回风温度”“送风温度”“冷阀开度”“故障状态”，系统要能归类成：

- 反馈量
- 设定值
- 执行器输出
- 状态信号
- 报警信号
- 模式切换量

**4. 典型联锁规则库**

例如：

- 风机未运行时阀门最小开度如何处理
- 故障时输出如何降级
- 风机启停与压差报警如何关联
- 手动模式是否绕过自动调节
- 冷水阀和电加热是否互斥或分段工作

这些最好不是靠大模型临场推理，而是做成规则库。

**5. 参数默认策略**

例如：

- PID 初始值
- 延时默认值
- 阀门上下限
- 频率上下限
- CO2 设定值默认区间

否则即便图结构对了，程序也会像“空壳”。

**6. 布局与命名规范**

复杂程序导出的 JSON 不只是能跑，还要“像人写的工程图”。

所以要有：

- 页签命名规范
- 节点命名规范
- 子流程命名规范
- 输入输出信号命名规范
- 自动布局策略

这一点经常被低估，但实际很影响工程可用性。

---

## 四、你可以把单一 Planner 拆成 3 个更专业的 Planner

现在一个 Planning Agent 承担了太多职责。复杂控制程序建议拆开。

**1. Architecture Planner**

负责决定系统骨架：

- 哪些页签
- 哪些子系统
- 哪些子流程
- 哪些全局信号

**2. Logic Planner**

负责每个子系统内部逻辑：

- 用哪些模块
- 怎么连
- 参数怎么给
- 有哪些联锁/保护/模式切换

**3. Assembly Planner**

负责全局装配：

- 子系统之间如何共享信号
- 哪些点跨页引用
- 哪些变量需要 quote / 映射
- 最终如何组织成平台结构

这样每个 Planner 的任务都更清晰，也更容易调试。

## 五、技术上最值得增加的三个机制

### 1. 约束解码，而不是自由生成

Coding 阶段尽量不要直接让 LLM 输出完整 JSON。

更稳的方法是：

- LLM 先生成结构化 IR
- 再由确定性代码把 IR 编译成 JSON

也就是“模型负责规划，程序负责落地”。

### 2. 检索增强不只是 RAG，而是“模板绑定”

检索到模块后，不是把文本塞给模型参考，而是把它变成强绑定对象：

- 模板 ID
- 必需参数
- 端口列表
- 默认值
- 可选扩展项

这样 Planner 只能在 schema 内工作。

### 3. 失败可回退的迭代机制

复杂程序不要一轮完成。

建议支持：

- 初稿生成
- 结构检查
- 错误回流
- 局部修复
- 再校验

特别适合 LangGraph。

---

## 六、一个更适合你的升级版工作流

你可以考虑改成下面这个版本：

**1. Requirement Compiler**

把自然语言需求编译成控制工程 DSL。

**2. System Decomposer**

把系统拆成子系统、页签、子流程候选。

**3. Pattern Retriever**

检索相似系统骨架、控制模板、原子模块。

**4. Architecture Planner**

先生成系统级骨架。

**5. Subsystem Planner**

对子系统逐个生成 graph IR。

**6. Global Assembler**

合并所有子系统，处理共享信号和跨页引用。

**7. JSON Compiler**

确定性编译为平台 JSON。

**8. Verifier / Critic**

做结构、端口、规则、风格检查。

**9. Repair Agent**

只修补错误，不重做全部生成。

这个流程比你现在更长，但生成复杂控制程序会稳很多。

---

## 七、落地优先级建议

如果不想一下子重构太多，建议按这个顺序做。

**第一优先级**

先把 **execution_plan 升级成强结构化 graph IR**。

这是最基础的。不做这一步，后面都容易飘。

**第二优先级**

把知识库从“基础模块库”扩展为：

- 原子模块库
- 子流程模板库
- 系统骨架案例库

**第三优先级**

新增 Verification Agent，做自动校验和回流修补。

**第四优先级**

让 Planning 分层：先系统骨架，再子系统逻辑。

**第五优先级**

把 JSON 生成改成“确定性编译”，减少 LLM 直接吐大 JSON。

---

## 八、最本质的一句话

你现在的系统更像：

**“根据需求检索一些模块，然后让模型把它们拼起来。”**

而复杂 AHU 控制程序真正需要的是：

**“先识别它属于哪种工程模板，再按子系统分层规划，在模板和约束下编译成图，最后经过规则校验后输出 JSON。”**

也就是说，升级方向不是“让 Agent 更聪明一点”，而是让系统从**文本生成范式**转向**工程编译范式**。
