## 0. 第五阶段先定死的实施决策

### 0.1 本阶段纳入

- 复杂 AHU 多子系统场景下的规划质量提升
- 共享信号归属前移与歧义治理
- `Verifier -> RepairAgent` 结构化 `repair_payload` 扩面
- workflow 级 repair 回跳回归补齐
- query suite、trace 摘要与阶段文档同步

### 0.2 本阶段明确不纳入

- `Send` 并行子系统派发正式入链
- 正式 HITL / `interrupt` / checkpointer / `thread_id` 主链化
- `langgraph` 版本升级或 `invoke(version="v2")` 迁移
- 完整 `internal_flow_objects` body 编译

### 0.3 为什么这轮不把 `Send` 和 HITL 一起做

- 当前最主要的真实问题仍是复杂场景的规划质量和 Repair 覆盖率，而不是主链拓扑本身。
- `Send` 并行虽然已有 `dispatcher / worker / merge / reducer / fan-in conflict` 的设计预留，但现在缺少的是“并行前应该稳定的状态契约与回归矩阵”。
- HITL POC 已验证 `InMemorySaver + thread_id + interrupt + Command(resume=...)` 可用，但官方文档明确要求恢复依赖 checkpointer 与幂等副作用边界；这些还不适合在当前质量基线未收口时直接并入正式主链。

### 0.4 开工前补充约束

- 本阶段的 query suite 分成两层：
  - 第一层是固定 fake analysis payload + 固定检索资产的确定性回归，用来守住契约与 repair 行为。
  - 第二层是少量真实 `workflow_trace.run_workflow(...)` 复跑，用作阶段交付证据，不作为唯一通过门槛。
- `shared_signal_registry` 继续只收 `binding_kind == shared_signal` 的条目。
  - `external_input / external_parameter / external_command / subsystem_output` 不进入该 registry，只保留在 `interface_bindings / subsystem_plan_map / trace` 中。
- `ambiguous_shared_signal_unresolved` 不是 `RepairRouter` 的新分支原因，而是 `RepairAgent` 在“尝试收敛后仍无法得到唯一 exporter”时写入的稳定拒绝原因。
- 模板/案例评分解释只保留一个事实源：
  - 详细 `score_breakdown` 放在 `architecture_plan.subsystem_slots[*]` 或 `pattern_bindings[*]`
  - `subsystem_plan_map[*]` 只保留最终 `selection_reason / degrade_reason`，不重复保存整份评分卡

## 1. 当前第五阶段要解决的真实问题

### 1.1 复杂 AHU 场景的规划质量仍不够稳

- `ArchitecturePlanner`、`SubsystemPlanner`、`GlobalAssembler` 虽已形成分层规划主链，但对复杂多子系统场景的稳定性仍不足。
- 目前真实风险已经从“能不能跑通”转成“模板/案例选择、共享信号归属、fallback 触发是否稳定可解释”。

### 1.2 `ambiguous_shared_signal` 仍缺少稳定治理策略

- 当前已收紧为“不做猜测式自动修复”，但仍缺乏稳定的“有限可修 + 稳定 reject + 完整诊断”闭环。
- 这类问题如果不收口，会持续成为复杂 AHU 规划场景的主要 reject 来源。

### 1.3 Repair 仍是 V1 子集

- 当前 `RepairAgent` 仅稳定支持：
  - `ir.unresolved.synthetic_shared_signal_source`
  - `ir.unresolved.shared_signal_owner_mismatch`
  - `ir.unresolved.missing_local_edge_endpoint`
  - `compile.wire.port.range`
- 真实 verifier failure 类型仍有大量只会走 reject，且 assembly 路径的结构化 payload 覆盖还不完整。

### 1.4 自动化验收已具备框架，但真实场景覆盖仍偏窄

- 现有 Phase 4 smoke 只有固定 2 条查询，且依赖 fake analysis payload 与临时 embedding。
- 现有 workflow 级 repair loop 测试主要集中在 planning 路径，对 assembly / compile 的真实回跳覆盖不足。
- trace 摘要已可用，但还缺少对复杂多轮 repair 和拒绝类别的稳定观测字段。

### 2.1 主链保持不变

```text
analysis
  -> retrieval
  -> architecture_planning
  -> subsystem_planning
  -> global_assembly
  -> coding
  -> verification
  -> repair_router
```

- 共享信号缺少 exporter、owner 不一致、owner 歧义等问题，能在更前面的规划阶段暴露，并通过结构化字段传到 verifier / repair / trace。
- `RepairAgent` 的 planning / assembly / compile 三类修补链路都具备 workflow 级回归。
- 新的 query suite 同时覆盖成功、稳定 reject、多轮 repair、预算耗尽等结果，而不是只覆盖成功基线。

## 3. 第五阶段关键契约调整

### 3.1 `architecture_plan.shared_signal_registry[*]`

新增字段：

- `resolution_status`: `resolved | ambiguous | missing_exporter`
- `candidate_exporters`: `list[str]`
- `resolution_evidence`: `list[str]`

约束：

- `ArchitecturePlanner` 必须明确共享信号是“已解析、歧义、缺 exporter”中的哪一种。
- `GlobalAssembler` 不再额外猜测 owner，只消费该结论并产出对应 unresolved item。
- `shared_signal_registry` 仍然只记录真正的 `shared_signal`。
- `allowed_external=True` 的 external 类接口不得为了诊断方便重新回流进 `shared_signal_registry`。

### 3.2 `subsystem_plan_map[*]`

新增字段：

- `selection_reason`
- `degrade_reason`

约束：

- `reuse_template`、`atomic_assembly`、降级 fallback 的触发原因必须可追踪。
- `SubsystemPlanner` 必须优先消费架构层共享信号归属与接口语义，不允许重新做局部 owner 猜测。
- `selection_reason` 只记录“为什么最终选这个模板/实现模式”。
- 详细模板评分拆解统一放在 `architecture_plan.subsystem_slots[*].score_breakdown`，避免 architecture / subsystem 两层各写一套解释。

### 3.3 `assembled_graph_ir.unresolved_items[*]`

planning / assembly unresolved 项统一补齐结构化字段：

- `candidate_exporters`
- `consumer_subsystem_ids`
- `resolution_status`
- `resolution_hint`
- `edge_locator`

约束：

- 不能再只依赖 `message` 文本驱动 repair。
- `VerifierAgent` 生成的 `repair_payload` 必须优先来自这些结构化字段。
- planning unresolved 的结构化字段由 `ArchitecturePlanner / GlobalAssembler` 负责产出。
- assembly unresolved 的结构化字段由 `GlobalAssembler` 负责产出，`VerifierAgent` 只做投影和补充，不重新发明定位信息。

### 3.4 `verification_report.issues[*].repair_payload`

第五阶段后要求三类 scope 全部具备结构化 `repair_payload`：

- planning：
  - `signal_name`
  - `canonical_signal_key`
  - `binding_kind`
  - `allowed_external`
  - `candidate_exporters`
  - `consumer_subsystem_ids`
  - `owner_subsystem_id`
  - `resolution_status`
- assembly：
  - `subsystem_id`
  - `edge_ids`
  - `from_node`
  - `to_node`
  - `reason`
- compile：
  - `source_real_id`
  - `target_real_id`
  - `invalid_target_port`
  - `target_input_count`

约束：

- compile repair 移除对 verifier `message` 的 regex fallback 依赖。
- assembly repair 改为优先消费结构化 payload，而不是只基于当前局部结构重扫。
- planning / assembly / compile 三类 payload 的唯一事实源分别是：
  - planning：`shared_signal_registry` + `interface_bindings` + `assembled_graph_ir.unresolved_items`
  - assembly：`assembled_graph_ir.unresolved_items`
  - compile：verifier 对 `compiled_artifact` 的结构化检查结果

### 3.5 `route_decision.reason`

新增稳定拒绝原因：

- `ambiguous_shared_signal_unresolved`

保留现有原因：

- `no_repairable_issue`
- `unsupported_repair_issue`
- `repair_patch_failed`

约束：

- `RepairRouter` 继续只负责预算和 scope 合法性裁决，不因为具体业务歧义类型新增路由分支。
- `ambiguous_shared_signal_unresolved` 由 `RepairAgent` 在 planning repair 已尝试收敛但仍无法得到唯一 exporter 时写入。

## 8. 下一阶段准入条件

只有在以下条件同时满足后，才进入 `Send` 并行或正式 HITL 主链化阶段：

1. Phase 5 query suite 稳定通过，且成功 / reject / 多轮 repair / 超预算结果均可复现。
2. planning / assembly / compile 三类 workflow 级 repair 回归全部稳定。
3. trace 摘要已足够支撑并行 fan-out / fan-in 和 HITL 暂停恢复诊断。
4. 若进入 HITL，需先补：
   - 副作用幂等性清单
   - `thread_id` 生成与持久化约定
   - 中断恢复状态契约
