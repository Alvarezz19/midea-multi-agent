# 第四阶段工作流评估报告

> 评估时间：2026-04-11  
> 评估对象：当前仓库中“Phase 4 首版已完成”的 LangGraph 工作流  
> 评估范围：文档、主链代码、现有测试、补充探测、真实查询复跑

## 1. 总体结论

当前仓库的文档与代码主链基本一致，`Phase 4` 的 `verification -> repair_router -> repair_agent -> resume` 闭环已经真实接入，状态契约、trace 摘要、预算控制和独立 HITL POC 也都已落地。

但从“是否已经稳定可用”这个标准看，我的结论是：

- 离线/桩化基线是稳定的：现有 `Phase 1/2/3/4` 回归、runtime 检查、`compileall`、HITL POC 均通过。
- 真实查询复现性还不够：我在 **2026-04-11 21:11:14** 和 **2026-04-11 21:12:17 / 21:15:04** 复跑 baseline 中的中文查询时，当前主链没有得到文档中记录的 `passed / accept`，而是稳定落到了 `planning -> reject`。
- 当前最核心的未解问题不是 Router 或 Repair Loop 结构本身，而是 **模板复用路径对“模板输入口 / 外部输入 / 共享信号”的语义划分仍然不稳**，这会直接把真实模板场景推入 `synthetic_shared_signal_source -> repair_patch_failed -> reject`。

一句话判断：**Phase 4 的闭环“框架”已经成立，但“真实 AHU 模板复用场景下的可通过率”还不能视为稳定达标。**

## 4. 关键问题

以下按严重程度排序。

### 问题 1：真实 baseline 查询在当前环境下无法稳定复现

严重级别：`P0`

证据：

- `outputs/phase4_baseline/baseline_20260411_164711/baseline_summary.md` 记录的固定查询，在更早的 **2026-04-11** baseline 里是 `passed / accept`。
- 我在 **2026-04-11 21:11:14**、**21:12:17**、**21:15:04** 的真实复跑中，至少两条中文查询稳定落入 `planning -> reject`。

影响：

- 当前“Phase 4 baseline 已通过”的说法不能直接等价为“当前环境下可稳定复现”。
- 对外如果把这套流程当成“已稳定支持模板复用 AHU 查询”，风险偏高。

我的判断：

- 这是当前最需要优先修正的现实问题，因为它直接影响对当前阶段成熟度的结论。

### 问题 2：模板复用路径会把大量模板输入口误判为必须由其他子系统导出的共享信号

严重级别：`P0`

这是我认为当前最核心的结构问题。

代码链路：

- `agents/architecture_planner.py:488-495`
  - 当子系统命中模板复用时，`imports` 默认直接取模板 `inputs`，`exports` 默认直接取模板 `outputs`。
- `agents/subsystem_planner.py:207-235`
  - `_compose_interface_signal_names()` 会继续把这些接口名和 `shared_signal_registry` 混合处理。
- `agents/global_assembler.py:304-418`
  - 对每个 import，会尝试寻找“真实 exporter”；找不到就注入 placeholder。
  - 若 `allowed_external=False`，就把它记为 `synthetic_shared_signal_source`。
- `agents/repair_agent.py:305-329`
  - `planning repair` 目前只有两种补救办法：推断唯一 owner，或该信号已在 `requirement_spec` 里被显式标记为 external。

真实证据：

- `outputs/workflow_trace_20260411_211217/workflow_node_io_record.json`
- `outputs/workflow_trace_20260411_211114/workflow_node_io_record.json`

这两次真实复跑里，都出现了大量：

- `送风机运行状态`
- `送风机故障状态`
- `送风机本地/远程`
- `送风机压差状态`
- `送风机启停手/自动`
- `送风机启停手动控制命令`
- `送风机启停自动控制命令`
- `送风机缺风报警延时设定值`
- `送风机故障报警复位`

这些信号在当前实现里被当成“必须有真实 exporter 的共享信号”，最终触发：

- `ir.unresolved.synthetic_shared_signal_source`
- `repair_patch_failed`
- `Unsupported planning repair target: 送风机运行状态`

问题本质：

- 模板的“输入口”并不天然等于“跨子系统共享信号”。
- 在 AHU 真实模板里，这些口很多更像：
  - 外部 IO
  - 操作命令
  - 配置参数
  - 来自项目上下文的控制点
- 但当前主链把它们过早抬升成了 `shared_signal_registry` 的强约束对象。

这就是为什么当前 repair loop 框架没问题，但真实模板场景还是会 reject。

### 问题 3：`ambiguous_shared_signal` 被列为支持，但对典型“多导出方”场景实际上修不动

严重级别：`P1`

代码证据：

- `agents/repair_agent.py:13-15` 把 `ir.unresolved.ambiguous_shared_signal` 列入 `SUPPORTED_RULE_IDS_BY_SCOPE["planning"]`
- 但 `agents/repair_agent.py:305-329` 的实际处理逻辑只有两种：
  - `_infer_unique_owner(...)` 成功，得到唯一 owner
  - 该信号属于 `external_signal_keys`

我额外构造了一个“同一共享信号有两个导出方”的场景，结果是：

- `RepairAgent` 直接返回 `reject / repair_patch_failed`

这意味着：

- 代码层面对 `ambiguous_shared_signal` 的“支持”更像是“能识别并进入 repair scope”
- 而不是“能完成歧义消解”

如果不修正，这一条会给文档和测试带来误导。

### 问题 4：`compile repair` 依赖解析 verifier 的中文 message，耦合过脆

严重级别：`P1`

代码证据：

- `agents/repair_agent.py:44` 定义了 `WIRE_PORT_RANGE_PATTERN`
- `agents/repair_agent.py:387-391` 直接对 `issue["message"]` 做正则解析

问题在于：

- repair 依赖的是“人类可读文案”
- 而不是 verifier 明确提供的结构化字段

这会带来几个风险：

- verifier 文案一改，repair 立即失效
- 多语言/编码差异会影响匹配
- 后续如果要做 prompt 改造、国际化或日志精简，这条 repair 很容易被意外破坏

我做的补充探测显示：

- 当 message 完全符合当前格式时，`compile repair` 是能工作的
- 但它的鲁棒性明显不够，建议改为 verifier 直接输出 `source_real_id / target_real_id / invalid_target_port / target_input_count` 一类结构化字段

### 问题 5：当前自动化测试对“真实模板复用+真实中文查询”覆盖不足

严重级别：`P1`

现有测试对 Phase 4 的结构覆盖其实已经不错，但主要还是：

- 状态契约
- Router 预算
- RepairAgent 的受控输入
- 桩化的 repair loop
- trace summary 聚合

它们没有拦住这次真实失败，说明以下能力目前没有被有效守护：

- 模板输入口与共享信号/外部输入的边界语义
- 真实中文查询驱动的 `AnalysisAgent -> ArchitecturePlanner -> SubsystemPlanner` 协同
- 真实模板复用场景下的 `synthetic_shared_signal_source` 大量出现
- repair 对“模板输入其实应视为 external”这一类问题的恢复能力

## 6. LangGraph 角度的专项评估

### 6.1 当前用法是合理的

- `recursion_limit=40` 是合理保险丝。LangGraph 官方文档也明确说明，复杂图或循环图可能触发 `GRAPH_RECURSION_LIMIT`，可以在 `invoke` 配置里显式调高。  
  参考：https://docs.langchain.com/oss/python/langgraph/errors/GRAPH_RECURSION_LIMIT

### 6.2 HITL 入正式主链前的准备还不够

- 现在只有独立 POC，正式主链还没有接 checkpointer。
- 官方文档强调：有 checkpointer 时必须通过 `configurable.thread_id` 持久化和恢复状态。  
  参考：https://docs.langchain.com/oss/python/langgraph/persistence

我的判断：

- 现阶段把 HITL 保持在 POC 是对的。
- 但正式入链前，至少还要补：
  - checkpointer 选型
  - `thread_id` 生命周期
  - 节点副作用幂等性
  - 人工审批协议

### 6.3 `Send` 并行还没有进入“可安全主链化”的状态

- 官方 Graph API 文档里，`Send` 是给 map-reduce / 动态 fan-out 用的；状态 schema 需要 reducer 来定义并发更新如何合并。  
  参考：https://docs.langchain.com/oss/python/langgraph/graph-api

而当前仓库状态是：

- 主链仍然串行
- `Send` 只有设计文档，没有正式入链
- `WorkflowState` 还是当前串行链路导向的 TypedDict

我的判断：

- 这不是当前 Phase 4 的 bug
- 但它说明“并行化 readiness”还没完成，现阶段不应该把 `Send` 当成即插即用的小改动

## 7. 优先级建议

### P0

1. 修正“模板输入口 -> 共享信号”的判定策略。
2. 区分至少三类接口：`external_input`、`cross_subsystem_shared_signal`、`template_local_parameter/command`。
3. 为真实中文查询建立最小 smoke 基线，至少守住：
   - `为 AHU 生成送风机标准控制`
   - `为 AHU 生成送风机、冷水阀与电加热联动控制`

### P1

1. 扩展 `planning repair`，让它能处理“模板输入应转 external”的场景。
2. 重新定义 `ambiguous_shared_signal` 的修复策略；如果暂时不能修，就不要在 `SUPPORTED_RULE_IDS_BY_SCOPE` 中声明支持。
3. 把 `compile repair` 从“解析 message 文本”改成“消费 verifier 的结构化 repair payload”。
4. 增补覆盖 `repair_patch_failed / no_repairable_issue / issue_ids filtering` 的单测。

### P2

1. 在主链接入正式 persistence / HITL 之前，先补齐 checkpointer 与 side-effect 设计。
2. 在并行化前，先设计好 reducer 和 fan-in 契约，再引入 `Send`。

## 8. 最终判断

如果把“第四阶段是否完成”理解为“Repair 闭环首版的代码框架已经入链”，答案是：**是，已完成。**

如果把“第四阶段是否已经能稳定支撑真实 AHU 模板复用查询”理解为“当前环境下可以可靠复现 baseline 并通过”，答案是：**还不能。**

当前最值得优先处理的，不是继续堆更多 LangGraph 节点，而是先把“模板输入口 / 外部输入 / 共享信号”的语义边界收紧，否则 Repair 闭环会持续在真实模板场景里被前置规划语义问题击穿。
