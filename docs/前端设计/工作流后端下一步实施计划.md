## 2. 当前主要缺口

接下来真正阻塞前后端联调和后续扩展的，不再是“有没有 API”，而是下面这些问题：

### 2.1 checkpointer 仍是进程内内存版

当前 [app/services/checkpointer_factory.py](</D:/yjsproject/midea/app/services/checkpointer_factory.py:1>) 使用的是 `InMemorySaver`。

这意味着：

- 服务重启后线程状态会丢失
- 无法支持多进程 / 多实例部署
- 只能做单进程开发和基础演示

### 2.2 后台执行模型仍是进程内线程

当前 `WorkflowService` 的 `task_scheduler` 默认是本地线程启动。

这意味着：

- 任务状态与 API 进程强耦合
- 不适合长任务、异常恢复和服务重启
- 不利于后续做流式事件推送和运行治理

### 2.3 仓储仍是内存态

当前 thread / attempt 元数据只保存在内存里。

这意味着：

- API 进程重启后历史记录会消失
- 前端刷新恢复仅在当前进程生命周期内有效
- 与 trace 文件索引之间还没有形成稳定一致的“元数据真相源”

### 2.4 trace 接口还没补齐

草图里提到的：

- `GET /api/workflow/threads/{thread_id}/attempts/{attempt_id}/trace`

当前还没落地。

### 2.5 健康检查仍偏轻量

当前 `health` 已能检查：

- LLM provider
- embedding provider
- checkpointer 是否可用
- Chroma collections 是否存在

但还没有检查：

- 真实 review/resume 所需 persistence 是否可恢复
- trace 根目录写权限
- worker 执行器是否就绪

### 2.6 缺少启动与联调说明

当前代码能跑，但还没有一份明确的后端启动文档和联调口径说明。

## 3. 下一阶段目标

下一阶段建议定义为：

**把后端从“开发骨架”推进到“前后端可稳定联调版”**

达到这个目标后，团队应该可以做到：

- 前端直接按固定 API 开始做页面
- 后端支持 review 中断与恢复
- thread / attempt 具备跨进程或跨重启最小恢复能力
- trace 和结果查询口径稳定
- 后续继续演进到 SSE 与 `Send/reducer` 时，不需要推翻现有 API

## 4. 建议按 5 个工作包推进

## 4.0 工作包 0：冻结运行契约

### 目标

先把 `thread_id`、`attempt_id`、checkpoint、状态机和错误结构的边界固定下来，避免后续 durable checkpointer 与 worker 改造时返工。

### 必须冻结的规则

1. `thread_id` 是 LangGraph checkpoint 恢复指针，对应一条可恢复会话主线。
2. `attempt_id` 是 API / trace / 前端展示层的一次运行主键，不直接替代 LangGraph 的 `thread_id`。
3. V1 阶段同一 `thread_id` 同一时刻只允许存在一个 active attempt。
4. active attempt 指状态为 `queued`、`running`、`interrupted` 的 attempt。
5. 当同一 `thread_id` 已存在 active attempt 时，新的 `POST /runs` 必须返回 `409 Conflict`，除非调用方显式创建新的 `thread_id`。
6. `POST /resume` 只能恢复当前 active interrupted attempt，且 `attempt_id`、`review_id` 必须同时匹配。
7. worker 开始执行前必须把 attempt 从 `queued` 或 `interrupted` 原子切换到 `running`，避免重复执行。
8. worker 完成后只允许落成 `interrupted`、`completed`、`rejected`、`failed` 四类终态/等待态。
9. `completed`、`rejected`、`failed` 的 attempt 不允许再次 `resume`。
10. 后端错误响应统一为稳定结构，前端不依赖 FastAPI 默认 `detail` 格式。

### 状态机转移

V1 对外状态固定为：

```text
queued -> running
running -> interrupted
running -> completed
running -> rejected
running -> failed
interrupted -> running
```

不允许：

```text
completed -> running
rejected -> running
failed -> running
interrupted -> completed   # 必须先经 resume worker 回到 running
```

### checkpointer 选型口径

建议冻结为：

- `dev/test`：优先使用 SQLite checkpointer，便于本地重启恢复测试。
- `prod`：预留 PostgreSQL checkpointer，不在 V1 联调阶段强制落地。
- `memory`：只允许单测或临时 demo 使用，不作为默认 API 服务配置。

### 最低验收

- 同一 `thread_id` 有 `queued / running / interrupted` attempt 时，再次 `POST /runs` 返回 `409`。
- `POST /resume` 的 `attempt_id` 不匹配时返回 `409`。
- `POST /resume` 的 `review_id` 不匹配时返回 `409`。
- `completed / rejected / failed` attempt 再次 `POST /resume` 返回 `409`。
- 错误响应结构统一，至少包含 `error.code`、`error.message`、`error.details`。

### 建议输出

- 补充服务层运行契约测试。
- 补充状态机转移测试。
- 更新错误响应模型。
- 在联调文档中明确 active attempt 规则。

## 4.1 工作包 A：把运行时改成可恢复版本

### 目标

把当前 `InMemorySaver` 替换成真正的持久化 checkpointer。

### 建议实现

- 保留 `checkpointer_factory.py` 作为唯一入口
- 不要把具体 checkpointer 类型散落到 `workflow_service.py`、`workflow_runner.py`、路由层
- 先做一个“本地可持久化”版本，再考虑更复杂的生产部署

### 最低验收

- 服务重启后，同一个 `thread_id` 还能 `get_state()`
- 若线程停在 review，重启后仍可 `resume`
- 现有 API 契约不变

### 建议输出

- `checkpointer_factory.py` 升级
- 新增针对 persistence 的 API 级测试
- 文档说明“开发 / 测试 / 生产”三种配置口径

## 4.2 工作包 B：把执行器从本地线程抽象成正式 worker 模型

### 目标

把“启动任务”和“执行任务”解耦。

### 建议实现

- 保留当前 `task_scheduler` 抽象
- 先把它收口成正式接口，而不是直接内联线程逻辑
- 后续可以平滑替换为队列 / worker

### 最低验收

- `POST /runs` 只做提交，不阻塞整次工作流执行
- `POST /resume` 只做提交，不阻塞整次工作流恢复
- worker 异常时 attempt 会稳定落成 `failed`
- worker 成功 / interrupt / reject / fail 四类结果都能稳定回写仓储

### 建议输出

- 执行器接口定义
- 本地线程版执行器
- 可替换的队列执行器占位实现
- 一组 worker 生命周期测试

## 4.3 工作包 C：补全前端联调所需接口与投影

### 目标

把前端真正会用到的 API 补齐，不让前端再需要碰内部状态。

### 必做项

- 新增 `GET /trace`
- 明确 `attempt detail` 和 `attempt result` 的字段边界
- 在 DTO 中预留 `subtasks`，但暂不强制返回
- 明确错误码

### 建议补充

- `GET /threads/{thread_id}/attempts/{attempt_id}/trace`
  - 返回 trace 摘要而不是全量节点 IO
- `GET /threads/{thread_id}/attempts/{attempt_id}/state-history`
  - 仅供调试页使用，默认限制条数

### 最低验收

- 前端不用读磁盘路径就能拿到结果页和调试页所需数据
- review 卡片字段稳定
- 错误码至少区分 `not_found`、`conflict`、`internal_error`

## 4.4 工作包 D：补启动说明、联调说明和验收基线

### 目标

让前后端能立即开始并行协作，不靠口头同步。

### 必做项

- 补一份后端启动说明
- 补一份联调约定
- 补一组 API 验收命令

### 最低验收

- 新同学拿到仓库后，能按说明启动服务
- 前端同学知道哪些字段稳定、哪些字段暂不依赖
- 回归时有明确命令，不靠人工点点看

## 5. 建议实施顺序

按优先级建议这样推进：

1. 工作包 0：冻结运行契约
2. 工作包 A：durable checkpointer
3. 工作包 B：正式 worker 执行模型
4. 工作包 C：补 trace / 调试接口与 DTO
5. 工作包 D：补文档和联调说明
6. 完成上述后，再进入 SSE

原因：

- 不先冻结 `thread_id / attempt_id` 边界，durable checkpointer 和 worker 很容易做出互相冲突的恢复语义
- 没有持久化 checkpointer，review 恢复和 thread continuity 就不稳
- 没有正式 worker，API 很难支撑更长的实际任务
- trace / 调试接口是联调效率的关键，但它依赖前两项更稳的运行基线

## 9. 风险与注意事项

### 9.1 不要把生产 checkpointer 选择拖到 SSE 之后

否则：

- review 恢复能力不稳
- 事件流语义会建立在不稳定线程模型上

### 9.2 不要让前端直接消费 `summary_json`

否则：

- trace 格式一变，前端就跟着坏
- 无法控制调试字段与页面字段边界

### 9.3 不要把当前线程执行器当长期方案

当前线程执行器只适合：

- 本地开发
- 单进程演示
- 测试环境

不适合作为最终运行模型。

### 9.4 不要提前把 API 设计绑死到串行节点顺序

后续还要接：

- `Send`
- reducer fan-in
- 更细粒度的 trace / subtasks

所以现在继续坚持：

- `status` 是产品态
- `current_step` 是主阶段
- DTO 是投影层

## 10. 一句话版本

下一步最应该做的不是继续加页面，而是把后端 API 从“开发骨架”推进到“可稳定联调版”：优先完成 durable checkpointer、正式 worker 执行模型、trace 摘要接口和联调说明，然后再进入 SSE 与更强运行态治理。
