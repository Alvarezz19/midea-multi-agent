# 工作流前端下一步实施方案

> 最后更新：2026-04-23  
> 依据：`工作流总结文档.md`、`工作流节点输入输出说明.md`、`docs/前端设计/工作流后端API草图.md`、`docs/前端设计/工作流后端启动与联调说明.md`、`workflow.py`、`app/api/*.py`、`app/services/*.py`、`tests/test_workflow_api.py`。  
> 目标：在现有 Workflow API V1 已可联调的基础上，给前端提供一份可以马上开工的任务方案。

## 1. 当前判断

当前后端已经具备前端 V1 闭环所需的服务层，不需要前端直接调用 LangGraph 图对象，也不需要读取完整 `WorkflowState`。

已稳定可用的后端能力：

- `POST /api/workflow/runs`：创建 thread 与 attempt，并提交后台运行。
- `GET /api/workflow/threads/{thread_id}`：查询 thread 概览。
- `GET /api/workflow/threads/{thread_id}/attempts`：查询 attempt 历史。
- `GET /api/workflow/threads/{thread_id}/attempts/{attempt_id}`：轮询当前 attempt 详情。
- `POST /api/workflow/threads/{thread_id}/resume`：提交人工 review 并恢复执行。
- `GET /api/workflow/threads/{thread_id}/attempts/{attempt_id}/result`：查询最终结果。
- `GET /api/workflow/threads/{thread_id}/attempts/{attempt_id}/trace`：查询 trace 摘要投影。
- `GET /api/workflow/threads/{thread_id}/attempts/{attempt_id}/state-history`：查询调试态历史投影。
- `GET /api/workflow/health`：查询运行依赖健康状态。

当前工作流主链：

```text
analysis
  -> ambiguity_router
ambiguity_router
  -> clarification_review | retrieval
clarification_review
  -> clarification_review | clarification_apply | retrieval
clarification_apply
  -> retrieval | END(reject)
retrieval
  -> architecture_planning
architecture_planning
  -> architecture_review
architecture_review
  -> architecture_review | architecture_feedback_apply | subsystem_planning
architecture_feedback_apply
  -> architecture_planning(feedback/clarify) | subsystem_planning(approve) | END(reject)
subsystem_planning
  -> global_assembly
  -> coding
  -> verification
  -> repair_router
repair_router
  -> END(accept/reject) | repair_agent
repair_agent
  -> subsystem_planning | global_assembly | coding | END
```

前端目录现状：

- `frontend/` 目前为空目录。
- 下一步应从工程脚手架、API 客户端、工作流运行页、HITL review 闭环和结果页开始。
- 不应先做复杂图编辑器，也不应把首版阻塞在 SSE / WebSocket 上。

## 2. V1 目标与边界

### 2.1 V1 必须完成

V1 的目标是跑通完整业务闭环：

```text
输入需求
  -> 发起运行
  -> 轮询进度
  -> 命中 clarification / architecture review 时暂停
  -> 用户提交 approve / feedback / clarify / reject
  -> 后端 resume
  -> 继续轮询
  -> 查看 completed / rejected / failed 结果
  -> 查看 trace 摘要与调试历史
```

V1 必须交付：

- 工作流启动页：输入 `user_query`、标题、HITL 开关。
- 工作流详情页：展示 `status`、`current_step`、阶段轨道、诊断摘要、当前 review 卡片。
- Review 交互：支持 `approve`、`feedback`、`clarify`、`reject`，并正确提交 `attempt_id` 与 `review_id`。
- 结果页：展示 `json_text`、`compile_report`、`verification_report`。
- Trace 调试页：展示 `/trace` 摘要和 `/state-history` 瘦身历史。
- 会话恢复：刷新页面后可通过 `thread_id` 与 `attempt_id` 恢复当前视图。
- 错误处理：统一消费 `{ error: { code, message, details } }`。
- 健康检查：进入页面时调用 `/health`，对不可运行依赖给出明显提示。

### 2.2 V1 暂不做

以下能力不要放进首版关键路径：

- 用户系统、鉴权、租户隔离。
- 复杂图形编辑器。
- 直接编辑完整 `WorkflowState`。
- 直接读取 trace 文件物理路径。
- 固定百分比进度条。
- 强依赖固定串行节点数量。
- SSE / WebSocket 实时流。
- `Send` 并行子任务可视化。
- reducer fan-in 详情页。
- `repair_review` 正式审核页。
- 生产级 PostgreSQL checkpointer / 队列 worker 的前端运维页。

## 3. 产品与界面方向

### 3.1 设计定位

前端不应做成普通聊天页。这个工作流更接近“美的智慧楼宇控制程序生成驾驶舱”，视觉应贴合美的品牌的清爽、友好、智能、可靠风格，而不是做成厚重的黑色工业监控屏。

参考口径：

- 美的官方 Brandbook 强调 `simply ideal`、友好、智能技术、质量、创新与价值：https://brandbook.midea.com/home
- 美的中文官网的业务表达集中在智能家居、工业技术、楼宇科技、机器人与自动化、美的能源等板块，并强调绿色、高效、智慧、数字化解决方案：https://www.midea.com.cn/zh

设计方向建议采用“美的蓝白科技 + 智慧楼宇控制台”：

- 主视觉：以白色、浅灰、低饱和蓝为基础，结合柔和卡片、清晰分区和轻量流程线，呈现美的官网常见的干净、现代、可信赖气质。
- 品牌色：以美的蓝作为主强调色，辅以浅蓝、冷灰、白色；状态色只用于语义提示，例如通过绿、警示橙、失败红，避免喧宾夺主。
- 行业感：保留 AHU / 楼宇控制的专业信息密度，但不要使用过重的深色机房大屏风格；更适合“智慧楼宇运维平台”而不是“黑盒工控台”。
- 信息层级：页面应像美的官网和企业级数字化产品一样清爽克制，优先突出当前运行状态、待审核动作、结果产物和异常诊断。
- 字体：正文优先选择清晰、现代、适合中文长文本阅读的字体；标题可以略带科技感，但不应使用过度机械、游戏化或赛博朋克风格。
- 图形语言：可使用圆角矩形、轻量线框、蓝色渐变光晕、细分割线和状态胶囊；避免紫色渐变、霓虹边框、厚重金属质感。
- 动效：保持轻盈、友好和可解释，只在运行阶段切换、review 挂起、结果完成时做明确反馈；避免到处加无意义微动效。

### 3.2 页面结构

建议首版使用单页应用，核心页面如下：

```text
/workflow
  工作流启动与最近运行列表

/workflow/:threadId/:attemptId
  工作流运行详情

/workflow/:threadId/:attemptId/result
  结果与导出视图

/workflow/:threadId/:attemptId/debug
  trace 摘要与 state-history 调试视图
```

如果首版开发速度优先，可以把 `result` 与 `debug` 做成详情页内的右侧 Tab，而不是独立路由。

### 3.3 推荐布局

详情页建议采用三栏布局：

```text
┌──────────────────────────────────────────────────────────────┐
│ 顶部：thread / attempt / status / health / 操作按钮           │
├───────────────┬──────────────────────────────┬───────────────┤
│ 左侧历史栏     │ 中间运行轨道与阶段详情         │ 右侧审核/结果栏 │
│ thread 概览    │ stage rail / diagnostics      │ review card    │
│ attempt list  │ trace summary                  │ result summary │
└───────────────┴──────────────────────────────┴───────────────┘
```

移动端降级为：

```text
顶部状态
-> 当前 review / 结果摘要
-> 阶段轨道
-> attempt 历史
-> trace 调试折叠面板
```

### 4.3 API 状态机

前端只需要认以下对外状态：

```text
queued -> running
running -> interrupted
running -> completed
running -> rejected
running -> failed
interrupted -> running
```

状态对应 UI 行为：

| 状态 | UI 表现 | 轮询策略 | 允许操作 |
| --- | --- | --- | --- |
| `queued` | 等待执行 | 开启轮询 | 可返回列表，不允许重复提交同 thread |
| `running` | 正在运行 | 开启轮询 | 禁用 review 提交 |
| `interrupted` | 等待人工 review | 停止常规轮询或低频轮询 | 允许提交 review |
| `completed` | 完成 | 停止轮询 | 允许查看结果和 trace |
| `rejected` | 已终止 | 停止轮询 | 允许查看终止原因 |
| `failed` | 失败 | 停止轮询 | 允许查看错误和 trace |

建议轮询策略：

- `queued` / `running`：每 `1500ms` 轮询一次详情。
- 连续 5 次无变化后退避到 `3000ms`。
- `interrupted`：停止高频轮询，仅在用户提交 review 后立即刷新。
- `completed` / `rejected` / `failed`：停止轮询，并拉取 result / trace。
- 页面重新聚焦时，立即刷新一次当前 attempt。

## 6. Review 交互设计

### 6.1 Review 卡片

当 attempt detail 满足以下条件时显示 review 卡片：

```text
status == "interrupted"
review.review_id 非空
review.status == "pending"
```

卡片内容：

- 阶段标签：`clarification_review` 或 `architecture_review`。
- 问题正文：`review.question`。
- 上下文摘要：`review.context_summary`，保留换行并支持折叠。
- 选项按钮：来自 `review.options`，值必须传 `option.value`。
- 反馈输入：当选择 `feedback` 或 `clarify` 时必填。
- 高级约束：`updated_constraints` JSON 编辑区，默认折叠。

### 6.2 提交规则

提交体固定为：

```json
{
  "attempt_id": "<attempt_id>",
  "review_id": "<review_id>",
  "decision": "approve | feedback | clarify | reject",
  "answers": [],
  "feedback": "",
  "updated_constraints": {}
}
```

前端校验：

- `attempt_id` 必须来自当前详情页，不允许用户改。
- `review_id` 必须来自当前 review 卡片，不允许用户改。
- `decision` 必须是 `approve`、`feedback`、`clarify`、`reject` 之一。
- `feedback` / `clarify` 建议要求填写文本说明。
- `updated_constraints` 必须是合法 JSON 对象；非法时在前端阻止提交。

提交后行为：

- 成功返回 `status=running` 后，立即刷新 attempt detail。
- 重新进入 `running` 轮询策略。
- 如果返回 `409 conflict`，刷新 attempt detail，并提示当前 review 已过期或 ID 不匹配。
- 如果返回 `validation_error`，展示后端 details 中的字段错误。

由于 `frontend/` 目前为空，建议首版直接建立轻量前端工程：

- 构建工具：Vite。

## 12. 验收标准

首版完成的最低标准：

- 用户可以从页面发起一次工作流运行。
- 页面能展示 queued / running / interrupted / completed / rejected / failed。
- 页面能在 interrupted 时展示 review 卡片。
- 用户提交 review 后，后端能 resume，页面能继续轮询。
- completed 后能展示 `json_text`、`compile_report`、`verification_report`。
- trace 页面能展示摘要，不直接读取 `summary_json`。
- 页面刷新后能根据 URL 恢复当前 thread / attempt。
- 后端统一错误 envelope 能被前端统一展示。
- 前端不依赖完整 `WorkflowState`。
- 前端不依赖固定节点数量或百分比进度。

## 13. 风险与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 轮询期间 attempt 状态短暂滞后 | 页面看起来未更新 | 用明确的“正在同步”状态和页面聚焦刷新补偿 |
| review_id 过期或不匹配 | resume 返回 409 | 前端刷新 attempt 并提示用户当前审核已变化 |
| `current_step` 新增未知值 | 阶段轨道显示错误 | 未知值降级展示原值，同时记录前端日志 |
| 后端 trace summary 为空 | 调试页空白 | 展示“暂无 trace 摘要”，不读取磁盘文件 |
| `json_text` 很大 | 页面卡顿 | 结果页默认折叠，仅预览前若干行，提供复制或下载 |
| 后续接入 `Send/reducer` | 当前阶段轨道不够细 | 使用 `subtasks` 预留区，但 V1 不渲染并行细节 |
| 后续接入 SSE | 轮询代码要迁移 | 把轮询封装在 hook 内，组件只消费 attempt state |

## 14. V1.1 预留方向

V1 跑通后，再考虑：

- SSE 事件流：用后端事件替代高频轮询。
- `subtasks` 展示：为正式 `Send/reducer` 增加并行子任务区域。
- 更细粒度 trace：按节点展示输入输出摘要，但仍不暴露完整内部状态。
- 下载接口：后端提供安全的结果文件下载，而不是前端拼磁盘路径。
- 生产运行治理：展示队列 worker、PostgreSQL checkpointer、持久化仓储状态。
- 权限与审计：记录 review 操作人、时间、理由。

## 15. 官方约束参考

本方案与 LangGraph 官方运行约束保持一致：

- LangGraph 是用于长运行、有状态 agent / workflow 的编排框架，核心能力包括 durable execution、streaming、human-in-the-loop 等：https://docs.langchain.com/oss/python/langgraph/overview
- 使用 checkpointer 时，`thread_id` 是 checkpoint 的主键，缺少它无法保存状态或从 interrupt 后恢复：https://docs.langchain.com/oss/python/langgraph/persistence
- interrupt 暂停后可通过 `__interrupt__` 暴露暂停信息，并通过 `Command(resume=...)` 恢复：https://docs.langchain.com/oss/python/langgraph/interrupts
- 后续如果做 SSE / streaming，可优先参考 `stream_mode="updates"` 与 `stream_mode="values"` 的语义：https://docs.langchain.com/oss/python/langgraph/streaming
- 前端可视化 LangGraph pipeline 的方向可以参考官方 frontend overview，但本项目 V1 先采用自有 REST 轮询投影 DTO：https://docs.langchain.com/oss/python/langgraph/frontend/overview

## 16. 一句话结论

下一步前端应先做“工作流运行驾驶舱”而不是“聊天页”或“图编辑器”：以 `thread_id / attempt_id / review_id` 为三大主键，基于 REST 轮询跑通创建、暂停审核、恢复执行、结果查看和 trace 调试，等 V1 闭环稳定后再进入 SSE、并行子任务和生产运行治理。
